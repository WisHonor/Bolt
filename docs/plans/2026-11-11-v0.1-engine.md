# v0.1, clean code and the gate: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Bolt v0.1's code is fit to ship in a closed product, and its speed gate checks exactly what "v0.1 ships when" says. Nothing taken from Git's source or its tests is left in the code, nor anything else whose license a closed product can't carry; the code that followed Git's code is rewritten from Git's documentation and the `git` program's behaviour, and decides every case as the old code did; a planted deep tree is refused at once; the gate follows the owner's new rule and is run ten times on the finished code; and the result is attacked once more.

**Architecture:** No stored format, `bolt.toml` key, ID or command output changes. The rewritten modules keep their interfaces, so the rest of the engine doesn't move. While a rewrite is in progress the old module lives in `crates/bolt-vcs-core/src/legacy/`, compiled for tests only, so that a comparison can run both on the same inputs from the outside; it is deleted before the merge. The deep tree is caught where every walk already counts entries against the save's limits (decision 130).

**Tech Stack:** Rust (the workspace's toolchain) and the crates already in the workspace. No new dependency. `hyperfine` runs only on CI runners. Git's documentation is read from Git for Windows' own copy (`C:\Program Files\Git\mingw64\share\doc\git-doc\`) or git-scm.com.

**Spec:** decisions [128](../decisions/128-v0.1-ships-without-goto-within-twice-gits-time.md) to [131](../decisions/131-code-that-follows-another-projects-is-rewritten-clean.md), with 023, 099, 108, 126 and 127; [milestones.md](../milestones.md) "v0.1 ships when"; [benchmarks.md](../benchmarks.md) §1; [testing.md](../testing.md) §4 and §5; [storage-format.md](../storage-format.md) §3 and §12; [security.md](../security.md); the decisions behind each rewritten module (038, 046, 047, 054, 060, 094 to 098 for Git's settings and ignore files; 031 and 033 for Git's refs and config; 051 and 059 for names).

**Rulings made while building:** `2026-11-11-v0.1-engine-rulings.md`, kept as the build goes, verbatim.

## The clean-room rules (every rewrite task)

A rewrite has three roles, each a fresh subagent, never the same one twice:

1. **The rewriter** works from a behaviour brief the controller writes (what the module must decide, its interface, the Bolt decisions behind it), Git's documentation, and the `git` program run on cases it makes up. It must not open Git's source (`C:\Users\elmas\AppData\Local\Temp\bolt-audit\` and any other copy), the old module (`crates/bolt-vcs-core/src/legacy/`), the old module's tests, the old module's git history (`git log -p`, `git show`, `git blame` on it), the audit's working files, or `docs/releases/v0.1.0-code-audit.md`. Its report lists every file it opened and every web page it read.
2. **The comparer** checks the new module against the old one from the outside: it may read the old module's public signatures (not its bodies) and calls both on the same inputs, generated and hand-made, refusals included. It reports each disagreement as an input with both answers, never as code.
3. **The reviewer** has Git's source open (and may clone it into a temp folder outside the repository) and says whether any part of the new module still follows Git's code, part by part, with the evidence. A part that does is rewritten again by a fresh rewriter, from a description of what to restructure that names no Git code.

Then the old module, its legacy copy and the comparison against it are deleted; the comparisons against `git` and the module's own tests stay.

## Task 1: The gate follows the owner's rule

**Files:** modify `bench/run.sh` (`gate_check`), `bench/README.md`, `crates/bolt-vcs/tests/speed.rs` (`status_on_an_unchanged_100_000_file_project`), the comments of `.github/workflows/nightly.yml` (`speed` job) and `.github/workflows/speed-gate.yml`.

**What:**
- `gate_check` holds each step to its own limit: `status` 2, `small-change` 2, `back-to-first` 3. Each line prints the step, Bolt's median, Git's median, the ratio, the limit, and `ok` or `OVER`; for `back-to-first`, a ratio over 2 that is within 3 adds `over the v0.2 goal of 2`. The job fails only when a step is over its own limit. The header line says what the limits are. The means, best and worst runs stay printed as now.
- The status test fails (an assert with both times in its message) when either of its two runs takes 2 s or more; it still prints both times.
- The README and the workflow comments say the same.

**Done when:** `gate_check` run by hand on made-up results in a temp folder (hyperfine's JSON shape, three steps, each tool) passes with `back-to-first` at 2.5 (and prints the goal note), fails with it at 3.1, fails with `status` at 2.1, and passes with all three under 2; `cargo clippy` and `cargo fmt --check` pass; the speed test compiles (it is ignored and runs nightly).

## Task 2: A walk measures a listing it meets again (decision 130)

**Files:** modify `crates/bolt-vcs-core/src/listing.rs` (the one place the measure lives, beside `SaveLimits`), `diff.rs` (the two-save walk), `snapshot.rs` and `snapshot/walk.rs` (the scan's walk against the last save, wherever a saved folder is gone through path by path), `snapshot/only.rs` (a partial save's walk), and their tests; add a test file in `crates/bolt-vcs/tests/` for the commands. Survey every reader of listings first (`grep` for `.listing(` and `SaveLimits`) and name in the report each walk that goes path by path and how it was changed, and each reader that doesn't need to (write-out's look-ups, `tidy`'s marking, `verify`).

**What:**
- One measure, beside `SaveLimits`: for a listing ID, the entries below it counted by path, the deepest folder below it and the longest path below it; each listing read once however many paths reach it (a memo by ID kept for the whole walk); no recursion (a save may nest deeper than a stack); a listing that can't be read is the same error the walk gives for it.
- Each walk keeps, per save it walks, the set of listing IDs it has entered. Entering one a second time, it measures it, counts the whole (entries, depth from where it is, longest path from where it is) against that save's limits at once, and walks it without counting its entries again. In the two-save walk each side does this on its own.
- The count stays the count by path: a save the limits allow is never refused; a save past them is refused with the same error and words as today ("it has more than 10000000 files and folders in total", and the depth and path errors), before the repeated part is walked.

**Done when:**
- Unit tests: the measure on a chain (24 levels, two entries each to the next) gives 2^25 and reads each listing once; honest saves with two folders of the same contents give the same counts, results and output as before; a save of 9,999,999 entries by path made with shared listings is accepted and one of 10,000,001 refused (with small limits where the walk takes them, as the existing tests do).
- A test per command, on a project whose save holds the planted chain: `goto` to it, `changes --save` of it, `show` of it, `discard` and `status` when the folder is on it with the chain's folder deleted from disk, `shelf`/`unshelf` and `undo`/`redo` across it each refuse in under 10 seconds in a debug build, write nothing, and say the save has more than 10000000 files and folders in total.
- Every existing test passes unchanged.

## Task 3: The audit, written up

**Files:** create `docs/releases/v0.1.0-code-audit.md`. Controller's task, from three auditors' findings (read-only, with Git's source at `v2.56.0` open).

**What:** for every module, test file, fuzz target, test vector, script and data file: what other project it relates to, whether it follows that project's code or only its documented behaviour, what was done about it, and that project's license. Then what a lawyer should look at: each rewritten module and how it was rewritten; the days the repository was public with the old code and no license; the old code in the repository's history; builds of it among the workflow artifacts and the stale draft release; that the new code was written by a model that may know Git's source from its training, so the reviewer's comparison is the evidence that it doesn't follow it; the dependencies' licenses and their duties.

**Done when:** every row says what was found and what was done; the file says plainly whether any code following another project's code remains.

## Tasks 4 to N: one task per module the audit names (rewrite, and its test material)

Filled in from the audit (Task 3): each module the audit finds following Git's code (or another project's) gets one task, run under the clean-room rules above. Each task:

- moves the old module to `crates/bolt-vcs-core/src/legacy/` (compiled for tests only), and its tests that copy Git's material with it;
- has the rewriter write the new module at the old path, with the same public interface, from the controller's behaviour brief; its own tests; and comparisons against the `git` program where Git has a command that shows the behaviour (`git check-ignore`, `git check-ref-format`, `git config`, `git ls-files`, ...), skipped with a message where `git` isn't installed;
- has the comparer run old against new on generated and hand-made inputs until they agree on every case, refusals included;
- has the reviewer judge the new code against Git's source;
- keeps the module's fuzz target driving the new code;
- removes the legacy copy and the old-against-new comparison once all three agree, and rewords every comment that named Git's source;
- for test files outside rewritten modules that copy Git's tests (the audit lists them), replaces the copied rows with comparisons against `git` and cases of our own.

**Done when (each):** the comparer finds no case where old and new differ; the reviewer finds no part that follows Git's code; the comparisons with `git` pass; every existing test that isn't Git's copied material passes unchanged; the fuzz target builds against the new code.
