## Please confirm

Each of these can be reversed before publishing. The first two freeze with format 1.

1. **What zstd reads past the rules a header shows** (rulings 10, 18 and 19). A match reaching back past the window, and a compressed block unpacking past the block limit, are read wherever zstd reads them. Refusing them would need a zstd decoder of Opalro's own. The spec lets any reader read or refuse them. A later Opalro must keep reading what v0.1 reads, since `tidy` may copy a planted frame of that kind over a person's own copy. That isn't fixed in v0.1, because a pack reaches someone's store only through write access to their `.opalro`.
2. **Short names past `opalro~9`** (rulings 8, 21 and 22). A save doesn't refuse them. The red team's two ways around that were looked at: a Mac's FAT driver opens no long-named entry by a short form (shown on macOS 15), and Linux's FAT driver, past `~9`, takes names from the clock, which no rule can list. Windows compares each folder's real short names.
3. **The name's pull request was merged by Claude** (ruling 1), on your word "do everything".
4. **The first run's one looser check, in the AlmaLinux container only** (ruling 14).
5. **The guide stays written for a computer with a desktop** (ruling 15).

## Rulings

1. **The name's pull request (#33) was merged by Claude, with a merge commit, before this work began** (`02a4eaf`). Its checks were green on all three systems, with the Release workflow's builds and clean-machine check. The owner's rule is that a change to what is stored waits for the owner's review. The owner's answer to the report on #33 was "do everything so that we can conclude v0.1 as finished", which this work read as that review given.
2. **The decisions are numbered in the order of the owner's lines:** 153 the code that follows Rust's, 154 zstd, 155 the short names. Signing changes no decided behaviour (decisions 119 and 145 already ship v0.1 unsigned), so it has no record of its own: the page for the owner says "decided".
3. **"No dictionary" means no `Dictionary_ID` field at all,** not only no dictionary: zstd reads a field holding 0 as "no ID given", a frame that "may or may not need a dictionary". Premise checked: zstd writes the field only for a dictionary ID other than 0, and `only_one_plain_frame_goes_to_the_one_call_decoder` passes the frames of both of Opalro's writer paths (one call, and streamed), with and without a content size.
4. **The frame header's reserved bit and its unused bit must both be clear.** RFC 8878 tells a decoder to refuse the reserved bit and not to interpret the unused one. zstd reads a frame with the unused bit set (the test shows it), but a later zstd may give that bit a meaning, and a frozen format must not depend on what a library does with a bit Opalro never writes.
5. **The window rule holds for a single-segment frame too,** whose window is its content size, as RFC 8878 defines it. A single-segment frame over 128 MiB is refused. Opalro's own frames have windows of a few MiB at most.
6. **`op9975` is `.opalro`'s hashed prefix,** worked out with the hash the Wikipedia article "8.3 filename" gives. The hash gives Git's four prefixes (`gi7eba`, `gi250a`, `gi7d29`, `maba30`) and `GI2837~1`, the name a Windows runner gave `.git` (security.md, T2). This laptop's NTFS drive gave `.opalro` the name `OP9975~1` once `OPALRO~1` to `~4` were taken. A test reads it again on every Windows run, and skips only on a drive that makes no short names.
7. **The hashed form is refused in the shape `git fsck` refuses for `.gitmodules`:** eight characters, the start of `op9975` shortened as the counter grows. That takes in `~1234567`, so names that start with `~` now go through the check. Only names of exactly that shape are refused, so `~$report.docx` stays an ordinary name.
8. **The plain short names stop at `opalro~9`,** as the owner's line says. On Windows the real short names in each folder are still compared, which catches whatever a drive made. The red team's reading of the kernel's source (S2, ruling 22) says Linux's FAT driver, past `~9`, takes `OP`, four hex digits from the clock and `~1` to `~8`, which no fixed rule can know. Listed under "Deferred".
9. **No new test vectors for zstd.** The review before the freeze listed the missing refusal vectors among the findings the owner left where decision 148 put them; F1 is the only finding the owner changed. Unit tests cover each refused shape on both read paths.
10. **Each block's size is checked from its header, on both read paths, before zstd sees it** (the code review's Important finding). RFC 8878 limits a block to the frame's window, or 128 KiB if that is smaller. zstd 1.5.7's streamed decoder checks that limit (`zstd_decompress.c`, lines 1315 and 1367), but its one-call decoder doesn't check a raw or RLE block, so a frame with one raw block of 1 MiB was read when Opalro read the entry in one call, and refused when it streamed it. Both paths now follow the block headers first (`BlockWalk` in `pack.rs`): a raw block's size, an RLE block's size and a compressed block's stored size. The damage test shows the two paths disagree with that check taken out. **What a header can't show,** a compressed block that unpacks past the limit, stays as zstd leaves it. The one-call decoder reads one, and the streamed decoder refuses one unless it decodes the whole frame in one go (line 2185). Such a block is outside RFC 8878, and no writer makes one. Checking for it would need a block decoder of Opalro's own, or the streamed decoder for every small entry, which would lose the speed work's one-call reads (decisions 110 and 111). So the spec says a reader may read such a block or refuse it, and that v0.1 reads it when it reads the entry in one call (stored in at most 1 MiB and, for a file's contents, at most 1 MiB unpacked too), and refuses it otherwise. Please confirm.
11. **A content size field of all ones is a content size,** and must equal the entry's (the review). zstd reports it as "no size given", so whether the frame has a size is read from the header's flags. The header checks are in one function (`frame_start`), used by both paths.
12. **The rest of the review:** the save corpus (`corpus.rs`) and the hand-made journal in `writeout/tests.rs` now hold `opalro~9`, `op9975~1`, `OP997~12` and `~1234567`, so the save, and the write-out each new spelling meets, are tested and not inferred. The comment on RT15's Windows probe no longer says no fixed list knows `.opalro`'s hashed short name. The header gets boundary tests: windows of exactly 2^27 and 2^27 + 2^24, a single segment of 2^27 and 2^27 + 1 bytes, the reserved bit, and each width of the content size field.

13. **The rehearsal is part of the clean-machine job,** not a job of its own. Every Release run rehearses, on the runners that already made a first run, sharing their downloads, and a failed rehearsal stops the draft, since the release job waits for that job. The rehearsal goes like this:
    - It lays the website out from the website zip, with the four archives and `SHA256SUMS` beside it.
    - It fills the download page's placeholder with `SHA256SUMS`' text, as part 7 of the owner's page says to, then checks that the page's fingerprints are `SHA256SUMS` exactly and that every archive the page names is there.
    - It serves the folder on `127.0.0.1` and downloads from it with `curl` or `Invoke-WebRequest`.
    - It runs the first run from what it downloaded: the checksum, the agreement (the archive's, byte for byte), the install, a first save, and a report written with the report form.

    That happens on the five runners, and on the Linux runner in three bare containers, plus Windows Server Core, which was cheap to add. Run 43316090796 passed everywhere.
14. **One check of the first run is looser where the system itself puts `~/.local/bin` on the PATH,** as AlmaLinux 9's root shell does. There `opalro` is found before the guide's PATH line is added, and the folder stays on the PATH after Opalro is removed, so the run says so in its log instead of failing. The workflow allows that only in the AlmaLinux container, which it starts with `FIRST_RUN_LOCAL_BIN_ON_PATH=yes` (the final review's point). Anywhere else a `~/.local/bin` already on the PATH fails the run, and everywhere `opalro` must still be found only at `~/.local/bin/opalro`. Please confirm.
15. **What the rehearsal found in the bare containers, left as it is:**
    - None of the three Linux images has `nano`. ubuntu:22.04 and debian:12 have no editor at all, and AlmaLinux has `vi`. So the guide's step that writes `config.toml` with an editor can't be followed as written there.
    - Windows Server Core has no Explorer, so "Extract All" and the steps through the Start menu can't be followed there either. The download page promises Windows Server 2016 or later, which includes Server Core.

    Both are about computers without a desktop. The guide is written for people at one, and the rehearsal does those steps from the shell. A line in the guide for such computers is deferred.

16. **RT16-1 (Medium), a raw or RLE block over its frame's limit, read in one call and refused when streamed: fixed** by the block check (ruling 10), from 69b72d0 on. Its proof runs on every push. Its second case, a compressed block that unpacks past the limit, is ruling 10's, and that proof is switched off with it.
17. **RT16-2 (Low), a content size of all ones read as none: fixed** (ruling 11). Its proof runs on every push.
18. **RT16-3 (Medium), a match that reaches back past the window, read on both paths: ruled on, not fixed.** zstd checks a match against the history it holds, not against the frame's window. Its one-call decoder holds everything back to the frame's start; its streamed one holds the window plus two blocks. So no setting of zstd's refuses such a match, and refusing it would need a decoder of Opalro's own, like ruling 10's block. The spec says it as it says ruling 10's block: two rules of RFC 8878 show only inside the blocks; a reader may read a frame that breaks either, or refuse it; v0.1 reads it wherever zstd does; no writer may write one. Opalro's own frames never hold such a match, since its compressor keeps to its window. Please confirm.
19. **RT16-4 (Medium), `tidy` and merging keep a planted copy over the person's own: ruled on, not fixed in v0.1.**
    - **How.** Merging keeps the first copy of an object it meets, in order of pack name, after checking it as a read does. For a small object that check is the one-call decoder, which reads ruling 10's block and RT16-3's far match. So a planted `00.pack` holding such a frame becomes the only copy, and the person's own is deleted. v0.1 still reads the file; the loss would come only with a reader stricter than zstd.
    - **Why not fixed now.** Checking every copy with the streamed decoder would slow every merge and still pass RT16-3's nearer matches. Storing copies again in Opalro's own encoding goes against decision 103. And a pack reaches someone's store only through write access to their `.opalro`, which could delete their packs outright; v0.1 takes packs from no one.
    - **So:** the spec says Opalro keeps reading what v0.1 reads here. Before networking (v0.3), when packs come from others, what is kept must be checked by a decoder that holds to the window and the block limit, or stored again in Opalro's own encoding (the follow-ups). Please confirm.
20. **RT16-5 (Low), the spec said v0.1 reads ruling 10's block in any entry stored in at most 1 MiB: fixed in the spec** (848f7a3). For a file's contents, the one-call read also needs at most 1 MiB unpacked. The proof is kept, switched off, as the record.
21. **Suspicion S1, a Mac's FAT driver naming `.opalro` `OPALR~1`: not shown, and the hole it needs isn't there.**
    - **What ran.** The red team's probe, on a FAT32 image that GitHub's macOS 15 runner made and mounted, on the branch `redteam/final-probes` (runs 43322841277 and 43326314609, the branch deleted afterwards).
    - **What it found.** No short form opened `.opalro`: not `OPALR~1`, `OPALRO~1`, `OPALRO` or six other forms. No short form opened an ordinary long-named file either: `longfilename.txt` didn't answer to `LONGFI~1.TXT` or four other forms.
    - **So:** macOS's FAT driver opens such an entry by its long name only, and a save's `opalr~1` makes a folder of its own. No change. The probes stay in `redteam16_platforms.rs`, switched off.
22. **Suspicion S2, Linux's FAT driver past `~9`: no change.** Past `OPALRO~9` it takes `OP`, four hex digits from the clock and `~1` to `~8` (the red team's reading of the kernel's source), which no fixed rule can list. It needs nine names with `.opalro`'s first six letters in the folder before `.opalro` is made. Ruling 8 is corrected to say so.
23. **Suspicion S3, a frame that makes one byte more than recorded holding up to three times the record's memory for a moment on Windows: no change.** It wasn't shown. On Linux the red team measured only more address space reserved (595 MiB against 339 MiB for a 256 MiB record), and the read stops at one byte past the size.
