# Milestone 2: rulings made while building

- **Plan:** [2026-11-02-milestone-2-coming-from-git.md](2026-11-02-milestone-2-coming-from-git.md)
- **Dates:** 2026-11-02 to 2026-11-04; merged in pull request #5
- **Decided by:** Claude, while building, under the owner's instruction to run the plan through to the merge. The owner can reverse any of them.

Building the plan raised choices it didn't settle, and a few places where it disagreed with a decision or with Git. Each ruling says what was decided, why, and what it costs if it turns out wrong. Task numbers are the plan's. The rulings that change a decided behaviour became decision records [043](../decisions/043-red-team-m2-rulings.md) and [044](../decisions/044-red-team-m2-final-rulings.md). The questions still open for the owner are under "For the owner to decide" in the [follow-ups](2026-11-01-milestone-1-follow-ups.md).

## Building the tasks

- **R1 (task 9).** `ObjectType` and `object_id(kind, data, hash)` are defined in task 9 (`git/mod.rs`), which also adds `miniz_oxide`, `sha1-checked` and `sha2`, because `craft.rs` writes and hashes objects there. The plan put them one and two tasks after their first use. *If wrong:* nothing; only the order changes.
- **R2 (task 10).** Blobs stream through a reader, `Repo::blob_reader(&self, id) -> Result<BlobReader<'_>, GitError>`, instead of `copy_blob(id, out)`. It implements `Read`: whole objects stream, deltified ones are read from memory, and a wrong ID fails the last read. `PackSet::add_content_from` reads from a `Read` and stores nothing on an error. *If wrong:* an adapter later.
- **R3 (task 6).** The ignore differential test takes Git's real walk as the reference: `git ls-files --others --exclude-standard -z`, with Git's personal lists off, for which files a save keeps, and `git check-ignore --no-index` for single paths. Each rule file is written as `.gitignore` for Git and `.boltignore` for Bolt. `check-ignore` alone doesn't apply "a file in an excluded folder can't be re-included". *If wrong:* a weaker differential test; task 15's tests would catch the gap.
- **R4 (task 1).** A standard user facing a folder the Administrators group owns gets the "Administrators group … not running as administrator" message, not "another user account". It names the owner truthfully, and its hint still offers `safe-folders`. *If wrong:* a standard user reads a hint about elevating that they can't follow.
- **R5 (task 1).** The windows-sys feature `Win32_System_SystemServices` (for the `SE_GROUP_*` constants) is used. A feature of a crate already in use isn't a new dependency, and `Cargo.lock` is unchanged. *If wrong:* nothing.
- **R6 (task 2).** `warnings` is in every `--json` document, error documents included, holding what was collected before the failure, or `[]`. A stable contract beats a key that comes and goes. *If wrong:* an empty list read as "nothing noted" when the failure came first.
- **R7 (task 2).** When a command fails, people see only the error, with no `warning:` lines; the JSON error document still lists the warnings. A damage note next to an error caused by that damage would read twice or mislead. *If wrong:* in text, a person misses a note collected before an unrelated failure.
- **R8 (tasks 4 and 13).** `set_test_pack_limit` stays process-wide, and task 13's interrupted-import test has its own test binary (like `crates/bolt-vcs-core/tests/pack_limit.rs`), so no test running beside it sees the limit. A thread-local would silently miss the worker threads a later milestone adds. *If wrong:* one more test binary.
- **R9 (task 5).** Decision 035's "Git's own list, applied on every system" means the stricter of Git's builds: Git for Windows' HFS check also ends at a backslash. No new decision record, since it narrows nothing ordinary and is what 035 asked for; design.md §5.16 and security.md T2 say "as Git for Windows applies it". *If wrong:* names with an invisible character before a backslash are skipped on import, with a warning.
- **R10 (task 6).** Ignore lines follow current Git: `match_pathname` keeps one byte of the literal prefix, as in Git 2.52 and later (checked against Git 2.56's `dir.c`). The differential test leaves out lines shaped like `x**/y` only when the installed Git is older. Decision 038 says "as Git", and the current release is the reference. *If wrong:* for that rare shape, Bolt keeps a file that an older Git (Apple's, or a long-term Debian or Ubuntu release) ignores.
- **R11 (task 6).** `Matcher::decide` takes `impl AsRef<[u8]>`, so names that aren't UTF-8 stay ignored when a rule ignores them, as in Git; `Matcher::in_force_bytes()` was added; `.boltignore` need not be UTF-8, since Git reads bytes and task 7 reads `.gitignore` with the same parser. security.md T11 and design.md §5 were corrected to match. *If wrong:* small interface changes in task 7.
- **R12 (task 7).** `SaveOutcome::NothingChanged` carries the save's warnings: a skipped `.gitignore` matters whether or not anything changed, and R7 only keeps warnings off a save that stops. *If wrong:* one more field.
- **R13 (task 7).** The walk loads the last save's listing of a folder when the walker reaches that folder, since `ignore` and `walkdir` yield a folder before its contents. Ignored names are compared exactly as stored, so a case-only rename of an ignored saved file drops it. The link test points at an outside `*.key` file rather than `/etc/passwd`. *If wrong:* an ordering change in `ignore` would record ignored saved files as removed; tests would catch it.
- **R14 (task 7).** "The kind matches" means folder versus not-folder: file, executable and link count as one kind, as Git keeps a tracked file through a mode or type change. Project links are task 8's, kept before this rule applies. An unreadable `.gitignore` stops the save as `SaveError::Ignore` with the system's reason, like `.boltignore`. *If wrong:* an ignored saved file that changed between file and link stays saved.
- **R15 (task 8).** Entries kept by rules (a), (b) and (d) stay even when their folder, or any folder above it, is gone from disk, and so do the folders leading to them. Something on disk in the way (a file where a kept entry's folder was) stops the save with a clear message. Rule (c) needs the file present. This follows decisions 036 ("whatever is there… or nothing") and 019 #2 ("never recorded as deleted"). *If wrong:* a user who deletes a folder holding a submodule still has the link in the next save; submodules are removed in Git, as 036 says.
- **R16 (task 8).** A kept folder's contents count against `MAX_SAVE_ENTRIES`, read from the store only as needed and stopping once over. It is a format limit that `diff` enforces, and Bolt must never write a save it refuses to read. *If wrong:* extra store reads for kept folders.
- **R17 (task 8).** Rule (c) is decided from the content ID `store_file` already computes (read once, streamed, exact), not from a separate capped read. *If wrong:* nothing known.
- **R18 (task 8).** The search of gone folders stops at the last save's limits rather than failing, because milestone 1's red-team tests need a save next to an over-limit save to succeed. A damaged listing inside a gone folder stops the save, as a damaged listing of a folder on disk already does. *If wrong:* deleting a folder no longer works around a damaged listing inside it.
- **R19 (task 8).** Gone folders are rebuilt in linear time and memory. No full paths are built inside a gone folder: the trimmed subtree (only kept entries and the folders leading to them) is built from the last save's listings with an explicit stack and becomes one entry of its parent. What is in the way is checked only at the edge, against the names the walk found. Entries and depth are counted as it goes, and it stops at the last save's limits, as in R18. A cap that stops every save would let a hostile import block all saves, which milestone 1's RT-6 rules out. *If wrong:* about 150 lines replaced.
- **R20 (task 8).** The walk and the kept-entry code moved to `snapshot/walk.rs` in a move-only commit (`IgnoreRules` renamed for what it now holds), since `snapshot.rs` had reached about 3,080 lines. *If wrong:* one large move, reviewed as a move.
- **R21 (task 9).** `MAX_REFS` is 7,600,000 (64 servers × 100,000, plus branches, tags and other refs), so decision 033's limits stay reachable. `object_id` returns a `Result`, since a detected SHA-1 collision is `Broken`. Owner refusals are carried as `GitError::NotYours(RepoError)`. The reftable hint uses `git refs migrate --ref-storage-format=files`; the plan's flag was wrong. *If wrong:* a hostile repository can make Bolt hold about 1 GB of refs before refusing.
- **R22 (task 9).** sha2 0.10.9, not 0.11: it shares digest 0.10 with sha1-checked 0.10, which has no stable digest 0.11 release yet, so four duplicate crates go away. *If wrong:* one minor version behind on sha2.
- **R23 (task 9).** `HEAD` and loose refs are read exactly as Git's `parse_loose_ref_contents` reads them (hex, then the end or whitespace, anything after it ignored; `ref:` with Git's whitespace skipping and trimming), instead of the plan's exact forms ending in `\n`. Bolt should read every repository Git reads unless that is unsafe, and these forms aren't. The refusals for packed-refs, a NUL in config, negative versions and one-level names stay. *If wrong:* nothing known.
- **R24 (task 9).** A NUL in `HEAD` or a loose ref is `Broken`: Git never writes one, the same as a NUL in config. A ref that is itself a symlink stays refused: Bolt never follows links, and Git writes them only under `core.preferSymlinkRefs`, off by default for years. `cpufeatures` stays duplicated (blake3 needs 0.3, sha1 0.10 needs 0.2) until sha1-checked has a stable digest 0.11 release. *If wrong:* a repository with symlinked refs needs `git pack-refs --all` or `git symbolic-ref` before import.
- **R25 (task 10).** Orphan pack files are skipped, as Git skips them: a `.pack` without its `.idx` is being written, and an `.idx` without its `.pack` is being removed. An object then missing is `Changed` if `objects/pack` changed since it was listed, otherwise a missing object. *If wrong:* a truly damaged repository missing a `.pack` reports missing objects instead of naming the orphan `.idx`.
- **R26 (task 10).** Up to 16 packs stay open between reads: opening one per read cost 4.8 times as much on Windows, and a pack deleted after opening keeps being read as it was. REF_DELTA bases are looked up in the same pack only, since packs on disk are self-contained. `Repo` is not `Sync`. The truncation test cuts each file at every one of its last 160 lengths, and at every 16th length before. *If wrong:* a `git gc` running at the same time on Windows sees Bolt's open files.
- **R27 (task 10).** A `.pack` that is a folder, link or device is an error ("not a regular file", naming it) rather than skipped, as Git skips files that aren't regular. Git's `stat()` follows links and Bolt never does, and naming the odd file helps more than a later "missing object". *If wrong:* a repository with a linked `.pack` can't be imported until the link is replaced.
- **R28 (task 11).** `parse_tree` returns empty names, `.`, `..` and names holding `/`, because decision 035 makes them the importer's to skip with a warning. The plan asked to refuse them, which contradicted 035. *If wrong:* nothing; the importer skips them.
- **R29 (task 11).** Bolt stays stricter than `git fsck` in eight shapes: a repeated tree, parent, author or committer line; a header line without a key; a stray continuation line; no empty line after the header; more than 1,024 parents; odd modes such as 120777, 40755, 644 or 140000; modes past 16 bits; a tag header without a key. Decision 032's format can't rebuild some of them exactly, and an odd mode would otherwise turn into a submodule link. Each refusal has its own message and hint (Git reads it, Bolt can't import it as it is, rewrite that history) instead of "check with git fsck". *If wrong:* such repositories need their history rewritten before import.
- **R30 (task 11).** `is_lfs_pointer` is a port of Git LFS's own parser (it accepts its alpha URL, whitespace, CRLF, extensions and `+6` sizes), with Bolt's bounds first: an empty blob and one over 1,024 bytes are not pointers (decision 037: "Git LFS's own test"). *If wrong:* nothing known.
- **R31 (task 11, amended).** `parse_tree` caps a tree at `listing::MAX_ENTRIES` (1,000,000) entries, since one Git tree becomes one Bolt folder listing and storage-format §3 limits those. A tree just over the cap is refused even when the importer would skip its extra entries; only hostile trees are that big. *If wrong:* such a tree stops the import.
- **R32 (task 11).** design.md §5.16 got one sentence: a blob is an LFS pointer when Git LFS's own pointer parser accepts it and it is non-empty and at most 1,024 bytes. Decision 037's "Git LFS's own test" already says so, and its example form is only a summary, so there is no new decision record. *If wrong:* nothing.
- **R33 (task 12).** The importer is the first product code to write project-link records (storage-format §7), so it got one product encoder (`test_support::add_link` uses it) and a test vector, `tests/vectors/project_link.json`: every format on disk has test vectors. *If wrong:* one extra vector file.
- **R34 (task 12).** encoding_rs 0.8.44, with what it pulls in (multiversion_no_op, rustversion, scopeguard, simdutf8); cargo-deny passes. The plan allows encoding_rs and its dependencies. *If wrong:* four small extra crates.
- **R35 (task 12).** Two spec clarifications without a new decision record. Storage-format §5 accepts Jujutsu's uppercase letters, as Jujutsu's own decoder does; decision 032 says it decodes "in Jujutsu's letters". Section 7's readers reject a project link whose system isn't `git` or whose commit ID isn't 20 or 32 bytes; that is version 1 of the record, and another system gets a new record version. *If wrong:* a later system needs a new record version.
- **R36 (task 12).** Names that aren't UTF-8 are collected across the whole import (the first 100 and a count) and left out of listings while the conversion keeps going. `Converter::finish()` returns `NotUtf8Names` after the last commit, before anything is committed. This follows decision 019 and the plan's corpus ("the second lists both"). *If wrong:* a repository with bad names takes a full conversion before it stops.
- **R37 (task 12).** The tag list has a budget across the whole import for what it will hold (names, messages, `git_tags` bytes), equal to its 512 MiB record cap and checked before a chain is read. Tag outcomes are remembered by the ref's target ID, copied and counted per ref. *If wrong:* a repository with more than 512 MiB of tag data stops early instead of late.
- **R38 (task 12).** The converter and its tests moved to `import/convert.rs` in a move-only commit. `ImportError` and task 13's flow stay in `import.rs`, as with `snapshot.rs` and `snapshot/walk.rs`. *If wrong:* one move.
- **R39 (task 13).** Tag names clash only when exactly equal, not when they differ only by letter case. Decision 034 renames only tag names that aren't UTF-8 or are over 255 bytes, and the tag list accepts names that differ only by case; the plan's "same rule" sentence is read through 034. *If wrong:* two tags that differ only by case can't both be checked out by name on a drive that ignores case.
- **R40 (task 13).** The lock file says `start` while `begin` runs for an import, since nothing can show it before `format` exists. `bolt import` prints `start`'s elevated-terminal note too (documented in json.md). Another tool's `.bolt` is one holding any entry besides `format`, `store`, `state`, `cache`, `tmp` and `config.toml`, so a Finder `.DS_Store` in an unfinished `.bolt` blocks a re-run. *If wrong:* a rare re-run needs the stray file removed.
- **R41 (task 13, clarified).** Renaming follows decision 033's own words: "names Bolt's rules refuse are renamed", and "a name that then equals another … gets -2". Names that need no change, first in byte order of their letter-case group, keep their names and are reserved first. A renamed name takes a suffix only when its new name is taken, so a lone `feature+x` becomes `feature-x`. Every other name gets the first free `-N` (N ≥ 2) in byte order of the original names, and a suffixed name must be free whatever its letter case. Tags follow R39. design.md and the plan's global constraints got one clarifying sentence, and decision 033 is unchanged. *If wrong:* in rare sets of clashes, different `-N` numbers than a literal byte-order reading gives.
- **R42 (task 13).** Skipped refs are capped like skipped entries: text shows the first 100 and a count, and JSON's `skipped_refs` is `{count, first}`. Mirror clones carry huge numbers of `refs/pull/*`. *If wrong:* JSON readers see only the first 100 names.
- **R43 (task 13).** A `.bolt` that Git tracks at the top of HEAD's tree stops the import before anything is made: Bolt never adopts files Git wrote as its own store. The hint says to run `git rm -r --cached .bolt` and commit, or to move it. *If wrong:* such repositories need that one change before import.
- **R44 (task 14).** The line-ending stop asks no question. Its hint offers both ways on in every case (have Git write the files back, or `bolt save --accept-crlf`), which meets decision 039's "offers two ways on" and "without a terminal it names the flag". The wording is singular for one file. A file that vanishes before the check opens it reports `Unreadable(NotFound)`, as `store_file`'s shared opener does. *If wrong:* a question in a terminal can be added later. This one is open for the owner.
- **R45 (task 16).** The plan's corpus row "`.git\hooks\x` imported as one name" contradicts decision 035 and Git's own `is_ntfs_dotgit`: a backslash ends the `.git` part, on every system (R9). The corpus asserts it is skipped with a warning, like the other `.git` spellings. *If wrong:* nothing; it is the stricter, decided behaviour.
- **R46 (task 16).** A SHA-1 collision can't be built as a Git object: sha1dc detects one only when the attack blocks meet their chaining state, and Git's object header shifts them. The corpus asserts the ID-mismatch case instead and points at task 10's collision test on the hasher itself (`crates/bolt-vcs-core/src/git/id.rs`, `tests/vectors/shattered-prefix.bin`). *If wrong:* nothing.
- **R47 (task 16).** Pack version 3 imports, since Git reads versions 2 and 3 and so does the code; the plan's corpus row grouping it with errors was a slip. The test shows version 3 imports and version 4 is refused. The ownership row points at the unit test in `git/mod.rs`, since adding a seam for it would change functions that touch disk. *If wrong:* nothing.
- **R48 (task 16).** Decision 037 has two parts: the pointer test is Git LFS's own (R30), and "a small file that merely looks like a pointer also stops the import". R30 and R32 missed the second, so `looks_like_lfs_pointer` follows 037's listed signs: at most 1,024 bytes, non-empty, a first line holding a git-lfs or hawser version URL, an `oid sha256:` line with 64 hex digits, and a `size ` line. Either test stops the import, each with its own message, and design.md §5.16 says so. *If wrong:* a repository holding an ordinary file shaped like a pointer can't import until that file changes.
- **R49 (task 17).** `start --json`'s `save` may be `null` after the read-back warning; json.md isn't released yet, and this is documented like `changed_files: null`. The identity note mentions the environment only when both `BOLT_USER_NAME` and `BOLT_USER_EMAIL` are set, since one alone names nobody (decision 025). There are no lines ready to paste when a name or email was cut. A `safe-folders` line below a `[section]` is an error where the list is needed, because it explains why the trust didn't apply, rather than a warning. *If wrong:* one more warning kind later.
- **R50 (task 18).** Task 18 also took small items that earlier reviews left in the files it touches. They were task 17's two small fixes in `repo.rs` and `import.rs` (in their own commits) and the `fuzz/Cargo.lock` refresh that the fuzz deny job needs. It also covered cheap test gaps:
  - task 14's boundary at twice the base;
  - task 6's `\!`, and a save where `!` can't re-include a file under an ignored folder;
  - task 10's loop of three REF_DELTA objects;
  - task 15's exact count of skipped person lines.

  *If wrong:* a slightly larger task.

## The red-team fixes

- **R51–R58 (the first session's fixes).**
  - RT3-1: nothing is allocated from an index's claimed count before its data is checked; memory grows as names pass the order check. Objects are capped at 2^24 per index and in total.
  - RT3-2: compact tables in the first pass, and decision 043's limit of 1,000,000 extra parents, checked in the first pass.
  - RT3-3: find the root cause (a newer miniz_oxide, or a fix inside Bolt's one `Inflater`, and no new dependency without the owner), and a short stream never sends the user to `git fsck`. The cause was Bolt's own loop.
  - RT3-4: a budget across the import on bytes rebuilt through deltas, set with a measured margin over git/git; R59 and R61 refine it.
  - RT3-8: drop the first reader before opening the second.
  - RT3-9: encode the tag list at its exact size, keeping no decoded copy.
  - RT3-10: a change-id header is used only once per import (decision 043), and such commits are counted in a warning; R60 widens it.
  - RT3-5 and RT3-6: as decision 043 says.
  - RT3-7: the include warning, as decision 043 says. Its proof test stays ignored, citing 043.
- **R59 (RT3-4).** The allowance rests on data a hole in a sparse file can't supply: the larger of 4 GiB and 500 times the compressed bytes of pack entries actually inflated, each entry counted once. A new proof test pairs the RT3-4 repository with a sparse empty pack. design.md states the limit, and the honest big-file case with its repack hint. The real fix, rebuilding each delta chain once from its bottom base as `git index-pack` does, is left as a question for the owner. *If wrong:* honest repositories with long chains of very big files need a repack before import.
- **R60 (RT3-10).** A change-id header is also refused when it equals the change ID any commit gets from its own commit ID; otherwise a hostile commit could still share a plain commit's ID. RT3-7's warning covers includes in `config.worktree` too. A sparse checkout set in the user's global Git config isn't caught, and that is a follow-up. *If wrong:* nothing known.
- **R61 (RT3-4).** For this milestone the allowance stays as in R59. The docs say honestly that zeros inside a stream still count. They cost Bolt about 1/1,000 (stored) to 1/35 (Huffman-coded) of the time they buy, so a hostile archive can still make an import slow. It can be stopped, nothing is committed, and a re-run reuses what it stored. The redesign is the owner's question:
  - rebuild each chain once, from its bottom base;
  - keep rebuilt objects in the cache;
  - rebuild a deltified big blob once for both of its reads.

  Until then, honest histories of files of 80 to 300 MiB can be refused. Recorded in decision 044. *If wrong:* a hostile archive can waste hours of processor time until the redesign.
- **R62 (RT3-5).** A folder kept whole keeps what the last save holds there, `.git` spellings included; only a save made before the fix, or a planted `.bolt`, can hold one. Writing files out (milestone 3) checks every name again (decision 043). The docs state the exception, and decision 044 records it. *If wrong:* such names stay in history until write-out refuses them.
- **R63–R65 (the second session's fixes).**
  - RT4-2: header results are kept per entry, the search for roots remembers the commits it has looked at, and header walks count against the allowance.
  - RT4-3: a warning when a `.boltignore` line takes back a file that `.gitignore` alone leaves out.
  - RT4-5: packs that list no objects are skipped, the last pack that answered is asked first, and at most 4,096 packs are read, with a repack hint.
  - RT4-4: a delta is applied as it inflates, so only its base and its result are held.
  - RT4-1 is ruled, not fixed: whole records are accepted until chunked and delta storage arrive, and the docs state how much disk an import can take. A write limit for imports is the owner's question. Decision 044 records all of these.

## The final review

- **R66 (task 21).** The final round of fixes took all 20 items of the whole-branch review, including the warning about `.git/info/exclude`. That warning is only a message: decision 038's rule of not reading personal lists stands, and reading the global excludes file is the owner's question. The owner's two checks by hand (importing one of their own repositories, and a project inside OneDrive) are part of milestone 2's "done when", not one of CLAUDE.md's merge gates. So the branch merges once every check passes, as the owner asked, and milestones.md says milestone 2 is merged and counts as done after those two checks. *If wrong:* main holds a milestone the owner hasn't tried by hand yet.
- **R67 (task 21).** `start` refuses an unfinished import only when its store holds file content, since an interrupted `start` leaves its own pack and milestone 1's `interrupted_start_can_be_finished` must keep working. Signs of Git LFS (`.git/lfs`, `filter=lfs`) make the first pass look through HEAD's files for a real pointer rather than refuse on the signs alone, since decision 037 allows repositories after `git lfs migrate export`. The first pass's progress covers the commit walk, not the short pass over tags.
- **R68 (task 21).** Two items left after the final fixes had to be fixed before merging. The pre-scan's limits were missing, so its memory was unbounded, contradicting design.md and security.md T11. The advice for unfinished projects could have deleted history. The line-ending hint's gaps (`eol=crlf`, subfolders) became a follow-up. *If wrong:* one more short round.
- **R69 (task 21).** `bolt import` or `bolt start` over a `.bolt` that had saves but lost its `format` file would have written over its head. That would orphan the saves made after the import, and a cleanup would then remove them. Fixed before merging: such a `.bolt` is refused as damaged. Also:
  - the hint no longer offers deleting when a head exists;
  - the lock is probed after the shape check, and only "would block" counts as held, for network drives;
  - the "no more than" wording.
- **R70 (task 21).** Two less likely paths still advised deleting a `.bolt` that may hold history: an empty diary next to packs, and the import's kept-folder hint after the head was written. Both were fixed.
- **R71 (task 21).** Packs with content but no saves mean "run the import again", not damage, because that is exactly what an interrupted import leaves.
- **R72 (task 21).** Three items went to the follow-ups: the uncapped scan of packs for unfinished `.bolt` folders, trusting the head over the packs, and that there is no way out once Git is deleted. The final review was then clean.
