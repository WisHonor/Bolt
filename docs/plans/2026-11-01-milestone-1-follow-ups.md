| Before v0.1 | Two reads the Git reader repeats. `packed_header` reads an entry's header and then `chain` reads the same one again; and when an object isn't in the pack that held the last one, that pack is searched a second time with the others. Neither changes a result. Measure whether they cost anything on a big repository before changing them. |
| Before format 1 freezes at v0.1 | Store each Git tag object once and have tags refer to it ([decision 043](../decisions/043-red-team-m2-rulings.md)), a format change. Each tag keeps its tag objects' bytes today, so many tags through one big tag object fill the tag list's 512 MiB from a tiny repository; the import holds the list only once, but stores every tag's copy. |
| Milestone 5 (scheduled 2026-11-04, decision 044's review) | Rebuilding Git's deltas without repeating work. Today `chain` takes the base it builds on out of the base cache, even the object's own copy; `unpack` never puts the object it built back; a base over 256 MiB is never kept; and `Converter::stream` reads a deltified file over 64 MiB twice in a row. So every version of a big file, or every few, is rebuilt from the bottom of its chain, and the import stops past its allowance for rebuilding ([design.md](../design.md) §5.16). A 200 MiB file in 50 versions changing 1% each needs about 251 GiB against an allowance of about 146 GiB; a 300 MiB one needs about 750 GiB, since both of `Converter::stream`'s reads rebuild each version whole. `git -c core.bigFileThreshold=64m repack -a -d -f` gets either in. The redesign has three parts: rebuild each chain once from its bottom base, as Git's `index-pack` resolves a pack; keep rebuilt objects in the cache; and rebuild a deltified big file once for both reads. Each object would then be built once, as Git's own clone builds it, so honest histories would need no repack, and a hostile pack could no longer buy repeated rebuilding with zeros inside its streams. |
| Milestone 6 | Packaging: Windows hides OneDrive's placeholders from Bolt because Bolt runs in its default "disguise placeholders" mode (security.md §7, checked 2026-11-04). If Bolt is packaged (MSIX, say), or anything changes that mode, try a project inside OneDrive again: placeholders Bolt can see stop every save and every command that reads them in `.bolt`. |
| Milestone 5 | With chunked storage and records stored as deltas (decision 009), look again at what an import writes: whether that ends RT4-1's disk use, or a write limit for imports is still needed ([decision 044](../decisions/044-red-team-m2-final-rulings.md), reviewed 2026-11-04). |
| Before v0.1 | Sparse checkouts set up where Bolt doesn't look ([decision 043](../decisions/043-red-team-m2-rulings.md)): through a config include, which only gets a warning, or in the user's own Git config. ## Smaller items from milestone 2's reviews (2026-11-04)

The task reviews, both red-team sessions and the final review left these small items open. None loses data or lets a repository escape its limits. Each names where it is. The red-team reports list their unproven suspicions separately.

**Messages and wording**
- `owner_allows` (repo.rs) still spells decision 030's rule inline beside `counts_as_users`: one place per rule.
- The elevated-only note repeats the `safe-folders` instruction, and shows even when the folder is already listed.
- `error_json` (output.rs) has no safety-net escape, although json.md calls messages already escaped.
- The `copy_unreadable` warning doesn't say what to do next.
- A `history`/`show` document closed by an error doesn't echo its warnings on stderr.
- The ref-limit messages print raw counts (7600000, 536870912 bytes) where "512 MiB" reads better.
- A detached `HEAD` holding the all-zero ID is refused as "isn't a branch"; say it names no commit.
- The Windows special-name ref message cuts names at 255 bytes and can hide the last part (refs.rs).
- A `config`, `HEAD` or loose ref over Bolt's cap still gets the `git fsck` hint, which can't help.
- When Git tracks a live Bolt project (`git add -A`), the import's tracked-`.bolt` stop doesn't say it is a project.
- "Other accounts on this computer" is wrong for a share root. The planted-`.bolt` case doesn't say what to do with the planted folder, and the identity cap of 256 counts characters before escaping.
- ~~`unnoted` blames Bolt when a folder was swapped for a link mid-walk. `store_file` reports an `InvalidInput` open as `ChangedDuringSave`. Both fail safe; the wording is off.~~ Done 2026-11-05: the walk refuses a folder swapped for a link where it opens it, as changed during the save, so `unnoted` is only ever a fault; a file that can't be opened is judged by what its entry is now.

**Code**
- `pack.rs` and `odb.rs` import each other. `odb.rs` mixes lookup, chains, loose objects, input, zlib, streaming and the cache; move `Input`/`Inflater` out. Test helpers are written twice.
- The short-ID-or-whole-ID fallback is written twice (snapshot.rs, main.rs).
- `Default` on `TagList`/`ServerLines` encodes to what `decode` refuses.
- The HEAD-to-commit step is written twice (import.rs `plan` and `tracked_at`).
- `has_promisor_pack` reads `objects/pack` unbounded, and compares `.promisor` case-sensitively.
- The base cache counts only base bytes; zero-length bases never evict.
- A tag of a tree or blob is judged from the target's header, which isn't checked against its ID.
- The line-ending check opens every file with a base entry. Carrying the walk's file length would skip most.
- `gone()` copies the walked parent's path once per gone folder.
- The `.bolt` check splits names at the first backslash only, while the `.git` check looks at every part. A NUL could end a name in `is_git_alias` as in C Git. `is_hfs_dotgit` checks the whole name, not each backslash part. All are unreachable while names holding `\` are never written.
- A case-only rename of a folder holding a kept entry (`Docs` → `docs`) is refused as not portable on a drive that ignores case. An ignored saved file re-created in the other Unicode form on macOS drops out.

- Finding an unfinished `.bolt` reads its packs for saves with no cap of its own, and every folder on the way up is looked at, even below a real project. A planted `.bolt` with 100,000 first entries costs about 2 s on every command run under it. Look only when no project is found above, and treat more than a few dozen first entries as saves.
- A head left at the first entry is trusted over packs that hold later saves. Decision 010 makes the head the record, but checking the packs too would be safer.
- A `.bolt` an import began, whose Git repository is then deleted, has no way out the hints name: `bolt start` refuses it and `bolt import` can't run. Say to move or delete it then.
