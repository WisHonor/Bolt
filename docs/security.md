# Bolt Security Plan — Draft

> **Status:** drafted in the design phase (2026-10-31), updated after milestone 1's two red-team sessions (2026-11-02) and for milestone 2's Git import (2026-11-03), with the owner's check of a project inside OneDrive (2026-11-04), and for milestone 3's working folder: folder handles, write-out, the caches and the journal (2026-11-06), and for milestone 4's undo, shelves, `tidy`, `save --amend` and crash recovery (2026-11-07), and after its two red-team sessions (2026-11-08), and for milestone 5's chunked files and Git LFS import as decided (2026-11-08) and as built (2026-11-09), and after its two red-team sessions, whose findings are fixed, and its whole-branch review (2026-11-09), and for milestone 6's presets, `bolt.toml`, `bolt setup`, `bolt verify`, the terminal design, Git's words and the release workflow (2026-11-10). Every defense gets a test in [testing.md](testing.md) when it is built. The Windows naming rules were checked against Microsoft's documentation on 2026-11-01 (see §6 and decision 004).

**In plain words.** Bolt assumes that any project you copy, any repository you import and any server you talk to might be trying to hurt you: overwrite files outside the project, run code on your computer, fill your disk, or trick you with tampered history. Bolt's defenses are simple rules, each applied in one place, and every rule has a test.

## 1. What we protect

1. **Your files and history:** never lost, never silently corrupted.
2. **Your computer:** nothing in a project can make Bolt run a program or write outside the project.
3. **Your secrets:** login tokens and passwords never end up in files, logs or history by accident.
4. **Private projects** (from v0.3): nobody reads a project they have no access to.
5. **Availability:** malicious input can make a command fail, but not hang it, crash it, or exhaust memory or disk without limit.

## 2. Who might attack

| Attacker | Example |
|---|---|
| A malicious project | A repository someone shares, or a Git repository you import, crafted to exploit Bolt |
| A malicious or compromised server | Sends tampered saves, oversized data or fake lines |
| A network attacker | Tries to read or change traffic |
| A teammate, within their permissions (v0.3) | Abuses locks, or sends huge files |
| Another customer of a hosting service (later) | Tries to read other projects' data through shared storage |

Out of scope: malware already running as you on your own computer.

## 3. Trust boundaries

- **Untrusted:** everything inside a project (file names, `bolt.toml`, `.boltignore`); everything in `.bolt/store` and `.bolt/state`, since files on disk can be tampered with; everything received from a server; every imported Git repository.
- **Trusted:** your personal settings and the Bolt program itself.

It reads at most 4,096 packs, refusing more before reading any; a pack listing no objects is never searched, and each object is looked for first in the pack that held the last one found. A hole raises the allowance only as far as Bolt inflates it: zeros inside an entry's compressed stream (stored blocks, or a Huffman code that spends one bit on a zero) are inflated and count, at 500 bytes of rebuilding for each byte inflated, roughly 35 to 1,000 times the time the inflating took. While it cuts a file, it keeps the list of its chunks, 40 bytes a chunk: about 80 MiB at 128 GiB, the most it cuts, with chunks of the usual 64 KiB, and four times that for a file made to cut into the smallest. Saving a 10 GiB file of new bytes peaked at 43.5 MB on Linux and 48.7 MB on the Windows laptop, within the memory gate's 500 MB ([decision 084](decisions/084-files-are-read-once-on-several-threads.md), [decision 088](decisions/088-benchmarks-and-the-speed-gates.md), [benchmarks.md](benchmarks.md) §1). ## 5. Engineering rules (approved, decision 022)

- The engine forbids `unsafe` code (`#![forbid(unsafe_code)]`). Memory-mapping files is avoided in v0.1: it needs `unsafe`, and a file changed underneath can crash the process.
- The one exception is a tiny, separate platform crate, which may use `unsafe` for operating-system calls only (for example Windows' Restart Manager, hiding `.bolt/`, file IDs). The owner reviews it line by line.
- No panics in library code: errors are returned, and clippy's `unwrap_used`, `expect_used` and `panic` lints are denied outside tests.
- One place per rule: name validation, path building and write-out each live in a single module that everything else must use.
- The owner reviews anything that touches disk or network before it is merged.
- Spec before code for anything on disk, and test vectors for every format.

## 6. Security tests

See [testing.md](testing.md) §3: fuzz targets for the decoders and parsers listed there, a malicious-repository corpus with at least one case per threat above, Windows-specific tests, and crash tests.

**Hostile Git repositories** (the review of Git's published vulnerabilities, 2026-11-02): `crates/bolt-vcs/tests/corpus_git.rs` holds 25 tests, one of them only on Windows, for 22 of the review's 24 kinds of case. The unusual commits a save keeps exactly are in `import_vs_git.rs`: `Craft` could write them too, but there the test also compares each with Git. A `.git` another account owns is tested in `git/mod.rs`, the only place its owner can be stubbed. A SHA-1 collision can't be built as a Git object, so `git/id.rs` feeds SHAttered's blocks to the hasher. Six fuzz targets cover the Git reader: loose objects, packs and their indexes, deltas, commits, trees and tags, refs, and config.

**Hostile saves written out** (T1 to T5, and the review's write-out cases): `crates/bolt-vcs/tests/corpus_writeout.rs` plants each save, or a switch's journal, as a hostile `.bolt` could hold it, runs `bolt goto` onto it, and checks the exit code, what was written, the warnings and messages, and that nothing reached a folder beside the project or went into `.git` or `.bolt`. Its cases: `.git` spellings, `.gitmodules`' plain and hashed short names and, on Windows, the real hashed short name of `.git`; `.bolt` spellings in a save (its listing is refused) and in a journal (the journal is refused); `\`, drive letters and device names, `COM¹` included; links named like folders with files below them (CVE-2021-21300, CVE-2024-32002); links leading out (absolute, a drive letter, `\\host` and `//host`, `..` past the top), written as placeholders; a hard link at each path a switch writes, to a file outside the project holding what the save expects, which must stay as it was (Git LFS's CVE-2025-26625; one of the files is stored as chunks); modes 0644 and 0755 under a umask of 000 and of 077 (Unix; a file that was 0666 before, and the executable bit flipped on a file already there, are in `crates/bolt-vcs-core/src/writeout/tests.rs`, `modes_are_exactly_0644_and_0755`); a folder a stopped switch made, swapped for a link before the switch finishes, with a file stored as chunks among those below it (`a_link_above_a_written_file_is_never_followed`); names too long for the system, paths over 4,096 bytes and a save 4,096 folders deep. Each case was seen to fail on a write-out with its defence taken out before it passed: on Windows, and for the two that need Unix on Linux (2026-11-06, in a throwaway container): the links leading out with `link_shape` taking every link as real, and the modes case both with no `fchmod` after a file is made and with `mode()` giving 0777 and 0666. The hard links and the chunked file below the swapped folder (milestone 5) were seen to fail on Windows on 2026-11-09, once write-out was made to write files in place, and to write through the link.

**Hostile diaries written out** (T26): `crates/bolt-vcs/tests/corpus_diary.rs` plants diary records, and the saves they name, as a hostile `.bolt` could hold them, makes them current through `state/head`, runs `bolt undo`, `bolt redo`, `bolt unshelf` or `bolt undo --to`, and checks the exit code, the message, what was written, and that nothing reached a folder beside the project or went into `.git` or `.bolt`. The hostile save holds `.git` spellings, links climbing out with `..`, a link named like a folder with a file below it (CVE-2021-21300), names Windows can't hold, and a plain link that must stay a link: a folder change undone or redone onto it, a shelf of it brought back, and an entry whose state names it as the target of `undo --to` must each write it only as `goto` would. A save holding a `.bolt` spelling is refused whole by every one of them, naming the save; an undo whose target isn't a command entry, a state naming a save the store lacks, and a folder change naming one, are refused with nothing changed. What the two write-out corpora share (a project with a folder beside it, and what was written where) is in `crates/bolt-vcs/tests/support/corpus.rs`. Each case was seen to fail with its defence taken out before it passed; the links leading out, with `link_shape` taking every link as real, failed on Windows, macOS and Linux in CI (2026-11-07), since the Windows machine the tests are written on can't make links.

**Hostile chunk lists** (T7 and T9): `crates/bolt-vcs/tests/corpus_chunks.rs` plants a save naming a big file through a chunk list no honest writer makes, as a hostile `.bolt` could hold it, then runs `goto`, `discard`, `status`, `changes` and `show` over it. Its cases: a list naming another file's chunks; a chunk of another size; a missing chunk; a list stored under a chunk's ID; a list claiming 10 GiB for 3 small chunks; a count far past its bytes; and a damaged list beside a good whole copy. Each is refused as damage, naming the pack and why, or the good copy is read and the damaged list's pack named in a `pack_damaged` warning; `status` and `show` read only IDs and sizes, so they pass; nothing wrong reaches the folder, and nothing outside the project changes. Each case was seen to fail with its defence taken out before it passed (2026-11-09). One more case, ignored and run nightly in a release build, writes out a valid list of the most chunks a list may hold (T11).

**Hostile rule files and planted presets** (T33 and T34): `crates/bolt-vcs/tests/corpus_rules.rs` plants a `bolt.toml` that is a link out of the project, a folder, a pipe or 2 MiB; one of nested tables and brackets, one with numbers at every limit, one whose keys and values hold escape codes, and one with as many rules as fit in 1 MiB; a `.boltignore` with ten thousand start marks, and one that is a link; every engine's files planted at once, a folder of a million names, links named like an engine's folders, and engine files deeper than a look goes; and rule files inside an imported repository. Each runs the commands that read the files and checks that they end, in bounded time, with what they wrote, warned and showed as T33 and T34 say, and that nothing outside the project changed.

- ~~Windows: whether synced folders show their placeholders to Bolt.~~ Checked 2026-11-04 in a OneDrive folder with Files On-Demand ([milestones.md](milestones.md)). Bolt refuses every reparse point inside `.bolt/`, and a save refuses a file or folder that is a reparse point but not a link, as a special file it can't read yet (a folder is never walked into; some sync and virtualisation tools make such folders, rarely). Windows hides OneDrive's placeholders from programs like Bolt: they run in its "disguise placeholders" mode by default (a small Rust program reported `PHCM_DISGUISE_PLACEHOLDER`), so Bolt sees ordinary files, even in a `.bolt` set to "Free up space", and reading an online-only file downloads it. PowerShell runs in the "expose" mode, so it shows them as reparse points. Other sync clients built on the same Windows feature (the Cloud Files API) should behave the same; untested. Two things follow. A save used to read every file, so in a folder of online-only files it downloaded them all; since milestone 3 the file-state cache leaves unchanged files unread (decision 053), and Bolt can still see which files are online-only (`FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS`). Milestone 6 packages Bolt as plain archives, with no MSIX, so the mode doesn't change ([decision 119](decisions/119-packaging-v0.1.md)); any package format that changes it brings the check back.
