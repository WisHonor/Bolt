# Bolt Security Plan — Draft

> **Status:** drafted in the design phase (2026-10-31), updated after milestone 1's two red-team sessions (2026-11-02) and for milestone 2's Git import (2026-11-03), with the owner's check of a project inside OneDrive (2026-11-04). Every defense gets a test in [testing.md](testing.md) when it is built. The Windows naming rules were checked against Microsoft's documentation on 2026-11-01 (see §6 and decision 004).

**In plain words.** Bolt assumes that any project you copy, any repository you import and any server you talk to might be trying to hurt you: overwrite files outside the project, run code on your computer, fill your disk, or trick you with tampered history. Bolt's defenses are simple rules, each applied in one place, and every rule has a test.

## 1. What we protect

1. **Your files and history:** never lost, never silently corrupted.
2. **Your computer:** nothing in a project can make Bolt run a program or write outside the project.
3. **Your secrets:** login tokens and passwords never end up in files, logs or history by accident.
4. **Private projects** (from v0.3): nobody reads a project they have no access to.
5. **Availability:** malicious input can make a command fail, but not hang it, crash it, or exhaust memory or disk without limit.

## 2. Who might attack

| Attacker | Example |
|---|---|
| A malicious project | A repository someone shares, or a Git repository you import, crafted to exploit Bolt |
| A malicious or compromised server | Sends tampered saves, oversized data or fake lines |
| A network attacker | Tries to read or change traffic |
| A teammate, within their permissions (v0.3) | Abuses locks, or sends huge files |
| Another customer of a hosting service (later) | Tries to read other projects' data through shared storage |

Out of scope: malware already running as you on your own computer.

## 3. Trust boundaries

- **Untrusted:** everything inside a project (file names, `bolt.toml`, `.boltignore`); everything in `.bolt/store` and `.bolt/state`, since files on disk can be tampered with; everything received from a server; every imported Git repository.
- **Trusted:** your personal settings and the Bolt program itself.

past that many nothing more is kept, so walks repeat, though each is still counted against the allowance. It reads at most 4,096 packs, refusing more before reading any; a pack listing no objects is never searched, and each object is looked for first in the pack that held the last one found. A hole raises the allowance only as far as Bolt inflates it: zeros inside an entry's compressed stream (stored blocks, or a Huffman code that spends one bit on a zero) are inflated and count, at 500 bytes of rebuilding for each byte inflated, roughly 35 to 1,000 times the time the inflating took. So a hostile archive can still make an import slow, though not endless: it can be stopped at any time, nothing is committed, and running it again reuses what was stored, though a second run reads and rebuilds every object again (what was converted is known only in memory) and saves only the storing. | T21 | Terminal spoofing: bidi overrides, line separators, control characters and invisible characters in names, messages, paths and errors | Every untrusted piece of text is escaped before printing: control characters, bidi controls, line and paragraph separators, every other invisible format character (Unicode category Cf, except the zero-width joiner and non-joiner, which emoji and scripts need) and the blank Hangul fillers; the import's summary, warnings and refusals escape ref names, paths and messages from the Git repository the same way; an import never gives two saves one change ID, so a planted commit can't show as a reviewed one in history: a `change-id` header's ID goes to the first commit with it, and to none when another commit's own ID gives it, and the other commits take the IDs their own commit IDs give, with a warning | 025, 028 (red team), 031, 043 |
| T22 | A project claiming to be the user (its settings set the name and email on the user's saves) | Identity comes only from the environment and the user's own settings; a project's identity is ignored, with a note | 025 (red team) |
| T23 | A repository planted in a parent folder (`C:\.bolt`, `/tmp/.bolt`) capturing commands run below it | Refuse a repository unless both the project folder and its `.bolt` folder belong to the user, as Git requires; listing that exact folder in the user's own `safe-folders` trusts both. A Git import applies the same rule to `.git`: one that another account owns is refused unless the project folder is in `safe-folders`. A hint that would offer that line never does for a folder other accounts can write to (on Unix a folder with the other-write bit, `/tmp` included; on Windows the root of a drive or share): it says why instead and asks the user to move the project into a folder of their own. A `safe-folders` line written below a `[section]` of the settings belongs to that section, so Bolt never sees it; where the list is needed, Bolt stops with an error that says the line must go above every `[section]`, and a project that is the user's own never reads the list. On Windows, a folder owned by the Administrators group counts as the user's only in an elevated terminal, as in Git; an elevated `bolt start` that makes such a project says it will open only there unless the folder is in `safe-folders`. A project directly in the user's Windows home folder (`C:\Users\<name>`, which Windows gives to SYSTEM) needs a `safe-folders` entry. A folder whose owner can't be told (FAT, exFAT, some network shares) is refused with a message that says so. `bolt start` ignores an enclosing `.bolt` that isn't the user's. Nothing inside a `.bolt` is looked at before its owner is known. A command resolves the folder it starts in (links, junctions) before it looks for `.bolt`, so the folder judged is the one `.bolt` is in, not a link to it; a `.bolt` seen just before its owner is looked up, then not found, is refused ("changed while Bolt looked at it"), so one that comes back is never used unchecked. Remaining risk: where another account may rename folders inside a folder that counts as the user's, it can rename one the user owns to `.bolt` and fill it; the user's commands below it, outside their own projects, then use it. On Windows that includes every folder made directly under `C:\`, where all signed-in users may change what is inside, and, in an elevated terminal, folders the Administrators group owns. Git has the same gap | 025 (red team), 026, 027, 030, 031, 042 |
| T24 | Submodule tricks: `.gitmodules` names holding `../`, paths into `.git`, addresses that start with `-` or run commands (`ext::`, `update = !cmd`), values with a trailing CR, a submodule's `.git` pointer file aimed elsewhere | Nothing about a submodule is fetched, run or parsed: an import turns it into a project link holding only the commit and never reads `.gitmodules`, which comes in as an ordinary file (or a link, if Git holds one); a save keeps every project link as it is and never looks inside its folder, so a submodule's `.git` pointer file is never read or stored; a folder below the top that holds a `.git` of its own (a submodule added after the import, a nested worktree or clone) is left out of saves whole, as if ignored, with a warning, so nothing in it is read but what the last save holds (decision 046) | 004, 036, 043, 046 |

## 5. Engineering rules (approved, decision 022)

- The engine forbids `unsafe` code (`#![forbid(unsafe_code)]`). Memory-mapping files is avoided in v0.1: it needs `unsafe`, and a file changed underneath can crash the process.
- The one exception is a tiny, separate platform crate, which may use `unsafe` for operating-system calls only (for example Windows' Restart Manager, hiding `.bolt/`, file IDs). The owner reviews it line by line.
- No panics in library code: errors are returned, and clippy's `unwrap_used`, `expect_used` and `panic` lints are denied outside tests.
- One place per rule: name validation, path building and write-out each live in a single module that everything else must use.
- The owner reviews anything that touches disk or network before it is merged.
- Spec before code for anything on disk, and test vectors for every format.

## 6. Security tests

See [testing.md](testing.md) §3: fuzz targets for the decoders and parsers listed there (the project link decoder has none yet: a follow-up), a malicious-repository corpus with at least one case per threat above, Windows-specific tests, and crash tests.

**Hostile Git repositories** (the review of Git's published vulnerabilities, 2026-11-02): `crates/bolt-vcs/tests/corpus_git.rs` holds 25 tests, one of them only on Windows, for 22 of the review's 24 kinds of case. The unusual commits a save keeps exactly are in `import_vs_git.rs`: `Craft` could write them too, but there the test also compares each with Git. A `.git` another account owns is tested in `git/mod.rs`, the only place its owner can be stubbed. A SHA-1 collision can't be built as a Git object, so `git/id.rs` feeds SHAttered's blocks to the hasher. Six fuzz targets cover the Git reader: loose objects, packs and their indexes, deltas, commits, trees and tags, refs, and config.

**Red-team sessions** ([decision 024](decisions/024-red-team-gate.md)). Every milestone ends with a time-boxed session in which a fresh agent attacks Bolt from an isolated sandbox and must prove each finding with a failing test. Every proven finding is fixed, or ruled on in writing, before the milestone is merged; its proof test stays as a permanent test ([testing.md](testing.md) §3), and new threats are added to §4.

**Windows name rules.** Checked on 2026-11-01 against Microsoft's "Naming Files, Paths, and Namespaces" page (dated 2024-08-28): Bolt refuses everything on that list, plus the console devices `CONIN$` and `CONOUT$`, while `COM0` and `LPT0`, which are not on it, stay ordinary names. Bolt also refuses `.bolt`'s short names (`bolt~1` to `bolt~4`) and its stream syntax (`.bolt::$INDEX_ALLOCATION`), because Windows treats both as `.bolt`.

**GitHub settings** (turned on by the owner on 2026-11-01):
- **On:**
  - dependency graph;
  - Dependabot alerts, malware alerts and grouped security updates;
  - Dependabot version updates, configured in `.github/dependabot.yml`;
  - CodeQL code scanning (default setup, which scans the Rust code, the workflows and the red-team Python scripts) with Copilot Autofix suggestions;
  - AI scans of the repository and of pull requests;
  - secret scanning with push protection;
  - private vulnerability reporting.
- **Off on purpose:**
  - agentic autofix: it spends AI credits and opens pull requests on its own;
  - automatic dependency submission: GitHub reads `Cargo.lock` directly.
- CI itself runs with read-only permissions, and its actions are pinned to exact commits ([testing.md](testing.md)).
- **Branch protection** (on since 2026-11-02, the ruleset "Protect main"):
  - force pushes to `main` and its deletion are blocked;
  - every change needs a pull request;
  - the CI checks (`test` on all three systems, and `deny`) and CodeQL must pass.

  Nobody can bypass it, the owner included, so every change, an agent's too, reaches `main` only through a pull request whose checks are green.

- ~~Windows: whether synced folders show their placeholders to Bolt.~~ Checked 2026-11-04 in a OneDrive folder with Files On-Demand ([milestones.md](milestones.md)). Bolt refuses every reparse point inside `.bolt/`, and a save refuses a file that is a reparse point but not a link, as a special file it can't save yet. Windows hides OneDrive's placeholders from programs like Bolt: they run in its "disguise placeholders" mode by default (a small Rust program reported `PHCM_DISGUISE_PLACEHOLDER`), so Bolt sees ordinary files, even in a `.bolt` set to "Free up space", and reading an online-only file downloads it. PowerShell runs in the "expose" mode, so it shows them as reparse points. Other sync clients built on the same Windows feature (the Cloud Files API) should behave the same; untested. Two things follow. A save reads every file today, so in a folder of online-only files it downloads them all; milestone 3's file-state cache must leave unchanged files unread, and Bolt can still see which files are online-only (`FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS`). And if Bolt is ever packaged (milestone 6), check again ([follow-ups](plans/2026-11-01-milestone-1-follow-ups.md)).
