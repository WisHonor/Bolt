This page is for you, the owner. It stays in the repository and never goes on the website. It says what to try, what to confirm, what to ask a lawyer and what to do, in that order, before v0.1 goes out. ## 1. What to try yourself

Half an hour on a project of your own, then ten minutes in a OneDrive folder. Use the archive from the draft, not a build from your own machine: the point is to try what people will get. The draft is made by the first Release run from `main` (part 10, step 3), so this part waits for that run; publish only after it. Follow [the guide](../guide.md) §2 to install it, exactly as a stranger would. If a step is unclear to you, it will be unclear to them: write it down.

**A project of your own (about 30 minutes).** Work on a copy, not the original. In PowerShell:

```text
opalro --version
Copy-Item -Recurse C:\path\to\my-project $HOME\opalro-try
cd $HOME\opalro-try
opalro start
opalro save "First save"
opalro status
```

Then change a few files the way you normally would (edit code, replace an image, delete a file) and go on:

```text
opalro status
opalro changes
opalro save "Second save"
opalro history
opalro goto <the change ID of "First save", from opalro history>
opalro goto main
opalro undo
opalro redo
opalro undo --list
```

(Not the oldest save in the list: `opalro start` made an empty "Start project" save first, and going there empties the folder. Undoable, but alarming.)

Then the corners. You are back on `main` with nothing changed, so each step below first changes a file:

```text
"more" >> notes.txt
opalro shelf "Half-done idea"
opalro shelf --list
opalro unshelf
opalro discard .
opalro undo
opalro save "More notes"
opalro goto <the change ID of "First save">
"other idea" >> notes.txt
opalro save --line try-something "On a new line"
opalro line
opalro goto main
opalro setup
opalro verify
opalro tidy
opalro status --json
```

(`opalro discard .` throws the change away and `opalro undo` brings it back. `--line` works only off a line: on `main` it is refused, guide §8. Change `notes.txt` to any file of yours.)

Also try importing a Git repository you have, on a copy: `cd` into the copy (the folder that holds `.git`) and run `opalro import`, then `opalro history`. If you have one with Git LFS files, try that too.

While you try, look for: a message you don't understand, a `Next:` line that suggests the wrong thing, anything slow, and anything that changed a file you didn't expect. And try what Git users will type: change a file, then `opalro commit -m "x"` (it should save), and `opalro restore .` (it should explain, not run).

**A OneDrive folder (about 10 minutes).** The guide's §2 says Opalro works in OneDrive, and that this was tried on a real OneDrive folder. Try it on yours:

```text
cd $env:OneDrive
mkdir opalro-onedrive-try
cd opalro-onedrive-try
opalro start --preset code
"hello" > notes.txt
opalro save "In OneDrive"
opalro status
```

Then, in File Explorer, right-click a file in that folder and choose "Free up space", so it is kept online only. Run `opalro status` and `opalro save "After free up space"` again. The guide says Opalro shouldn't see the placeholder; if it stops or says something strange, copy the exact text.

When you are done, `Remove-Item -Recurse -Force .opalro` in each try folder, or delete the folders.

### First: the one ruling that held up the release

**Code that follows Rust's own code** ([decision 131](../decisions/131-code-that-follows-another-projects-is-rewritten-clean.md); engine item 1). The [code audit](v0.1.0-code-audit.md) can't say that no code following another project's code remains. About 300 lines of the platform crate's Windows folder code (`crates/opal-vcs-platform/src/dir/windows.rs`) follow Rust's standard library. Rust's license (MIT or Apache-2.0) allows that in a closed product, as long as its notice ships, and it does: Rust's license is in `THIRD-PARTY-LICENSES-RUST.html` in every archive.

**Decided: keep it, under Rust's license** ([decision 153](../decisions/153-the-platform-code-that-follows-rusts-stays.md), yours, 2026-11-12), as the audit recommends: every Rust program owes Rust's notice anyway. The other choice was to have it written again, which would have been new `unsafe` code in the part that guards against a folder swapped under a command. With this ruling the release build was made (parts 7 and 10).

### What publishing makes permanent

**The storage format** (what Opalro writes on disk; [decision 121](../decisions/121-format-1-freezes-at-v0.1.md), [decision 148](../decisions/148-what-format-1s-spec-says-before-it-freezes.md)):

1. **The name:** decided: Opalro, and `opalro` for everything a person types ([decision 150](../decisions/150-the-name-is-opalro.md), yours). It is built into `.opalro/`, `opalro.toml`, `.opalroignore` and the first bytes of the program's own files (`OPALPACK` and five more). Renaming after publishing needs a new format. Part 9 has what is left: a lawyer's check of the name, and the repository's name on GitHub. Also decided: a save refuses `opalro~5` to `opalro~9` and `OP9975~1`, the short name NTFS works out for `.opalro`, on every system, since a Linux computer writing to a Windows drive can't check them ([decision 155](../decisions/155-every-short-name-of-opalro-is-refused.md), yours, choosing option B of [decision 152](../decisions/152-red-team-rulings-on-the-name.md)).
2. **zstd:** decided: exactly one frame ([decision 154](../decisions/154-format-1s-zstd-is-exactly-one-frame.md), yours). zstd is the compression Opalro stores with; a frame is one compressed piece. A stored entry is now exactly one zstd frame: no skippable frame, no dictionary, a window of at most 128 MiB, and nothing after it. Opalro is built without zstd's decoders for the formats from before zstd 1.0. Before, v0.1 read several frames, skipped skippable frames and read the old formats v0.4 to v0.7. Opalro itself always wrote one such frame, so no project changes meaning; a pack made by hand that holds more is now damaged ([task 12's review](../../.superpowers/sdd/2026-11-11-v0.1-package/task-12-format-review.md), F1, the finding it called blocking).
3. **TOML details.** `opalro.toml` may start with a byte order mark; nesting deeper than 80 levels, or a key of more than 80 dotted parts, counts as "not TOML" ([148](../decisions/148-what-format-1s-spec-says-before-it-freezes.md)).
4. **What is left loose on purpose.** The conflict record's layout does not freeze (v0.2 defines it); the ignore rules are pinned to Git 2.52 (2.56 for `:(optional)`) ([148](../decisions/148-what-format-1s-spec-says-before-it-freezes.md)). The engine work changed two sentences of [storage-format.md](../storage-format.md) §12: the ignore rules are read "as `gitignore(5)` describes and `git check-ignore` decides", and `[z-a]` matches `z` alone, as Git and Opalro always did (the old sentence said it matched nothing) (engine item 9).
5. **Five small format items, cheap now, a feature line after** (a feature line is the note in `.opalro/format` that makes an older Opalro refuse the project; [148](../decisions/148-what-format-1s-spec-says-before-it-freezes.md), last consequence):
   - refusal vectors (test examples of bad bytes): only the chunk list has examples a reader must refuse;
   - smaller vector gaps (a project link in a listing, two extra fields in a save, two move notes, a `redo` diary entry, a rebuilt Git commit, a pack frame without a content size);
   - the extra-field limit: a Git commit with a header over 64 KiB or a message over 1 MiB stops a whole import; raising it to 1 MiB fixes that;
   - room to grow in the diary: anything added to a diary entry later needs a new record version (the review's advice: accept it, and say so in the spec);
   - how `opalro.toml` rules match files (top folder or not, `!`, trailing `/`, letter case) is unsaid; no v0.1 code matches them, so v0.2 or v0.3 must define it under the freeze.
6. **How big files are cut and stored** ([082](../decisions/082-how-big-files-are-cut-into-chunks.md), [083](../decisions/083-a-chunk-list-is-stored-under-its-files-id.md)): chunks of 16 KiB to 256 KiB (about 64 KiB), only files from 1 MiB to 128 GiB cut, the chunk list as a record type of its own (kind 18), `feature chunks` in `.opalro/format`. Decision 121 keeps *where* Opalro cuts out of the freeze; the limits freeze.
7. **No format change from the speed work** ([109](../decisions/109-the-speed-sessions-follow-ups-and-format-1s-three-open-rows.md)): three rows asking for one (a Git tag stored once, a chunk count bounded by file size, a tighter bound on a stored copy's size) were answered no.
8. **A list of 8,388,608 one-byte chunks takes about 82 s to write out an 8 MiB file** (milestone 5's known costs). It is valid format 1, so a planted project can do this forever after the freeze.

**`opalro.toml`'s keys** ([114](../decisions/114-bolt-toml-keys-and-how-bolt-reads-it.md)):

9. The key names are final: `preset`, `chunk-files-over`, `ask-before-saving-over`, `ask-before-saving-files-over`, `[[rule]]`. Sizes are text with a unit. A key Opalro can't use never stops a command: Opalro warns and uses its own value, so a typo shows only as a warning.

**Command names**:

10. No decision freezes them, but once testers learn them and write scripts, a rename means keeping the old name working too. Check the seventeen names in the guide's §4 now. Related calls: Git's words run only in the forms that mean the same, `opalro restore` is always explained and never run, and `opalro stash pop 2` uses Opalro's shelf numbers, not Git's ([116](../decisions/116-gits-words-as-shortcuts.md), [124](../decisions/124-restore-is-explained-and-a-shortcut-takes-nothing-for-what-it-isnt.md)). `opalro` alone prints the overview and exits with 2; 0 may be friendlier (milestone 6, item 22).

**The `--json` formats** ([117](../decisions/117-what-json-covers-at-v0.1.md), [json.md](../json.md)):

11. `opalro_json` 1 freezes: field names, types, meanings, each warning's `kind` and the exit codes. A field can be added later, never renamed or removed. Errors have no machine-readable code in v0.1; scripts go by the exit code. `verify` gained the problem kind `save_too_big` ([126](../decisions/126-verify-also-finds-a-save-that-cant-be-written-out.md)).
12. Change IDs are written in Jujutsu's letters ([122](../decisions/122-change-ids-in-jujutsus-letters.md)). Display only, but every `change_id` a script stores looks like this from now on.

**What freezes the moment you press "Publish release":**

**How to take a release back.** You can, partly.

7. **Put the files on your website:** the four archives and `SHA256SUMS` for people to download, the documents from `opalro-0.1.0-website.zip` as pages (part 6), and the download page with its checksums and the report address.
8. **Merge the prepared "v0.1 published" pull request.** It marks the format and the `--json` formats as frozen in the documents and records the release.
