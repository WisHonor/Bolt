Opalro v0.1 is the first release of Opalro, a version control system for code and large binary files together, with its own engine and storage format: it is not built on Git.

It is an early release, for one person on one computer. There is no server yet, so no sharing, merging or locking.

## What it does

- **Saves and history:** `start`, `save`, `status`, `changes`, `history`, `show`, `goto`, `discard`.
- **Lines and shelves:** `line` to try ideas on a line of their own; `shelf` and `unshelf` to put changes aside.
- **Undo for everything:** `opalro undo` takes back any command that changed something, and `opalro redo` brings it back.
- **Presets:** `opalro start` asks what kind of project it is (Game, Code or Custom); Game and Code write their rules into `opalro.toml` and `.opalroignore`, and `opalro setup` shows them and switches presets.
- **Big files:** cut into chunks, so a change to part of a file stores only the part that changed.
- **Coming from Git:** `opalro import` brings in a Git repository, Git LFS files included.
- **Looking after a project:** `tidy` and `verify`.

What Opalro writes on disk is described in the storage format, published on https://opalro.com, and frozen from this version: every later Opalro reads what v0.1 wrote.

**Speed:** measured against Git and Git LFS on GitHub's Linux and Windows machines, the losses included; the benchmarks are published on the same page. All the numbers here are from GitHub's runners. On Git's own source, Opalro's first save takes about a fifth of Git's time on Linux and a tenth to an eighth on Windows, and a small save is level with Git on Linux and quicker on Windows. Saving a 10 GiB file peaks at 44 MB of memory. Git or Git LFS came out ahead in these cases: `status` takes 1.4 to 2.2 times Git's time; going back to another version 1.8 to 2.7 times Git's on Linux; a switch that rewrites thousands of files 1.8 to 3.1 seconds against Git's 0.46 to 0.75 (3,557 files, Linux); the whole history listing 1.5 to 2 times Git's. On a slow disk Git LFS is quicker at the first save of big files that don't compress, and Git at going back to an old version of a big file. A long history takes more space than Git's (64.6 GB against 6.6 GB for Linux's history, 369 MB against 314 MB for Git's own), since Opalro doesn't store versions as differences yet, and importing Linux's history peaks at 3.4 GB of memory. The guide's section "Where Git and Git LFS still do better" lists every case with its numbers.

Opalro's own bar is to stay within twice Git's time. This version ships without meeting it for going back to another version (`goto`): Opalro's speed check holds it to three and a half times Git's time until v0.2, and twice is the goal for v0.2. `status` with nothing changed and a small save stay held to it: Opalro's speed check fails when either takes more than twice Git's time.

## Download

From https://opalro.com: one archive per system, `opalro-0.1.0-x86_64-pc-windows-msvc.zip` for Windows, and `.tar.gz` archives for Linux (`x86_64-unknown-linux-gnu`) and macOS (`aarch64-apple-darwin` for Apple silicon, `x86_64-apple-darwin` for Intel). Each holds six files: the program, `README.md`, the user guide (`docs/guide.md`), the user agreement (`USER-AGREEMENT.md`), and the notices for the code of other people built into Opalro (`THIRD-PARTY-LICENSES.html` and `THIRD-PARTY-LICENSES-RUST.html`).

What each system needs:

- **Windows:** Windows 10 or 11, or Windows Server 2016 or later, on a 64-bit Intel or AMD processor.
- **Linux:** a 64-bit Intel or AMD processor, and glibc 2.34 or newer (Ubuntu 22.04, Debian 12, Fedora 35, RHEL, AlmaLinux and Rocky Linux 9, and later).
- **macOS:** macOS 11 or later, on Apple silicon or Intel.

Nothing else needs to be installed.

`SHA256SUMS`, on the same page, lists a SHA-256 for each archive. The guide's section 2, "Installing", has the command that checks a download on each system. A match says the file arrived whole and is the one put on the page; it doesn't say who made it, since nothing is signed.

## Not signed

The programs aren't signed. On Windows, SmartScreen may say "Windows protected your PC" when Opalro is started from Explorer (choose "More info", then "Run anyway"); started from a terminal it usually says nothing. On macOS, a program unpacked by double-clicking the archive is blocked on its first run, even from Terminal (System Settings, Privacy & Security, "Open Anyway"); unpacked with `tar` in Terminal, it isn't. The guide's "Installing" section has the steps. Signing is planned.

## Closed source

Opalro is closed source: you may use it under the user agreement, `USER-AGREEMENT.md`, in every archive.

## Known limits

No server, no merging, no locking, no repair (`opalro verify` finds damage but can't fix it), and no export to Git yet. The guide's section "What v0.1 doesn't do yet" lists them all, and its section "Stopping" says how to remove Opalro, or leave a project, without losing files.

## Problems

Write to support@opalro.com. A security problem goes to the same address, privately, with "security" in the subject.

## For scripts

Every command can print `--json`. The formats are described in the `--json` reference, published on https://opalro.com, and frozen from this version (`opalro_json` 1).

These names changed while v0.1 was being made, before the formats were frozen; a script written against a build from before this release needs them:

| Document | Before | Now |
|---|---|---|
| `start` | `line` (always `"main"`) | `position` (`{"line": "main"}`) |
| `discard` | `restored` | `restored_paths` |
| `discard` | `removed` | `removed_paths` |
| `status` | `not_written_here` | `not_written` |
| `status` | `unfinished_switch`: text or `null` | `unfinished_switch`: `true` or `false` |
| warnings (any command that reads) | kind `damaged_pack` | kind `pack_damaged` |
| `history` | `line` (text or `null`) | `position` (`{"line": …}` or `{"save": …}`) |
| `line` | `current` (text or `null`) | `position` (`{"line": …}` or `{"save": …}`) |
| `changes`, each file | `lines` (`"text"`, `"binary"`, …) | `content` |
| `changes`, each file | value `too-big` | `too_big` |
| `changes`, each file | value `too-many-lines` | `too_many_lines` |
| `setup --preset` | `changes` | `files` |
| `setup` | `rules_file` | `has_rules_file` |
| `setup` | `ignore_lines` | `ignore_block_lines` |
| `save` | `result` value `nothing-changed` | `nothing_changed` |
| a change (`status`, `show`, `changes`) | `change` value `kind-changed` | `kind_changed` |
| a change (`status`, `show`, `changes`) | `kind` value `project-link` | `project_link` |
| `goto`, `discard`, `shelf`, `unshelf` | `files_in_use` (always `[]`) | the field is removed; the `files_in_use` warning stays |
| `goto` | none | `recorded` (`true` or `false`) added |
| every error document | `error.message` and `error.hint` as made | escaped as on screen: same names, but a message holding a control character reads differently |
| every save (`change_id`, `change_id_short`) | letters `k` for 0 to `z` for 15 | Jujutsu's letters, `z` for 0 to `k` for 15: the same bytes, written the other way round |
