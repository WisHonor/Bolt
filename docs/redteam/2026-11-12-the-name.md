Code attacked: a copy of the rename at a5f91f4, built in release mode (`cargo build --release -p opal-vcs`, the program `opalro`) in the no-network sandbox (Debian bookworm, Rust 1.99.1, git 2.39.5). Windows and macOS items are written as probes for GitHub's runners and were not run.

Run it with `cargo test --release -p opal-vcs --test redteam15 -- --ignored --test-threads=1`. In the sandbox, on the code attacked: `test result: FAILED. 0 passed; 1 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.09s` (the whole output is in `redteam/attacks14/proofs-output.txt`). Without `--ignored` the file passes (1 ignored). It is formatted with `rustfmt --edition 2024` and passes `cargo clippy -p opal-vcs --test redteam15 -- -D warnings` in the sandbox.
Platform probes: `crates/opal-vcs/tests/redteam15_platforms.rs` (Windows and macOS only, all three `#[ignore]`d, to be run on a `redteam/name-*` branch). Not run; it compiles away on Linux, and with its gates taken off it passes clippy in the sandbox (`redteam/attacks14/run.sh platforms`).
Attack code: `redteam/attacks14/`: `probe.py`, probes of the release program (old variables and settings folders, look-alikes in a working folder, the old format line and magic bytes planted in `.opalro`, another tool's `.opalro`, a pre-release build's folders and rule files, typed paths and patterns aimed at `.opalro`, a project's own identity, an import of Git commits tracking `.opalro` spellings); `rt15_alias.rs`, an exploration of `is_opal_alias` against the drives' rules, of the context strings, and of a record stored under its old-context ID. `run.sh probe <name>`, `run.sh explore rt15_alias` and `run.sh platforms` run them in the sandbox.

Counts: Critical 0, High 0, Medium 0, Low 1.

## Findings

- **RT15-1 Low (a spelling of `.opalro` shown as `.opalro`: the joiner in it printed as it is; T21, T2; `import.rs`, `tracked_stop` and the `nested_opal_folder` warning).**
  - **What.** The code's own rule is that a name standing for `.git` or `.opalro` is shown with every invisible character visible, so a spelling can be told from the real name: the save's `git_names_left_out` warning and the import's list of left-out entries both use `escape_all`. Two of the import's messages about the same spellings use `escape(…, false)`, which lets the zero-width joiner and non-joiner through (T21's exception for emoji and scripts). So a Git commit tracking `.o‌palro` (U+200C after the `o`) at the top stops the import with "Git tracks \`.opalro\` at the top of this project", as the terminal shows it, and one tracking `sub/.o‍palro` (U+200D) gets "Git checked out a folder named .opalro at \`sub/.opalro\`… delete it unless you made it", while the line above it, from the same import, shows `sub/.o\u{200d}palro`. Not made by the rename: `tracked_stop` and the warning printed `.b‌olt` the same way before; found while attacking the new name's spellings.
  - **Who is hit.** Someone importing a Git repository that tracks such a spelling: the message names an entry that reads as `.opalro` and isn't one, so they look for, rename or delete the wrong thing (`git rm -r --cached .opalro` matches nothing; deleting `sub/.opalro` deletes nothing, or a real one). No data is written or lost by Opalro; the import stops or leaves the entry out as designed.
  - **Proof (test).** `the_import_shows_the_joiner_in_a_tracked_opalro_spelling`: a commit tracking `.o\u{200c}palro/x`, then one tracking `sub/.o\u{200d}palro/x`, each imported:
    ```
    a joiner was printed as it is, so the name reads as .opalro:
    ".o\u{200c}palro/x": ["error: Git tracks `.o\u{200c}palro` at the top of this project, and Opalro can't use it as its own .opalro folder."]
    "sub/.o\u{200d}palro/x": ["warning: Git checked out a folder named .opalro at `sub/.o\u{200d}palro`. Opalro left it out of history, but commands run inside it would use it as an Opalro project; delete it unless you made it."]
    ```
    (The test's `{:?}` shows the joiners; the program printed the raw bytes E2 80 8C and E2 80 8D.)
  - **Suspected fix.** `escape_all` for the name in `tracked_stop`'s message (where it is formatted, since `ImportError::Stop` is printed with `escape` later) and for the path in the `nested_opal_folder` warning, as `walk.rs` and `import_output.rs` do. The warning could also say "a folder whose name stands for .opalro", since on Linux `sub/.o‍palro` is no project.

## Suspicions (no proof; never findings)

- **A short name of `.opalro` that only Linux reaches** (not made by the rename). Write-out compares a name with the real short names of `.git` and `.opalro` only on Windows, where folder listings give them. On Linux writing to an NTFS drive (WSL's `/mnt/c`, ntfs-3g, ntfs3) a hashed short name of `.opalro` (made when four names starting `OPALRO` came first) isn't compared; on a vfat drive mounted on Linux, the kernel's own generator tries `~1` to `~9` before hashing, so `.opalro` can be `OPALRO~5` to `OPALRO~9`, which `is_opal_alias` lets through (`opalro~5` is in its test of ordinary names). A Git repository can supply the four names, since Git checks them out before `opalro import` makes `.opalro`; a line of it naming `OPALRO~5/…` would then be written into `.opalro` by `goto` on Linux. The same held for `BOLT~5` and `BO…~1` before the rename; the rename only lets `.opalroignore`, which shares the six letters, take one of the four places. Not tried: the sandbox has no privileges to mount a drive. Git has the same gap for `.git` (it refuses `git~1` only).
- **The hashed short name of `.opalro` is knowable.** security.md says no hashed prefix is known for `.opalro`; Windows' checksum is a fixed function of the long name (Git hard-codes `gi7eba` for `.gitmodules` from it), so `.opalro`'s could be refused on every system, which would close most of the item above. `a_save_naming_the_hashed_short_names_of_opalro_and_its_ignore_file_writes_into_neither` prints the one NTFS gives.

## What held

- **The look-alike test against the drives' rules** (`rt15_alias.rs`): 441,650 names (every name of up to three of 34 pieces, among them `.`, the six letters in both cases, `~`, digits, space, `:`, `\`, `/`, U+200B, U+200C, U+202E, U+206F, U+2060, U+FEFF, U+0130, U+212A, U+FFFF, `$INDEX_ALLOCATION`, plus 400,000 spellings of `.opalro` and `opalro~1` to `~9` with letter case, ignorables, U+00AD and U+034F inserted and NTFS endings added) against a model of HFS+ (ignorables dropped, ASCII letter case; HFS+'s decomposition adds nothing, since its only singletons onto ASCII are U+212A, U+037E and U+1FEF) and of NTFS as Git models a six-letter name (`.opalro` or `opalro~1` to `~4`, then dots and spaces, then the end or a stream): 78,289 names a drive takes for `.opalro`, every one refused by `is_opal_alias`, `validate_name` and `writable_here`. The first-letter fast path (`.`, `o`, `O`, the lead bytes E2 and EF) misses none of them. `x\.opalro` is an ordinary name, as designed: write-out never writes a name holding `\` on Windows.
- **Look-alikes in a working folder** (`probe.py lookalikes_saved`): 15 spellings (`.OPALRO`, `.Opalro`, `.opalro.`, `.opalro `, `.opalro. .`, `opalro~1`, `OPALRO~4`, `opalro~1.`, `.o‌palro`, a byte order mark in front, U+206F and U+200D inside or after, `.opalro:x`, `.opalro::$INDEX_ALLOCATION`, U+202A in front), each at the top and in a folder below: all 30 left out of the save with `git_names_left_out`, names shown with `escape_all`.
- **Old variables and settings folders** (`probe.py settings`): with `BOLT_USER_NAME`, `BOLT_USER_EMAIL`, `OPAL_USER_NAME`, `OPAL_USER_EMAIL`, `BOLT_CONFIG_DIR`, `OPAL_CONFIG_DIR` (pointing at a `config.toml` naming Mallory) and `~/.config/bolt`, `~/.config/opal`, `~/.config/Bolt`, `~/.config/Opal` set up, `opalro start` still asks for a name and email and names `~/.config/opalro/config.toml`. The release program holds no `bolt` in any case, and of the `OPALRO_…` names only `OPALRO_CONFIG_DIR`, `OPALRO_USER_NAME`, `OPALRO_USER_EMAIL` and `OPALRO_ASCII`; the test hooks are compiled out.
- **A project's own identity** (`probe.py project_identity`): a `[user]` in `.opalro/config.toml`, `bolt.toml`, `opal.toml`, `.bolt/config.toml`, `.opal/config.toml` and `opalro.toml`, with only `OPALRO_USER_NAME` set: the save stops for want of an identity; with the user's own, the save is the user's and `ignored_project_identity` names Mallory; `opalro.toml`'s `user` key is passed over with `rules_ignored`.
- **The old format line and magic bytes** (`probe.py old_magic old_caches`): `.opalro/format` saying `bolt-repository 1` or `opalro-repository 1` is damage to every command, and `start` there says it is a project already. Packs with `BOLTPACK` and `BOLTPEND` are damaged packs to `status`, `history`, `save`, `tidy` (nothing removed) and `verify` (both named), never read. Caches with `BOLTFILE` and `BOLTCHID` are rebuilt (they start `OPALFILE` and `OPALCHID` again after a `save`). A `BOLTJRNL` journal stops `goto` and `save` ("can't be used") and is reported by `status`. No crash.
- **Context strings** (`rt15_alias.rs`): the eight flavours' strings are pairwise distinct, so the rename made no two kinds of record alike; content IDs carry no context. A folder listing stored under the ID a `bolt-vcs …` context gives it is refused on read ("does not match its fingerprint") and reported by `verify`.
- **Another tool's `.opalro`** (`probe.py foreign_opalro import_names`): holding `notes.txt`, `FORMAT` or `format.bak`, `start` and `import` refuse it and leave it as it was; holding only names Opalro puts there (`config.toml`, `state`) it is taken as a start that stopped, as decided. In other letter cases on Windows and macOS: `start_and_import_refuse_another_tools_folder_in_another_letter_case` (not run).
- **A pre-release build's folders and files** (`probe.py old_project_folders import_names`): `.bolt/`, `.opal/`, `sub/.bolt/`, `bolt.toml`, `opal.toml`, `.boltignore` and `.opalignore` are saved and imported as ordinary files (10 files in the save); `.boltignore`'s line keeps nothing out, and neither `bolt.toml` nor `opal.toml` is read.
- **Typed paths and patterns** (`probe.py typed_patterns`): `.opalr?`, `.opalr*`, `[.]opalro`, `*`, `.*`, `?opalro`, `*/head`, `**/head`, `.OPALR?`, `[.]OPALRO/x` with `discard`, `save` and `changes`: none reaches `.opalro` (unchanged after each) or the left-out `.OPALRO`; `.opalro/*` is refused as being in `.opalro`.
- **The import's stops** (`probe.py import_names`): a commit tracking `.OPALRO`, `opalro~2`, `.o‌palro` or `.opalro.` at the top stops the import (but see RT15-1 for how the third is shown); `sub/.opalro` is left out and warned about.
- **By reading** (each checked against the code, not run): every name check moved with the rename and none kept the old one: `own_folder`, `listed_hints` (the walk's hints, short names included), `holds_own_repository`, `kept_unasked`, `presets::look`, `project_path`, `holds_only_opals_own`, `tracked_opal` and `subfolders`, and `writable_here`'s real-short-name comparison (`own_short_names`); no `bolt` is left in the code, the workflows or the scripts outside the records decision 150 keeps; every test the workflows name with `--exact` exists; the environment variables the workflows, bench and test helpers set are the ones the code reads; the storage spec's context strings, magics and gear numbers match the code and the vectors. `.opalro` and `.opalroignore` sharing `OPALRO~1` to `~4` lets neither stand for the other in a save, an import or a write-out: all four plain short names are refused in every case, and a hashed one of `.opalro` is compared on Windows. A short name of `.opalroignore` that a planted save names is the probe `a_save_naming_the_hashed_short_names_of_opalro_and_its_ignore_file_writes_into_neither` (not run).
