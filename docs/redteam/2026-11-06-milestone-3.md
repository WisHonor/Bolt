# Red-team report: milestone 3 (decision 024, 2026-11-06)

Code attacked: this copy of `milestone-3` at 5a8e0aa ("Write milestone 3's attack surface for its red-team session").
Proof tests: `crates/bolt-vcs/tests/redteam5.rs`. 4 tests, each marked `#[ignore = "RT5-n: …"]` and each asserting the SAFE behaviour. All four were run in the no-network sandbox and fail as claimed. `rt5_4` is Unix-only (hard links and mode bits). The other three run everywhere. No Windows-only or macOS-only attack was found worth a gated test, so nothing waits on the Windows runners.
Run them: `cargo test -p bolt-vcs --test redteam5 -- --ignored`. In the sandbox, on the code attacked, it ended `test result: FAILED. 0 passed; 4 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.47s`. Without `--ignored` the file passes (4 ignored). The file is formatted with `rustfmt --edition 2024`.

Counts: Critical 0, High 1, Medium 2, Low 1.

The write-out held against what the attack surface aimed it at: names, links, crashes, a FIFO or link among the packs, and paths that leave the project (see "Held up"). The findings come from two places. Three are the cache and the plan deciding what may be overwritten from what they believe is on disk: a cache that matches by path, size and time, and a plan that never looks inside a folder it is about to replace. The fourth is a name rule that lets a line pose as a save's change ID.

## Findings

- **RT5-1 High (unsaved work: the file-state cache vouches for a file it has never seen; T9 in spirit, a new case of "a cache must only ever be a hint").**
  - **What.** `FileCache::matches` trusts a path whose kind, size and modified time are the ones recorded. Nothing ties the entry to the file itself. A different file renamed onto the path keeps its own time (`rename` doesn't touch it), so if it has the same size and the same time, the cache vouches for content that isn't there.
    - `status` and `save` show and save nothing.
    - `goto` and `discard` take the cache's word for what is on disk. The plan's `expected` comes from `read_folder` (cached). `keep_safety_copies` then sees "the save already holds this" and keeps no copy. `Run::look` asks the cache again right before it overwrites. The file is replaced and its bytes are gone.
    - Same-time files are common: npm sets every file in a package to 1985-10-26 08:15 UTC, many zip and reproducible-build tools give a whole tree one time, and FAT (2 s) and HFS+ (1 s) give one time to everything written in the same tick. No time is set back after Bolt looked (decision 011's known limit doesn't cover this). The user only runs `mv`.
  - **Who is hit.** Anyone whose files share a time (unpacked archives, packages, FAT/exFAT drives) and who moves one file onto another of the same size, then runs `goto` or `discard`. No attacker is needed. A hostile archive can arrange the sizes and times on purpose.
  - **Proof (test).** `rt5_1_a_file_renamed_over_a_saved_one_is_seen_and_never_lost`: `a.txt` ("AAAA") is saved with the archive time, and the user's new `notes.txt` ("KKKK") has the same time. The user runs `mv notes.txt a.txt`, then `goto` to the earlier save:
    ```
    saved: []
    before the rename: ["\"added\" \"notes.txt\""]
    after it: []
    goto: Some(0)
    the notes (KKKK) survived the goto: false
    ```
    `status` lists nothing after the rename. The goto exits 0, keeps no safety copy, and "KKKK" is neither on disk nor in the store.
  - **Fix.** Record the drive's file ID in each cache entry and require it to match (`EntryMeta` already carries `file_id`, which `look` uses), plus the change time where the platform gives one. This is decision 053's option A, as a second check on top of the seal. Separately, anything about to be overwritten or removed without a safety copy should be hashed, not taken from the cache: the cache may speed up `status`, but it should never decide what is destroyed. Needs a decision superseding part of 053.

- **RT5-2 Medium (wrong state after `goto`; T21-adjacent: a misleading message).**
  - **What.** The plan collects collisions only for entries new to the folder (`new_here` in `writeout::plan`). Where the target holds a file and the folder holds a folder, the action carries `expected: Folder` and isn't checked. An ignored file inside that folder (a build output) is invisible to the plan. `apply` then removes the saved files inside the folder, fails to remove the folder (`DirectoryNotEmpty`), records it as `Changed`, and says "1 entry changed while Bolt was switching". Nothing changed during the switch.
    - The goto exits 0 and moves `head`. The folder is now on neither save: the old file `d/f` is gone and the target's file `d` was never written.
    - `status` then shows `d` as removed. A `save` there records that removal in the user's name.
    - With an unsaved or new (unignored) file in the same place, the goto is correctly refused before it changes anything ("Your unsaved changes are in the way"), so only ignored files slip through.
  - **Who is hit.** Anyone with build outputs in a folder that another line turns into a file or link.
  - **Proof (test).** `rt5_2_an_ignored_file_in_a_folder_becoming_a_file_is_in_the_way`:
    ```
    goto: Some(0)
    warning: 1 entry changed while Bolt was switching, so it left them as they are:
      d
    You're on line main.

    folder now: [(".gitignore", "*.o\n"), ("d", "<dir>"), ("d/x.o", "build")]
    status: [{"change":"removed","kind":"file","new_size":null,"old_size":6,"path":"d"}]
    ```
  - **Fix.** In `plan`, for an action that puts a file or link where the folder holds a folder, look at the folder on disk (as `in_the_way` does for new entries). If it holds anything the plan doesn't remove, make it a collision so the goto is refused before anything changes, as it already is for unignored files. Also give `DirectoryNotEmpty` while clearing a folder its own wording, not "changed while switching".

- **RT5-3 Medium (T21: terminal trickery through a line name).**
  - **What.** `resolve_target` (and `history::resolve`) try a line name first, then a change-ID start, then a fingerprint start (decision 055). Line names may be any letters and digits, so a line can be named exactly like the short change ID `history` prints for another save. `bolt goto <that ID>` then goes to the line's save, without saying the text was also a change ID.
    - An imported save's change ID is fixed by its commit (decision 032: the Jujutsu rule, or the commit's own `change-id` header), so a repository's author knows in advance what `history` will show, and names a branch to match.
    - The only sign is "You're on line pkql." instead of a save being named.
  - **Who is hit.** Anyone who imports a repository from someone else and goes to a save by the change ID `history` shows. That is exactly what the output invites, for example to check out a fix.
  - **Proof (test).** `rt5_3_goto_by_the_change_id_history_shows_reaches_that_save`:
    ```
    history shows: kmyn  just now  Ada Lovelace  Fix the security bug
    bolt goto kmyn: You're on line kmyn.
    app.txt now holds: "attacker's version\n"
    ```
  - **Fix.** Treat a text that is both a line name and the start of a save's change ID or fingerprint as ambiguous: refuse it and list both, as `show` does for an ambiguous start. Alternatively, refuse such names for new lines (`save --line`) and rename them on import by decision 033's rule, listing the renaming. Either needs a decision refining 055. A line name made only of the letters k to z, or of 8 or more hex digits, is the case to catch.

- **RT5-4 Low (T3: a change outside the project, through a hard link).**
  - **What.** When only the executable bit differs, `Run::put` calls `set_executable` on the file in place. A hard link shares that mode with every other name of the file, so a goto changes a file outside the project. Content changes are safe, since they are written in `.bolt/tmp` and renamed over the link. Git deletes and rewrites the file for a mode change.
  - **Who is hit.** A user who hard-links one copy of a script or config into a project, where a save flips its executable bit. A hostile save can do that flip on purpose, but it still needs the user's link.
  - **Proof (test).** `rt5_4_goto_never_changes_a_file_outside_through_a_hard_link`:
    ```
    assertion `left == right` failed: the file outside the project is now 755; goto: Some(0)
      left: 493
     right: 420
    ```
  - **Fix.** Write the file anew through `.bolt/tmp` and a rename for a mode-only change too, as for a content change, or do so whenever the file has more than one link.

## Not proven

Suspicions without a failing test. None counts as a finding.

- **A folder of the project on another drive.** Files are written in `.bolt/tmp` and renamed into place. If a project folder is a mount point (another drive, a bind mount), the rename fails with `EXDEV`. The switch then stops with its journal kept, and every changing command after it fails the same way, until the user moves the folder. The sandbox drops every capability, so a mount couldn't be made to show it.
- **Look-alike line names.** `is_line_name_char` takes any Unicode letter, so a hostile import can add `mаin` (Cyrillic а) beside `main`. `bolt line` lists both, and `escape` keeps letters. This is the same family as RT5-3 but not tested.
- **One seal for all of a user's projects.** The cache key belongs to the user, not to a project, so a cache sealed in one of the user's projects is trusted in another. That only matters together with RT5-1's same-size, same-time coincidence, and RT5-1's fix covers it.
- **Read-only commands write in `.bolt/tmp` without the lock.** `status` writes there twice: the drive-clock file (`drive_now`) and the cache it then writes. Another Bolt that opens the repository while no lock is held clears `tmp/`, so a concurrent `status` may fail or lose its cache write. That looks harmless, but it wasn't tested.
- **A misleading count.** After an abort right after the last write, the next command says "Finished a switch … wrote 0 files and removed 0 entries" (seen in the abort sweep below). It is cosmetic.

## Held up

These were tried in the sandbox unless marked as code reading, and Bolt behaved correctly:

- **A FIFO in the project folder.** `status`, `status --full`, `changes`, `save`, `discard` and `goto` all finished in under 0.2 s.
- **A pack that is a FIFO, a link to `/dev/zero`, or a link to `/`.** Reads pass over it. `save` refuses with "it is not a regular file". Nothing hangs.
- **Paths given on the command line.** `save`, `changes` and `discard` were tried with `out/secret` through a link to a folder outside, the link itself, `../`, an absolute path outside, `.bolt` and `.bolt/state/head`. Each was refused or touched nothing, and the outside file stayed.
- **Partial saves.** A deleted file named alone, a folder turned into a file, `d/*.txt` with a deletion and a deeper file, a file turned into a folder, and a path below what is now a file. Each saved exactly what was named, or refused before saving. `discard` takes no patterns, and says so.
- **Nested projects.** A folder holding a `.git` folder, a `.git` file or a `.bolt` folder is left alone by `discard`. On Linux, `.GIT` is an ordinary name, as Git has it there.
- **A folder replaced by a file in `goto`.** With an unsaved or new file below it, the goto is refused before anything changes. RT5-2 is the ignored-file gap.
- **A process abort at every fault point (`BOLT_FAULT_AT`, `--features fault-injection`).** The sweep covered `goto` (11 stops, then success) and `discard` (9 stops, then success). After each stop, `status` ran and the next `save` finished the switch. The folder ended wholly on one save, and the discarded bytes were kept, either on disk or as safety copies. This adds real aborts to the error-return sweeps in `writeout/tests.rs` and `switch/tests.rs`.
- **The journal (code reading).** It is checked against its checksum, its paths must be in order, unique and valid, a removal must say what it removes, and names are checked again in `apply`. A planted journal can write nothing a planted save couldn't, and every action checks `expected` against the disk.
- **The version 2 index (code reading).** Count against length, a fan-out that never decreases and ends at the count, IDs sorted inside their fan-out range, and every entry inside the entry area. The merge keeps a damaged pack and reads it again at each merge, which decision 062 bounds and states.
- **Output escaping (code reading and earlier tests).** `escape` covers control, bidi and invisible characters in names and lines. `changes` reads at most 64 MiB plus one byte per file, whatever the listing says.

## Session 2 (2026-11-06): the fixes

Code attacked: this copy at 63846a6 (the four fixes). New proofs: `rt5_5` and `rt5_6` in `crates/bolt-vcs/tests/redteam5.rs`, ignored. In the sandbox `cargo test -p bolt-vcs --test redteam5` passes (4 passed, 1 ignored: RT5-1 to RT5-4 now hold), and with `--ignored` `rt5_5` fails as shown below. `rt5_6` is gated to Windows and macOS and is **unverified**: it waits for the Windows runners on `redteam/m3`.

### Per fix

- **RT5-1 (file ID in the cache): bypassed (RT5-5).** A rename, a hard link (`ln -f`) and a copy to a new name all give another file ID and now miss, as decision 067 intends. But a file overwritten *in place* keeps its ID: `cp -p`, `unzip -o`, `tar --overwrite` and `rsync --inplace -t` truncate the existing file, write the new bytes and set the source's time. Same ID, same size, same (shared) time: the cache vouches for it. This is not decision 067's known limit (a file deleted and made again in a freed inode) nor FAT slot reuse; it needs no coincidence beyond the one RT5-1 already relied on. Also read: the file ID comes from `fstatat` on Unix and `FileIdInfo` on Windows, both per entry, and a 0 file number is never trusted.
- **RT5-2 (a folder that goes holds what the plan never read): held on Linux, one regression on drives that ignore case (RT5-6, unverified).** Tried by reading and against the code: an ignored file deep in a nested folder (the walk descends through removed folders only, and lists everything else), an ignored folder, a nested `.git`/`.bolt`, a link standing in for a saved folder (never descended), a non-UTF-8 name (counted as left), and a folder the target only removes (it stays without the false warning). On a drive that ignores case, `take_over_renamed` gives a new file `D` the expectation of the removed folder `d`, so `D` joins the folders that go; `left_below` then builds `D/f`, which the `removed` set (exact strings, `d/f`) doesn't hold, so the folder's own saved files are "in the way" and the goto is refused with nothing unsaved or ignored.
- **RT5-3 (a line name that is also another save's ID): held.** `goto`, `show` and `changes --save` all go through `line_named`; `switch` only re-reads the line under the lock. `history` lists first parents of the current line, the same walk `by_change_prefix` searches, so every change ID `history` shows is checked. Uppercase hex is lowered for fingerprints; uppercase letters never name a change ID; a `@` name is a server line, never a line or ID. The line's own save matching is correctly not refused.
- **RT5-4 (mode-only change rewritten through `.bolt/tmp`): held.** By reading: `set_executable` is no longer called by the write-out, so a mode-only change goes through the same tmp-and-rename as a content change, for `goto` and `discard` alike (both use `Run::put`). `rt5_4` passes.

### New findings

- **RT5-5 High (unsaved work lost; T25, a way around RT5-1's fix).**
  - **What.** `FileCache::matches` trusts kind, size, modified time and file ID. A file overwritten in place keeps its file ID, and copy and unpack tools set the source's time on it. With the shared times RT5-1 described (npm, archives, FAT), the cache vouches for content that isn't there, and `goto`/`discard` replace it without a safety copy.
  - **Who is hit.** Anyone who runs `cp -p`, `unzip -o` or `tar --overwrite` of a file with the same size and time over a saved one, then `goto` or `discard`. A hostile archive can arrange it.
  - **Proof (test).** `rt5_5_a_file_copied_over_a_saved_one_keeping_its_time_is_seen_and_never_lost`:
    ```
    status after the copy: []
    goto: Some(0)
    the notes (KKKK) survived the goto: false
    test result: FAILED. 0 passed; 1 failed; 0 ignored; 0 measured; 4 filtered out
    ```
  - **Fix.** Decision 067's option B now, not later: record and match the change time (`st_ctime` on Unix, which `utimensat` and every write bump and no user call can set back; `ChangeTime` from `FILE_BASIC_INFO` on Windows). It also closes the inode-reuse limit. Option C (hash anything about to be overwritten without a safety copy) stays the stronger backstop. Needs a decision superseding part of 067.

- **RT5-6 Low, unverified (Windows, macOS: a needless refusal; regression from RT5-2's fix).**
  - **What.** A save turns folder `d` (holding `d/f`) into file `D`. On a drive that ignores case, `goto` there is refused, listing `D/f` as "unsaved changes, or files Bolt ignores", though nothing is unsaved or ignored. The user can't reach the save without deleting `d` by hand.
  - **Proof (test).** `rt5_6_a_folder_becoming_a_file_in_another_case_is_not_in_its_own_way`, `#[cfg(any(windows, target_os = "macos"))]`, not run here.
  - **Fix.** In `left_below`, compare as the drive compares names: build `removed` from `fold_path` and look up `fold_path(below)`, or skip a folder that goes only through `take_over_renamed`'s expectation and walk the removed spelling.

### Not proven

- **Racing a build during `goto`.** A file appearing in a folder that goes between `plan` and `apply` still ends in "changed while switching" with the folder on neither save. That message is then true, so it isn't a finding.
- **The hint after a refused `discard`.** The collision hint says "then run bolt goto again" for `discard` too. Cosmetic.
- **Unicode-composing drives (macOS HFS+).** `left_below` joins on-disk names (NFD) to plan paths (NFC) with exact strings, like RT5-6's case gap; not tested.
