# Red-team report: the final builds (RT16, decision 024, 2026-11-12)

Code attacked: a copy of `v0.1-final` at 1eaa3b1, as briefed, built in release mode (`cargo build --release -p opal-vcs`, the program `opalro`) in the no-network sandbox (Debian bookworm, Rust 1.99.1, git 2.39.5, zstd 1.5.7 through `zstd-sys` 2.1.2). While the session ran, the branch moved to c8eedd0: its 69b72d0, "the code review's fixes", checks each zstd block against its frame's limit on both read paths and refuses a content size of all ones. Every proof and exploration was run on both, 1eaa3b1 and c8eedd0, and each finding says which it holds for. By the session's end the branch was at ba1699e: its 848f7a3, the second review, rewrites §11's sentence on which entries v0.1 reads in one call (RT16-5) and adds a test; it changes no code the proofs reach.
Proof tests: `redteam/attacks15/redteam16.rs`, 6 tests, each marked `#[ignore = "RT16-n: …; until its fix is in"]` and asserting the SAFE behaviour. `redteam/attacks15/run.sh proofs` copies the file into `crates/opal-vcs/tests/` and runs `cargo test -j 2 --release -p opal-vcs --test redteam16 -- --ignored --test-threads=2`. On 1eaa3b1: `test result: FAILED. 0 passed; 6 failed`. On c8eedd0: `test result: FAILED. 2 passed; 4 failed` (69b72d0 fixes RT16-1's raw and RLE blocks and RT16-2). The whole output is in `redteam/attacks15/proofs-output.txt`. Without `--ignored` the file passes (6 ignored). It is formatted with `rustfmt --edition 2024` and passes `cargo clippy -p opal-vcs --test redteam16 -- -D warnings` in the sandbox.
Platform probe: `redteam/attacks15/redteam16_platforms.rs`, for suspicions S1 and S2: on macOS it makes and mounts a FAT32 image with `hdiutil`; elsewhere it uses a FAT folder named in `RT16_FAT_DIR`. Not run (no macOS, and no mounts in the sandbox); it compiles and passes clippy here (`run.sh platforms`).
Attack code: `redteam/attacks15/`: `rt16_explore.rs`, hostile frames through both read paths, as content and as a folder listing, plus a memory probe (`run.sh explore`); `rt16_cli.rs`, planted frames through `save`, `verify`, `discard` and `tidy` (`run.sh cli`); `rt16_names.rs`, the name rule against the spec's words and Git's form, and `names.sh`, the new spellings through a save and an import (`run.sh names`). Their output on both trees is in `explore-output.txt`.

Counts: Critical 0, High 0, Medium 3, Low 2. RT16-1 and RT16-2 were found by the code review too and are fixed on the tip by 69b72d0 (except ruling 10's case, which RT16-4 is about); RT16-5 is fixed in the spec by 848f7a3; RT16-3 and RT16-4 are open at ba1699e.

## Findings

- **RT16-1 Medium (a frame format 1 refuses, read in a small entry and refused in a large one: raw and RLE blocks over the block limit; decision 154, T8, T9; `pack.rs`, `read_small`). Fixed on the tip by 69b72d0, except a compressed block (ruling 10).**
  - **What.** RFC 8878 limits every block to Block_Maximum_Size, the window or 128 KiB if that is smaller, and "this maximum is applicable to both the decompressed size and the compressed size of any block in the frame" (§3.1.1.2.4). zstd 1.5.7's streamed decoder checks it (`zstd_decompress.c`, lines 1315 and 1367); its one-call decoder doesn't, for a raw or an RLE block (lines 1022 and 1025). At 1eaa3b1 `read_small` checked only the header and the frame's length before the one call. So an RLE block of 200 KiB, raw blocks of 200 KiB, or blocks of 2 KiB in a 1 KiB window were read in a small entry (a record stored in at most 1 MiB, a file recorded and stored in at most 1 MiB), and the same frames in a larger entry were refused ("Data corruption detected"). Decision 154 says small and large entries refuse the same bytes with the same words. Of 19 hostile frames tried on both paths at 1eaa3b1, 9 were read by the one-call path only.
  - **Who is hit.** Someone whose `.opalro` holds a pack another person or program wrote (a shared or synced folder). The save takes the planted frame as the file's copy and stores none of its own, `opalro verify` says "no problems found", `discard` writes the file from it, and `tidy` copies it as it is into a pack Opalro writes, ahead of the person's own copy (RT16-4). A reader that keeps to the frozen spec refuses it; so does v0.1's own streamed path, for a larger entry.
  - **Proof (test).** `rt16_1_a_small_file_whose_rle_block_is_over_its_limit_is_damaged`: a 200 KiB file whose only copy is one RLE block of 200 KiB (window 2^21, content size given). On 1eaa3b1:
    ```
    an RLE block of 200 KiB: format 1 refuses this frame, yet the save took it as the file's copy and `opalro verify` passed it (Some(0)):
    Verified .tmpW10EIj: no problems found.
    ```
    On c8eedd0 it passes: the save warns that the planted pack is damaged ("a block holds more than its frame allows"), stores its own copy, and `verify` names the planted one. `run.sh cli` shows, on 1eaa3b1, the 200 KiB file's planted frame used and passed while a 1.2 MiB file with the same kind of frame is refused and reported.
  - **What the fix leaves.** 69b72d0 walks every block header on both paths before zstd sees it. A header can't show a compressed block that unpacks past the limit, and the code review ruled that a reader may read one (ruling 10, now in §11). `rt16_1_a_small_file_whose_last_block_decodes_past_its_limit_is_damaged` (a 64 KiB window, one compressed block stored in 7.5 KiB that unpacks to 70 KiB) fails on both trees: by the spec as briefed that is damage; under ruling 10 it isn't, and the test goes if the owner confirms that ruling. RT16-4 is what ruling 10 costs that it doesn't say; RT16-5 was its first wording.

- **RT16-2 Low (a content size of all ones read as none; decision 154; `pack.rs`). Fixed on the tip by 69b72d0 (ruling 11).**
  - **What.** An 8-byte Frame_Content_Size of 2^64 − 1. RFC 8878 gives no value of the field a meaning of its own (its table's "unknown" is a field of 0 bytes, §3.1.1.1.4), so the frame says it holds 2^64 − 1 bytes, which isn't the entry's size. zstd's API reports that one value as "unknown", and at 1eaa3b1 both paths read the frame as giving no size: a 1,000-byte file and a 1.2 MiB one were read.
  - **Who is hit.** Nobody's data in v0.1, where both paths agree. A program written from the spec refuses what v0.1 verifies and copies on.
  - **Proof (test).** `rt16_2_a_content_size_of_all_ones_is_damage`: on 1eaa3b1, "a content size of 2^64 - 1: format 1 refuses this frame, yet the save took it as the file's copy and `opalro verify` passed it (Some(0))"; passes on c8eedd0 ("the zstd frame of … has the wrong size").

- **RT16-3 Medium (matches that reach past the window are read, on both paths; decision 154, T8, T9; `pack.rs`, zstd). Open at ba1699e.**
  - **What.** A match may reach back "up to a distance of Window_Size, or the beginning of the Frame, whichever is smaller" (RFC 8878 §3.1.1.3; zstd's own format document: "all offsets leading to previously decoded data must be smaller than Window_Size"). A frame with a match further back isn't an RFC 8878 frame, and §11, even as amended, calls it damage: its one exception is a compressed block that unpacks past the block limit. Neither decoder checks it. The streamed one keeps the window plus two blocks and 64 bytes of history and reads any match within that; the one-call one reads any match back to the frame's start. With zstd's own frames, their window byte lowered to 128 KiB: matches 200 KiB back are read by both paths, in a 400 KiB file and in a 1.4 MiB file; 450 KiB back, in a 900 KiB file, the one-call path reads and the streamed one refuses; 700 KiB back, in 1.4 MiB stored in 700 KiB, refused as a file (streamed) and read as a folder listing (one call). 69b72d0's block walk can't see a match; that takes decoding the sequences.
  - **Who is hit.** As RT16-1: the save takes such a planted copy as the file's only copy, `verify` passes it, and `tidy` keeps it over the person's own (RT16-4). A reader that keeps to the window, as the spec says, refuses it.
  - **Proof (test).** `rt16_3_matches_past_the_window_are_damage`: a 900 KiB file (450 KiB of noise, twice), its frame from Opalro's own compressor (`pack::prepare`) with the header rewritten to give a 128 KiB window. Fails on both trees:
    ```
    matches 450 KiB back, window 128 KiB: format 1 refuses this frame, yet the save took it as the file's copy and `opalro verify` passed it (Some(0)):
    Verified .tmpovFnbX: no problems found.
    ```
  - **Suspected fix.** As ruling 10 did for a compressed block: a decoder of Opalro's own, or the spec saying what a reader may do and what v0.1 does (with RT16-4 in view, since a frame "a reader may refuse" can become someone's only copy).

- **RT16-4 Medium (`tidy` and merging keep a planted copy over the person's own, then remove theirs; T9, T27; `merge::copy_packs`). Open at ba1699e.**
  - **What.** When two packs hold one object, merging and `tidy` (both through `merge::copy_packs`) copy the first copy they meet, taking the packs in order of name, after checking it as a read does; the other copy is left out as already held, and its pack is removed. For a small object that check is the one-call decoder, which reads frames the streamed decoder refuses: RT16-1's at 1eaa3b1, ruling 10's compressed block and RT16-3's far matches on the tip. So a planted pack whose name sorts first (`00.pack`) turns a frame "a reader may refuse" into the only copy of the person's file, in a pack Opalro wrote, and the person's good copy is deleted. Ruling 10 weighs reading such a block as harmless; it doesn't say that a reader which refuses it, as the spec lets any reader do and as v0.1's streamed path does, then has no copy left.
  - **Who is hit.** Anyone whose `.opalro` someone else can add a pack to. v0.1 still reads the file; the loss comes with the first reader that refuses the frame: a later Opalro with another decoder or another threshold for the one-call read, or a program written from the spec.
  - **Proof (test).** `rt16_4_tidy_keeps_the_persons_own_copy_over_a_planted_one`: save a 70 KiB file; plant `00.pack` holding ruling 10's frame for it (a 64 KiB window, one compressed block that unpacks to 70 KiB); make every pack two days old; `opalro tidy`. Fails on both trees:
    ```
    after tidy, the file's only copy is the planted frame (1 copies); verify says:
    Verified .tmp4vhCcv: no problems found.
    ```
    On 1eaa3b1 RT16-1's RLE frame does the same (`run.sh cli`, `rt16_cli_tidy_keeps_which`: "after tidy: …pack: 14 B, planted frame: true", the person's 26-byte copy gone).
  - **Suspected fix.** Check what merging and `tidy` copy with the streamed decoder, which refuses all three kinds above, or prefer the copy that passes it; or close RT16-3 and ruling 10's case so that no such frame is read at all.

- **RT16-5 Low (the amended spec said v0.1 reads ruling 10's block in any entry stored in at most 1 MiB; for a file it doesn't; storage-format.md §11, `pack.rs` `copy_content`). Open at c8eedd0; fixed in the spec by 848f7a3.**
  - **What.** 69b72d0's §11: "A reader may read such a block or refuse it: v0.1 reads it in an entry stored in at most 1 MiB, and refuses it in a larger one." `read_record` takes the one-call path by stored size, but `copy_content` and `read_content` take it only for a file recorded at most 1 MiB, however small its stored bytes. So one frame stored in 7,800 bytes (16 RLE blocks of 64 KiB, then ruling 10's 70 KiB block) is read as a folder listing and refused as a file. The sentence freezes with format 1.
  - **Who is hit.** No one's data in v0.1. A program that does what the spec says reads files v0.1 refuses, so the two disagree on what is damage.
  - **Proof (test).** `rt16_5_the_same_frame_is_read_as_a_listing_and_refused_as_a_file` (pack level, the same stored bytes under both kinds). Fails on both trees:
    ```
    one frame (7800 B stored), two answers:
      as a listing: Ok(1120256)
      as a file: Err("pack …pack is damaged: the zstd data of f60255ff1691… is invalid: Data corruption detected")
    ```
  - **Fix.** 848f7a3, the second review, which landed during the session, writes what v0.1 does: it reads such a block "when it reads the entry in one call (stored in at most 1 MiB and, for a file's contents, at most 1 MiB unpacked too), and refuses it otherwise". The proof then shows behaviour the spec allows, and goes if that wording stays.

## Suspicions (no proof; never findings)

- **S1. macOS's FAT driver may give `.opalro` the short name `OPALR~1` at the first try, which `is_opal_alias` lets through.** Read from Apple's source, not run. In `msdosfs_apply_generation_to_short_name` (`msdosfs_conv.c`, apple-oss-distributions/msdosfs) the tilde's place for a one-digit number is index 6; while the byte there is a space the index steps left, and the tilde is then written over the byte it stops on. `.opalro`'s base is the six letters `OPALRO` (the leading dot dropped, `msdosfs_unicode_to_dos_name`), so index 6 is a space, the index stops on the last `O`, and generation 1 gives `OPALR~1`; `msdosfs_uniqdosname` reuses the buffer, so 2 to 5 give `OPALR~~2` to `OPALR~~5`, then `OPALR~NN` from 6 plus the directory offset. On macOS write-out compares no real short names, and a save may hold `opalr~1` (the save probe keeps it), so a line naming `opalr~1/…`, checked out by `goto` onto a FAT drive on a Mac, could reach into `.opalro` (T2): if the probe confirms it, it is of the kind RT-1 and RT-2 were. The code review's ruling 8 deferred "plain short names past `~9`" as needing nine names taken first; on a Mac this would need none. The probe `every_short_name_a_fat_drive_gives_opalro_is_refused` makes `.opalro` after 0, 1, 4, 5, 9 and 12 names with the same base, finds every short name that opens it (the plain, Apple's, sequential tails to four digits, the hashed one and Linux's random ones), and fails on any that `is_opal_alias` lets through.
- **S2. Linux's vfat driver doesn't go on to `OPALR~10` after `OPALRO~9`,** as ruling 8 has it: it takes `OP`, four hex digits of the clock, `~` and a digit 1 to 8 (`vfat_create_shortname`, `fs/fat/namei_vfat.c`). No fixed name covers that; refusing `op` + four hex digits + `~` + one digit would (524,288 names, the shape the hashed rule already has). `OPALR~10` is FreeBSD's sequence, a system Opalro doesn't support. The same probe runs on a vfat folder named in `RT16_FAT_DIR`.
- **S3. On Windows a planted record whose frame makes one byte more than it records may commit up to three times the record for a moment** (1.5 GiB for 512 MiB): the streamed path writes into a buffer reserved for the record, which doubles to take the one byte before the refusal. On Linux only the address space grows, since glibc moves the block with `mremap`: a 256 MiB record that is one byte over is refused in 319 ms with peak RSS up 258 MiB (an honest one: 255 MiB, 214 ms), and the address space peaks at 595 MiB (an honest one: 339 MiB). Not measured on Windows; within the 512 MiB record bound.

## What held

- **Good frames** (`run.sh explore`): every one read by both paths, as a file and as a folder listing, on both trees: Opalro's two writer paths (one call, streamed) at 0, 1, 1,000, 1,048,576 and 1,048,577 bytes; a window of exactly 2^27 with and without a content size; content-size fields of 8 and 2 bytes; and on the tip a single segment of 232 bytes with one RLE block of 232, one RLE block of exactly 128 KiB, and 1.1 MiB of raw blocks with a block header across the streamed decoder's 131,075-byte read. 17 good frames in all, none refused.
- **Hostile frames:** 19 on 1eaa3b1 and 28 on the tip, each read four ways (`read_small`, `decode_into`, `copy_content`, `read_record`), plus the 6 proofs' frames through the program. On 1eaa3b1: 9 read by the one-call path only (RT16-1, RT16-3), 4 read wherever they went (RT16-2 at 1,000 bytes and at 1.2 MiB, RT16-3 at 200 KiB, and raw blocks of 64 KiB in a 1 KiB window, which zstd's streamed decoder read in one go), 6 refused by both. On the tip: 5 read by the one-call path only (ruling 10's three compressed blocks, RT16-3's two), 2 read by both (RT16-3), 21 refused by both, each small one with the words its large twin got: "a block holds more than its frame allows" (raw and RLE blocks of 200 KiB, 300 KiB, 64 KiB in a 1 KiB window, 2 KiB in a 1 KiB window, 128 KiB + 1), "has the wrong size" (all ones; a single segment of 200 holding 232), "not a frame format 1 allows" (2^64 − 2, zstd's error value), and compressed blocks of 128 KiB under a 64 KiB window ("Data corruption detected").
- **No other zstd reader** (by reading): every kind goes through the two paths tried here, records through `read_record` and files and chunks through `copy_content` or `read_content`; `copy_stored` copies bytes only after one of those checked them; a chunk list stored with compression 1 is refused outright ("is compressed"); and the only other use of zstd outside tests is `compress_bound` in `ingest.rs`.
- **Reads stay inside the stored bytes:** the header check reads at most 18 bytes and never past the entry; the block walk wraps the entry's own reader, which stops at its end; the trailing check reads only from it.
- **Cost** (`rt16_cost`, Linux): a 2 MiB file with a 2^27 window and no content size, read streamed: peak RSS up 4 MiB, as with Opalro's own 2^21 window (address space up 64 MiB); every frame of the explorations, good or hostile, was read or refused in under 3 ms.
- **The build:** `zstd-sys` is built with only its `std` feature in every workspace member (`cargo tree -e features -i zstd-sys`); the release program keeps its symbols (12,464) and none is `ZSTDv0…` or `ZSTD_isLegacy`. A pre-1.0 frame through the program is refused by the magic check before zstd sees it, so behaviour alone can't show the decoders are gone; the symbols do.
- **The name rule** (`rt16_names.rs`): 3,596,496 names (every name of up to four of 32 pieces, among them `.`, the letters of `opalro` and `op9975` in both cases, `~`, digits, space, `:`, `\`, U+200B, U+200C, U+206F, U+FEFF, `$INDEX_ALLOCATION`; the `~` forms on 16 starts, with counters of up to seven digits (each one to 2,000 and every 997th after, plain and padded with zeros) and 11 endings; nine invisible characters put in each place of five short names) against storage-format.md §3 word for word, and against Git's `is_ntfs_dot_generic` ported with `op9975` and `~1` to `~9`: 110,011 refused, 0 differences, and `validate_name` and `writable_here` agree with `is_opal_alias` on every one. Ordinary names pass: `~$document.docx`, `~$Budget.xlsx`, `~WRL0001.tmp`, `.~lock.report.odt#`, `~lock.file#`, `~1234567.txt`, `~12345678`, `op9975~10`, `opalro~10`. Refused by design, as the shape `git fsck` refuses: eight-character names such as `~1234567`, `o~123456`, `op~12345`.
- **Through the program** (`names.sh`): of 15 names, each at the top and in `sub/`, a save left out the 18 spellings (`opalro~5`, `OPALRO~9.`, `op9975~1`, `OP997~12 `, `o~123456`, `~1234567`, `op9975~1:x`, and two with an invisible character inside) with `git_names_left_out`, and kept the other 12 files. An import of a commit tracking `opalro~5`, `op9975~1`, `~1234567` or `o~123456` at the top stops; below the top they are left out and listed. Every other path reads names through a folder listing, whose decoding refuses them (`validate_name`); the code review added the new spellings to the save corpus and the hand-made journal (read, not re-run).

## Not done

- S1 and S2's probe: it needs macOS, or a FAT drive mounted on Linux (`RT16_FAT_DIR`), on a `redteam/*` branch.
- No legacy frame was decoded through the program (see "The build"); no legacy encoder in the sandbox.
- The repository's own suites weren't run.
- Merging with more than 32 small packs wasn't run on its own: it copies through `merge::copy_packs`, as `tidy` does. RT16-4's other order (the person's pack sorting first) wasn't run either.
- Windows and macOS: nothing run.

## After the session

The rulings are in [the final builds' rulings](../plans/2026-11-12-v0.1-final-rulings.md), 16 to 23.

- **RT16-1:** fixed by the block check on both read paths (69b72d0). Its proof runs on every push, in `crates/opal-vcs/tests/redteam16.rs`. Its compressed-block case is ruled on (ruling 10), and that proof is switched off.
- **RT16-2:** fixed (69b72d0). Its proof runs on every push.
- **RT16-3:** ruled on, not fixed (ruling 18). §11 now says that two rules of RFC 8878 show only inside the blocks, that a reader may read a frame breaking either or refuse it, and that v0.1 reads it wherever zstd does.
- **RT16-4:** ruled on, not fixed in v0.1 (ruling 19). Checking or storing again what comes from others is in the follow-ups, before networking.
- **RT16-5:** fixed in the spec (848f7a3). Its proof is kept, switched off.
- **S1:** the probe ran on macOS 15, on the branch `redteam/final-probes`, which was deleted afterwards (runs 43322841277 and 43326314609). A second probe tried more forms. The Mac's FAT driver opened no long-named entry by a short form: not `.opalro` by `OPALR~1`, `OPALRO~1` or `OPALRO`, and not `longfilename.txt` by `LONGFI~1.TXT`. So the hole isn't there (ruling 21).
- **S2 and S3:** no change (rulings 22 and 23).
