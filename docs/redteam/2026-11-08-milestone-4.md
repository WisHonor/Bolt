# Red-team report: milestone 4 (decision 024, 2026-11-08)

Code attacked: a copy of `milestone-4` at 1690a72 ("Write milestone 4's attack surface for its red-team session").
Proof tests: `crates/bolt-vcs/tests/redteam6.rs`. 4 tests, each marked `#[ignore = "RT6-n: …"]` and each asserting the SAFE behaviour. All four were run in the no-network sandbox and fail as claimed. `rt6_3` needs the `fault-injection` feature, and `rt6_4` is Linux-only (it reads the process's peak memory from `/proc`). The other two run everywhere. No Windows-only attack was found worth a gated test, so nothing waits on the Windows runners.
Run them: `cargo test -p bolt-vcs --features fault-injection --test redteam6 -- --ignored`. In the sandbox, on the code attacked, it ended `test result: FAILED. 0 passed; 4 failed; 0 ignored; 0 measured; 0 filtered out; finished in 16.64s`. Without `--ignored` the file passes (4 ignored, or 3 without the feature). The file is formatted with `rustfmt --edition 2024`.

Counts: Critical 0, High 0, Medium 2, Low 2.

Undo, redo, shelves, amend and the crash recovery held against nearly everything the attack surface named (see "Held up"). The findings come from the edges: `tidy` trusting an older `head` it can read, a switch's check of a file coming long before it replaces it, a lost `head` picked up while a switch is stopped, and a journal read whole into memory by every command.

## Findings

- **RT6-1 Medium (saved history deleted for good; T27 and T28).**
  - **What.** When `state/head` names an older entry that still reads, Bolt trusts it (decision 075 says so). `tidy` then keeps only what that older entry's diary reaches. Every entry made after it, and every save only those entries name, counts as garbage. Packs written more than 24 hours earlier are removed, so those saves are gone for good.
    - Before `tidy`, nothing tells the user. `history` and `undo --list` simply stop at the older entry, and `status` shows the newer work as unsaved changes.
    - After `tidy`, putting the newer `head` back gives "the store doesn't hold" that entry, with the hint "Your saves are safe", which is now false.
  - **Who is hit.** Anyone whose `state/head` is rolled back while the packs are not. Decision 075 names the causes itself: a sync tool (OneDrive, Dropbox and iCloud roll single files back when they settle a conflict), or a restore of `.bolt/state` from a backup. `tidy`'s own help says it frees "saves no line, shelf or tag reaches", so the user has no reason to fear running it.
  - **Proof (test).** `rt6_1_tidy_never_deletes_saves_made_after_an_older_head`: saves "One", "Monday" and "Tuesday"; the folder then moves on; `state/head` is put back to the entry after "One"; the packs are two days old; `tidy`:
    ```
    status before tidy:
    On line main.
      modified  a.txt  (4 B → 19 B)
    tidy: Some(0)
    Freed 4.7 KB (4 packs removed, 1 written).
    Monday's save still readable: false; Tuesday's: false
    ```
  - **Fix.** Before judging, `tidy` should list the diary entries that no other entry follows (`diary_ends`, as for a lost `head`). If one is newer than `head` and not on its diary, it should stop and say so, or keep that entry's diary and its states as if they were in the window. A crash's leftover entry is an end too, so the cheap rule is to keep every end inside the window together with its diary. Needs a decision refining 077.

- **RT6-2 Medium (unsaved work lost; the follow-ups' row 70, wider than known).**
  - **What.** When a switch replaces a file, `Run::put` first looks at it (`look`: its kind, size and hash, against what the plan expected). Then it writes the new contents to a file in `.bolt/tmp`, and only then renames that file over the old one. Nothing is checked between the look and the rename. For a big file the gap is the whole time it takes to write the new contents: about a second for 64 MiB in the sandbox, and far longer for the multi-gigabyte files Bolt is built for. Whatever another program saves into the file during that time is replaced, with no safety copy. Row 70 records only the last instant before a new file is made. This is an existing, tracked file, and the gap is long. `undo`, `redo`, `unshelf`, `goto`, `discard` and `shelf` all write through `put`.
  - **Who is hit.** Anyone whose editor or tool saves a big file while an `undo`, `redo`, `unshelf` or `goto` that changes it is running. An art tool's autosave, or a save made just as the command started, is enough.
  - **Proof (test).** `rt6_2_a_file_saved_while_undo_writes_over_it_is_never_lost`: `art.psd` (64 MiB) has two saved versions. The test runs `goto` to the first, then `undo`. As soon as the undo's file in `.bolt/tmp` passes 1 MiB, the "art program" saves new contents over `art.psd`:
    ```
    undo: Some(0)
    Undid goto: back on main at movz, 1 file written.
    the work saved during the undo survived: false
    ```
    The undo exits 0 and says nothing, and the art program's bytes are neither on disk nor in the store. It failed three runs out of three.
  - **Fix.** Look at the file again right before the rename: its file ID, size and change time must be the ones `look` saw. If they differ, the file is `Changed`: leave it, and leave its new contents in `.bolt/tmp` or remove them. That shrinks the gap to the instant row 70 already accepts. A no-replace rename in the platform crate, or for an existing file a rename of the old one aside first (kept as a safety copy until the switch is done), would close it entirely.

- **RT6-3 Low (a recovery that strands the project; T28).**
  - **What.** A switch (`discard`, `goto`, `undo`…) stores its diary entry, writes its journal and starts changing files. If it is stopped there and `state/head` is then lost, `undo --list` offers exactly one end: the stopped switch's own entry, since the entry before it has a child. `undo --to` picks it up by adding a new entry after it. The journal, though, still says it was made from the old `head` (`journal.from`), and `move_head` only removes a journal whose target is the old head. So the next changing command finds a journal "made for another save than the one the project is on", and every changing command refuses, `undo` and `discard` included.
    - The hint says to delete `.bolt/state/journal`, after which the folder stays half switched. The discarded work can then come back only through `undo` twice with `--shelve`, and nothing says so.
    - `undo --to` itself says "No file was changed", while the switch it picked up had changed some.
  - **Who is hit.** A user whose computer stops during a switch (power cut, crash) and whose `state/head` is then lost, the very case decision 075's pick-up is for.
  - **Proof (test).** `rt6_3_picking_up_a_lost_head_after_a_stopped_switch_lets_the_project_go_on` (fault-injection): a `discard` is stopped at `switch:changed`, then `state/head` is removed, then the user runs `undo --list` and `undo --to <the only end>`, then `discard` and `undo`:
    ```
    undo --to 6948c256…: Made entry 6948c2562cbc (discard) the current one: on main at vnos "One". No file was changed: …
    discard: Some(1) error: A switch between saves was stopped here, and Bolt can't finish it: .bolt/state/journal was made for another save than the one the project is on.
    hint: … To go on without finishing the switch, delete .bolt/state/journal: …
    undo: Some(1) error: (the same)
    ```
  - **Fix.** When `undo --to` picks up a lost `head` and a journal is there: if the pick is the journal's target, finish the switch as the next command would (its `from` is the pick's parent), then add the pick-up entry. Otherwise, say that a stopped switch is there and offer its `from` entry too. At the least, `undo --list` should list the journal's `from` and `target` with the ends, and say which one finishes the switch.

- **RT6-4 Low (memory exhaustion from a planted journal; T26, the follow-ups' row 69, wider than known).**
  - **What.** `Journal::read` reads `state/journal` whole, up to `MAX_BYTES` (4 GiB), before checking anything. Row 69 says changing commands read and hash it. In fact `unfinished_warning` reads it too, so every read-only command does: `status`, `history`, `undo --list`. A sparse file costs nothing on disk and is made in an instant (`truncate -s 4294967295`). Each command then allocates and fills about 4 GiB. In the 4 GB sandbox `bolt status` is killed by the kernel's out-of-memory killer. Under a lower address-space limit it fails more gently, but every command still says "out of memory". With 3 GB, `status` takes 7 s and 3 GB each time.
  - **Who is hit.** Anyone who opens a project folder someone else prepared: a zip, a shared drive, a USB stick, a synced folder. It needs no more than T26's hostile diaries already assume.
  - **Proof (test).** `rt6_4_a_huge_journal_costs_status_little_time_and_memory` (Linux): a sparse journal of 4 GiB less one byte, then `bolt status` under `run_limited`:
    ```
    bolt status: Ended { code: None, timed_out: false, secs: 7.540651935, peak_mb: 4051, stderr: "" }
    ```
    `code: None` means it was killed (the out-of-memory killer).
  - **Fix.** Read the journal's header first, and refuse one whose length doesn't match its action count and checksum area before reading the rest. Or stream it: decode and hash it as it is read, from a buffer, so that a bad one is refused after its first bytes. Cap what a read-only command reads: `unfinished_warning` only needs the target and `from` IDs at the front.

## Not proven

These are suspicions without a failing test. None counts as a finding.

- **A future time is "just now".** `relative_time` shows any time ahead of the clock as "just now", and `undo --list` with a lost `head` puts the newest time first. An entry made while the clock was ahead, or a planted one, is offered first as where the diary stopped. Only someone who can write `.bolt` can plant one, and they could just as well rewrite `head`.
- **A clock set back, then corrected.** The window is judged by each entry's own time and the 24-hour grace by each pack's own time, both from the same clock. Work done while the clock was days behind (a dead clock battery, before the network fixes it) counts as old: `tidy` can drop a `discard`'s kept work although it is the newest step. Not tested: the sandbox can't set the clock.
- **Many shelves cost a lot of store.** Every diary entry holds the whole shelf list, about 40 bytes a shelf, so at the 10,000-shelf limit each command adds about 400 KB, and making those shelves writes about 2 GB of entries. Bounded, and no user gets there by accident.
- **Two shelves holding one save.** `restore_shelves` compares shelves by save, so in a planted state where two labels name one save, undoing an `unshelf` of one of them never brings it back. Bolt never makes such a state itself.
- **Counts in step lines.** "Undid goto: …, 1 file written." when the step also removed a file to make a folder (`d` to `d/x`); the redo of the same step says "1 file written, 1 removed". Cosmetic.
- **Redo stricter than goto.** A redo that removes a folder holding an ignored file and a new file of the user's is refused, naming the folder; `goto` leaves such a folder. Safe, only inconsistent.

## Held up

Each of these was tried in the sandbox unless marked as code reading, and Bolt behaved correctly:

- **Undo, redo and `undo --to` as writers.** Tried: discard, shelf and goto undone and redone, with unsaved work, deletions and edits back to the old bytes in the way. Also files and folders swapping places at one path (`d` and `d/x`) through `goto`, `discard`, `discard d/x`, `shelf` and `unshelf` onto another save. A new file in a folder a step made, ignored files where an undo writes (`*.log`, `build/`, `*.o`), and links inside the project in place of saved files and folders. Each either wrote exactly the step's paths or was refused with nothing changed. A file deleted after a step is "in the way" of undoing it: conservative, not lost.
- **`--shelve`.** Tried with an executable bit, a link, a new file deep in a new folder, a folder turned into a file, and on `undo`, `redo` and an `undo --to` jump. The shelf held exactly the work in the way, and undoing the step brought it back.
- **Placeholders (links leading out).** A placeholder made executable, a file of the user's holding the same bytes, a placeholder edited into notes. The edited one is "in the way"; the others are the link, and only their mode is lost, never bytes.
- **Amend.** Refused on an imported line with a tag; the save it replaced can't be reached by `goto` (by fingerprint or change ID), so no line can be made on it. After `undo` of an amend, the change ID reaches the save the line holds.
- **A lost `head`.** Missing, uppercase, CRLF, empty, 100 MB of zeros, a folder (told as damage), naming a save. Each stops every command with the right message. `undo --list` and `undo --to` work, and `undo --to` refuses text that isn't 8 hex digits.
- **Crashes at every abort point** (`BOLT_FAULT_AT`, a sweep in `redteam/attacks5/crash_sweeps.rs`). Covered: `undo --to <entry> --shelve` (10 stops), `redo --shelve`, `tidy` with old packs (19 stops, `tidy:removing` included), `unshelf` onto another save, and `discard d/x` where `d` became a file. After each stop, `status` ran, then the command again, `undo` and `redo`. The unsaved work was always on disk or in the store.
- **`tidy`'s marking (code reading, and the sweep above).** The window's states, the parent's state of the oldest entry in the window, undo and redo targets, folder changes, shelves, and the parents of kept saves are all kept. A pack whose copy reads otherwise is left. Content is kept by fingerprint without being read, and damage then stops the rewrite of that pack.
- **Terminal output.** Escape sequences, a carriage return and a bidi override in save, shelf and amend messages and in file names were escaped in `undo --list`, `--all`, the step lines and `shelf --list`. Closed, full and gone stdout and stderr for `undo`, `redo`, `unshelf`, `undo --list --all`, `shelf --list`, `tidy`, `save --amend` and `--json undo`: no panic. A failing stdout exits 1 and says the work was done.
- **Git's ignore files.** `.git/info/exclude` as a FIFO, a link to `/dev/zero` or a folder, `.git` as a file or a link, and `.gitignore` as a FIFO: each was skipped with a warning, with no hang. `.boltignore` as a FIFO is refused.
- **Long messages.** A 130,000-byte shelf message and save message are stored and listed.
- **Windows read-only fallback (code reading).** `set_read_only` opens by name, but every open adds `FILE_OPEN_REPARSE_POINT`, so it never follows a link out.
