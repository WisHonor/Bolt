Counts: Critical 0, High 0, Medium 1, Low 2.

What held: nothing a command says depended on who won the race between the walk and the helper that reads listings ahead. Over 1,050 random projects run through this build and main's side by side (random trees, `.gitignore` and `.boltignore` files of tricky lines, edits, links, files turned folders, nested repositories, partial saves, amends, shelves, undo and redo), every command's exit code, output and warnings, and the folder's files after every command, were the same. No change was missed, no wrong tree or wrong bytes reached the store or the folder, and no repository was swallowed. The findings are costs the speed work added where it now does work main did differently (memory in RT12-1, reads in RT12-2), and one answer taken from a cache without the store's word (RT12-3).

## Findings

- **RT12-1 Medium (a resource bound broken by a hostile or very branchy project; T11, decision 105).**
  - **What.** `save --amend` asks every other line whether it reaches the save being amended (the T29 check, `shown_elsewhere`). With `cache/change-ids` version 2, each line it asks gets its own complete list of saves back to the first: a line whose list the cache doesn't hold copies the tail of another line's list (`ChangeIds::chain`), so lines that share a history each hold a copy of it, 48 bytes a save, before overheads. `store` then encodes every list into one body and seals it into a second copy before the 256 MiB cap is checked; past the cap nothing is written, so the next amend does it all again. An imported Git repository with 10,000 branches over a 1,000-commit history makes every amend take 1.4 GB (main's took 0.47 GB). Under the 1.5 GB address-space cap the suite's `bolt_capped` uses, it aborts with `memory allocation of 479668050 bytes failed` and no message of Bolt's own. Memory grows with lines times history: by extrapolation (not run), about 30,000 such branches pass the sandbox's 4 GB, where main would stay near 1.4 GB.
  - **Who is hit.** Anyone who imports a Git repository with many branches over a long history and then amends: a hostile repository (a project may have 100,000 lines), or a large organisation's repository with thousands of branches. Under the 1.5 GB cap the abort comes in the cache's second `store`, after the commit: the amend is made, and the command dies with exit code 134, `memory allocation of … bytes failed` and nothing of Bolt's, so the person is told it failed when it didn't (`amend_after_abort.sh`, below). With less memory still it dies in the first `store`, before the walk, and nothing is made. Nothing is lost either way. Main paid in time instead (128 s for the first amend at 10 million line-save pairs, 2.7 s once its 160 MB cache was written); this build takes 3 to 4 s every time, when it has the memory.
  - **Proof (test).** `rt12_1_an_amend_among_many_lines_stays_within_memory`: a Git history of 1,000 commits with 10,000 branches at the commit before `main`'s newest, imported, a file changed, then `bolt save --amend m` under `bolt_capped`:
    ```
    assertion `left == right` failed: memory allocation of 479668050 bytes failed
      left: None
     right: Some(0)
    ```
    `redteam/attacks11/amend_lines.py 1000 10000` puts the two builds side by side:
    ```
    new capped 1.5 GB amend {'secs': 9.8, 'exit': -6, 'peak_mb': 1380, 'said': 'memory allocation of 479668050 bytes failed | …'}
    new free amend {'secs': 4.0, 'exit': 0, 'peak_mb': 1384, 'said': 'Amended wkxr  "m"  (1 file)'}
    new free amend again {'secs': 3.0, 'exit': 0, 'peak_mb': 1384, …}          change-ids bytes None
    main capped 1.5 GB amend {'secs': 128.3, 'exit': 0, 'peak_mb': 474, 'said': 'Amended wkxr  "m"  (1 file)'}
    main capped 1.5 GB amend again {'secs': 2.7, 'exit': 0, 'peak_mb': 470, …}   change-ids bytes 160276082
    ```
    At 2,000 branches over 300 commits the peaks were 132 MB against 41 MB. `amend_after_abort.sh`, the same project, then `history` and `status` after the abort:
    ```
    memory allocation of 479658050 bytes failed
    exit 134
    history before: wkxr  2023-11-14  a  c
    history after:  wkxr  2023-11-14  a  m
    On line main.
    Nothing changed since wkxr.
    ```
  - **Fix idea.** Don't make a list per line to answer "does this line reach that change ID": keep a line as its own saves plus where it joins another list, or walk the joined list in place without copying it. Work out the encoded size from the lists before encoding and skip the write past the cap, and encode with `try_reserve`, so a cache too big to keep is never built and keeping it can never fail a command after its commit.

- **RT12-2 Low (a project built to be slow: a new read path slower than the old one; T11, T32; the store's block window in `pack.rs`, which no decision records).**
  - **What.** Every small read of a pack (up to 4 KiB) is answered from the last 64 KiB block read of its entries, or of its index, and a read outside that block reads a whole new block. That pays off when records sit side by side; when they don't, each small read costs 64 KiB. Writing out a file whose small chunks are stored out of file order in one pack costs about three blocks a chunk: the index's IDs, the index's line, then the entry. For 8-byte chunks that is about 200 KB read for each chunk where main read under 500 bytes, and twice main's time: 100,000 chunks took 4.2 to 5.1 s against main's 2.3 to 2.5 s, and 400,000 took 23.2 to 23.5 s against 10.4 to 11.9 s; spread over 20 packs in turn, 12.2 s against 9.6 s. Decision 109 says a list of distinct tiny chunks "still costs a read for each"; each such read now costs 64 to 200 KiB, and the longest list a chunk list may hold (8,388,608 chunks) would read on the order of 1.7 TB from the page cache.
  - **Who is hit.** Bolt's own cutter makes chunks of at least 16 KiB, stored in file order, so it takes a planted `.bolt` to get here: a hostile project makes `goto`, `discard` and `undo` of one file about twice as slow as on main. Honest work gained: saving 100,000 new files over a 200,000-object pack took 3.7 to 4.2 s against main's 7.0 to 8.7 s, and chunks of 3,000 bytes wrote out faster than on main (`big_pack_lookups.py`, `rt12_chunk_thrash.rs`).
  - **Proof (test).** `rt12_2_a_scattered_small_read_costs_a_small_read`: 20,000 distinct 8-byte chunks stored in one pack in scrambled order, a save of the file they make, `bolt discard`, and the bytes the process read (`rchar`, which the shell that waited for it counts):
    ```
    read 3856038106 bytes to write 160000 bytes: 192801 a chunk
    ```
    `rt12_chunk_reads.rs`, both builds:
    ```
    100000 chunks shuffled true: new 5.07 s, read 19924 MB (199240 B a chunk)
    100000 chunks shuffled true: main 2.50 s, read 36 MB (363 B a chunk)
    400000 chunks shuffled true: new 23.50 s, read 87747 MB (219368 B a chunk)
    400000 chunks shuffled true: main 11.94 s, read 170 MB (426 B a chunk)
    ```
  - **Fix idea.** Read a block only when reads show locality (the last small read fell in the same block or just before it) and read just the bytes asked for otherwise; or keep smaller blocks (4 to 8 KiB), or a few of them.

- **RT12-3 Low (a misleading message from a cache that lies under a good seal; T32, decision 105).**
  - **What.** `goto` (and every command that finds a save) given all 64 digits of an ID takes it as a save the line reaches as soon as the line's list in `cache/change-ids` holds it (`by_fingerprint_prefix` returns on `ChangeIds::reaches`), without asking the store whether it is one. A list that starts at the line's newest save, as a good list does, but holds a folder listing's ID makes `goto` of that ID fail with `object … is FolderListing, not Save` (`is Content, not Save` for a file's content, `is not in the store` for nothing). Main says `No save, line or ID matches "…"` with its hint. The save that is read is still checked, as decision 105 promises, so no wrong save is gone to; and an ID of a real save no line reaches would be gone to where main refuses it, though only when typed in full.
  - **Who is hit.** It takes a list sealed with the user's own key, so a program running as the user, or a damaged cache rebuilt by hand; then the user gets an error about the store's objects where there is only a wrong ID. The same trust is what decision 105 accepts for short IDs; this is the one answer where the list alone decides whether an ID is a save at all.
  - **Proof (test).** `rt12_3_goto_of_a_full_id_no_save_has_says_no_save_matches`: two saves, then a list for `main` with the top folder's listing ID put second, sealed with the test user's key, then `bolt goto <that ID>`:
    ```
    Some(1): error: object 840bcf88a30c6168f4ec852cb9e555fe683789b486b40aa1309a8c1cb2dc8c63 is FolderListing, not Save
    ```
    `rt12_changeids.rs` runs the same lie with a file's content ID and with an ID of nothing, on both builds; `history` and `undo --list` read past the stranger correctly on both.
  - **Fix idea.** Before answering from the list, check that the ID's copy in the store is a save (the index line's kind, no read of the record), and fall back to the lines' walk when it isn't; or check the list's links from the line's newest save down to the ID, as `by_change_prefix` does.

## Not proven

Everything here was attacked and held, or only measured. The code for each is in `redteam/attacks11/`.

- **Listings read ahead, against damaged copies.** `rt12_ahead_damaged.rs`: a pack planted with a good copy of the listing read just before and a damaged copy of the next (a changed byte, a changed header, the pack cut short, or undamaged), six pack names each so the planted pack sorts first in some and last in others; `status`, `changes`, `history`, `save` and `status` again, 30 runs of each read-only command on this build and one on main's: all identical (688 s).
- **Listings read ahead, against planted saves.** `rt12_ahead_planted.rs`: folders naming a file's content, a save, or nothing (on disk and gone from it), three folders sharing one listing, a `.GIT` folder in a subfolder's listing, 3,000 saved folders gone from disk so the helper fills its buffer: 25 runs each, identical to main, errors included.
- **Everything a user sees, differentially.** `diff_fuzz.py` (400 projects), `diff_fuzz2.py` (350: partial saves, `--amend`, `shelf`, `unshelf`, `undo`, `redo`, links, files turned folders, nested `.git`/`.bolt` spellings, folders removed; the working folder compared after every command) and `diff_fuzz3.py` (300: ignore lines with NULs, overlapping ends around one star, classes, escapes, trailing spaces, non-ASCII): every exit code, output, warning and folder agreed with main. This covers the hash index of plain lines, `Ends` for one-star lines, the late ignore verdict and its two warnings, and folders that take the last save's listing ID, on a case-sensitive drive.
- **Packs that aren't packs.** `odd_packs.sh`: a pipe, a folder, a link to `/dev/zero`, an empty file and another project's pack, named to sort first and last: `status`, `changes` and `save` said what main says, no hang. The unreadable-pack case didn't reach Bolt (the copy for each build couldn't copy a mode-000 pack), so it is untested here.
- **Open files on the deepest chain.** `deep_fds.py`: 2,000 levels with a file in each, 21 packs, `status` and `save` under `ulimit -n 256`: at most 150 files open (main 141), and faster than main (0.4 s and 1.2 s against 1.2 s and 2.1 s).
- **Kept chunks and chunks spread over packs.** `rt12_chunk_thrash.rs`: 100,000 8-byte chunks over 20 packs in turn and in runs, and 20,000 3,000-byte chunks: write-out correct everywhere; the tiny ones slower than main (RT12-2), the 3,000-byte ones faster (1.5 s against 3.4 s). One-byte chunks can only be 256 distinct values, so a list of them is now mostly repeats and cheap; distinct tiny chunks are the slow list.
- **Lookups in a big pack.** `big_pack_lookups.py`: no regression for honest work (above). Its first version forgot to save first and so timed `status` over 300,000 never-saved files: 23.9 to 28.0 s against main's 22.9 to 25.5 s, a difference within this machine's noise that RT13 could measure again.
- **A lying change-ID list.** `rt12_changeids.rs`: a stranger in `main`'s list (a listing, content, nothing): `history` and `undo --list` read past it to the true line on both builds; `goto` of its full ID is RT12-3. Lists that skip a save, hold the right saves with wrong change IDs, or belong to an older tip were not planted end to end; reading `chain`, `links_hold`, `for_each_on_line` and `by_change_prefix` found them checked.
- **Projects built to be slow.** `slow_projects.py 5`, `status` twice, `save`, `status` again, this build against main's: 150,000 files in one folder (10.2, 1.27, 2.26, 0.91 s against 14.5, 2.4, 3.7, 1.4 s); 15,000 folders whose every name is outside ASCII, so every folder is asked for all four names (1.55, 1.85, 1.76 s after the first status, against 1.49, 2.06, 1.69: the same within noise); a `.gitignore` of 100,000 one-star lines that all fail (5.4, 5.0, 0.23 s against 27.3, 26.1, 18.3 s); 100,000 copies of `a.txt/`, one hash bucket a file named `a.txt` must walk to its end (0.76, 0.71, 0.21 s against 1.8, 1.6, 2.0 s); 100,000 `!` lines (no difference). Ignore files are capped at 1 MiB, so "a million one-star lines" can't be built; the first run of the script, past the cap, was refused by both builds alike.
- **Packs merged and removed under a reader.** `concurrent_tidy.sh`: a writer saving and tidying (merges and removals) while `status` and `changes` run 84 times: the only failures were "changed while Bolt was reading it" from the writer's own edits, on both builds; no store error, no warning about packs. Main also warned 6 times that it couldn't keep the file cache (its temporary file cleared under it); this build, writing the cache only when it changed, didn't.
- **Read only (no exploit found).** `listing_after` and `last_is` spare only what `first_copy` and the read would give for the same pack name; `peek_listing` notes nothing. `old_ids` holds a stored ID only for a listing nothing was dropped from, and a partial save never changes those listings; `Listing::decode` accepts only the canonical encoding, so a reused stored ID is the ID the listing would get. Version 2 `find` reads its short range only inside a fan-out range that was checked to rise and end at the count. `read_small` gives way to the streamed path for anything off, and `one_plain_frame`'s window formula is zstd's. The rewritten `is_bolt_alias` and `is_git_alias` answer as main's did for every case I could build. `listed_hints` folds ASCII case and treats a non-ASCII name as all four. `EarlyFlush` keeps the helper's failed flush (which a `dup`'d handle would otherwise swallow) and `finish` returns it before `sync_all`, the rename and `head`. `FileCache::store` skips its write only when every slot was kept and none turns racy or was added; the hint compares path bytes, so it can't answer from another slot. Change-ID lists only ever grow by a save on its true first parent.
- **The file cache, planted.** Not exercised beyond reading: on Linux every entry holds the change time and the drive's file number, so an older cache put back, a time set back by hand, or a same-size edit fails to match. The 2-second rule still looks at the modified time only, as on main (a file edited twice within one tick of the change-time clock with its modified time put back each time would be missed), which isn't new.
- **A folder swapped for another folder mid-walk.** `rt12_mid_walk.rs`: at `walk:looking`, `sub` renamed away and a new `sub` made with the same names and sizes, while the cache vouches for two of its three files and not the third: `status` and `save` both refused with `sub/b.txt changed while Bolt was reading it.`, no mix of the two folders.
- **Not reached (for RT13).** The other act-point races in the walk (`walk:sending`; a file swapped between look and read at a kept level of a deep chain; `.git` made after a folder was listed; an ignore file changed mid-walk); crash sweeps (`BOLT_FAULT_AT`) through a 40 MiB save and a `goto` writing it, and `fault::early_flush` beyond the existing `early_flush.rs`; a pack replaced or removed while a command runs; the memory of `status`, `goto` and `changes` on the widest folders the limits allow; 10,000 small packs; a line of a million saves with the cache removed; `ulimit -v` runs of the read-ahead with the largest listings; a short ID that fits two saves through a list that hides one (known limit).

## Held up

No finding needs another system. What wasn't run, and what would run it:

- **Windows:** `listed_hints` with NTFS short names, `.git` and `.bolt` spellings with trailing dots or spaces or a stream, a folder's `.gitignore` only its short name shows; and RT12-1's and RT12-2's tests compile away there. A Windows runner on a `redteam/*` branch.
- **macOS:** the 256-file default with the deepest chain (held here under `ulimit -n 256`), and composed and decomposed names on APFS against listing reuse. A macOS runner.
- **Drives that fold case:** case-only renames against a folder taking the last save's listing ID, on ext4 `casefold`, vfat, NTFS or APFS. Needs a mount the sandbox can't make (no privileges) or the runners above.
- **Power loss:** whether an unflushed `cache/files`, `cache/change-ids`, `state/lock-info` or the drive test's rename, or an early flush, can leave a torn file that is trusted. A stopped process can't show it; it needs a VM with `dm-log-writes` or a similar replay.
