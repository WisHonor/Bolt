# Red-team report: milestone 2, `bolt import` (decision 024, 2026-11-03)

Proof tests: `crates/bolt-vcs/tests/redteam3.rs`. 11 tests, all run in the no-network sandbox, all fail as claimed. Five are Linux-only (`#[cfg(target_os = "linux")]`): four measure peak memory through `/proc`, and RT3-5's `.GIT` needs a case-sensitive drive. The other six run everywhere; `rt3_5b` is the one written for the controller to run on Windows and macOS too (it uses only names those systems can hold). No Windows-only or macOS-only attack was found worth a gated test. Each test asserts the SAFE behaviour.
Scripts: `redteam/attacks3/`, each with its captured output in a `.txt` beside it. `gitrepo.py` is a small byte-exact Git writer (the sandbox has no `git`); the others build one hostile repository each. Every command below runs in the sandbox (`bash redteam/sandbox.sh run …`, working dir `/work` = this copy). Timings and peaks come from `/tmp/t/release/bolt` (`cargo build --release -p bolt-vcs`) measured with `redteam/attacks2/measure.py`; the sandbox's 4 GB limit stands in for "the machine ran out of memory".
Run all tests: `RUST_TEST_THREADS=1 cargo test -p bolt-vcs --test redteam3` (one at a time, so the memory tests don't compete for the sandbox's 4 GB). In the sandbox, on the code attacked, it ended `test result: FAILED. 0 passed; 11 failed; 0 ignored; 0 measured; 0 filtered out; finished in 302.31s` (full output: `redteam/attacks3/redteam3-test-output.txt`). The test file is formatted (`cargo fmt --check`) and passes CI's `cargo clippy --workspace --all-targets --all-features -- -D warnings`, so a throwaway branch reaches the tests.

Counts: Critical 0, High 2, Medium 4, Low 4.

What held: nothing was read or written outside the project, no output was spoofed, and no import differed from Git without saying so (see "Held up"). The findings are about availability (memory, disk, time), one bug that refuses valid repositories (taken for a dependency's; it was Bolt's own loop, see RT3-3's fix), and what `bolt save` stores after an import.

## Findings

- **RT3-1 High (T19, T7: Git's pack index is read whole, sized by its own count).**
  - **What.** `git/pack.rs::read_index` allocates the index's names (`count × 20` bytes for SHA-1), then its offsets (`count × 4`, the 64-bit table, and `count × 8`), with `count` taken from the index's own fan-out and checked only against the file's length. Every pack's index is loaded on the first object lookup, so before any object is read or refused. T19 says "a pack's index is read a piece at a time, with a capped entry count, never whole; a Git import reads `.git` by the same rules": Bolt's own packs have the cap (`MAX_PACK_OBJECTS`), Git's don't.
  - **Why the length check misses it.** A sparse file passes it and costs nothing on disk; `tar` keeps the hole, and zip or 7z carry the zeros at ~1000:1. Zeros fail the order check, but only after the names are read in.
  - **Who is hit.** Anyone who runs `bolt import` in a repository they received as an archive. A `git clone` can't deliver it: Git writes the `.idx` itself.
  - **Proof (test).** `rt3_1_a_sparse_git_pack_index_does_not_make_import_allocate_its_size` (60 million objects claimed):
    ```
    `bolt import` of a repository whose only pack index is a 1602 MB hole took 1155 MB: Ended { code: Some(1), …
    stderr: "error: Bolt can't import this Git repository: …/pack-abab….idx lists its objects out of order, …"
    ```
  - **Proof (script).** `sh redteam/attacks3/sparse-idx.sh /tmp/t/release/bolt 25 100 200 230` (`sparse-idx.txt`):
    ```
    objects claimed: 100M; .idx 2800001072 bytes apparent, 44 KB on disk
      tar --sparse -czf of .git: 465 bytes
      /tmp/t/release/bolt import: exit 1, 6.7 s, peak 1911 MB
    objects claimed: 200M; …  tar --sparse -czf of .git: 463 bytes  → exit 1, 11.6 s, peak 3819 MB
    objects claimed: 230M; .idx 6440001072 bytes apparent, 44 KB on disk
      tar --sparse -czf of .git: 468 bytes
      /tmp/t/release/bolt import: exit killed by signal 9, 3.3 s, peak 4080 MB
    ```
  - **Fix.** Give Git's indexes the cap T19 promises, per index and in total across all packs (`objects/pack` may hold 50,000 of them), and refuse before allocating. Or don't keep the names whole: binary-search the index file with positional reads, keeping only its fan-out. Session 2's RT2-5 fix for Bolt's packs is the model.
  - **Fixed** in 25cd774. A repository's packs may list at most 16,777,216 objects (2^24), per index and in all; past that the import stops on the index's count, before its length is checked or any table is read. Names and offsets are read 2,048 entries at a time, and a name is kept only once it comes after the one before, so a table of zeros fails at its second name. `rt3_1_…` passes in a Linux container from the `bolt-redteam` image (no network): the import stops in 0.02 s with `…/pack-abab….idx lists 60000000 objects, more than the 16777216 Bolt reads from a repository's packs, whose indexes it keeps in memory.`

- **RT3-2 High (T7, T11: octopus merges multiply memory and disk).**
  - **What.** A chain of merges, each with the merge before and 1,023 root commits as parents (Bolt's limit is 1,024). In Git's pack each merge after the first is a ~60-byte delta on the first: ~110 bytes a merge.
    - Pass 1 (`in_order`) pushes each commit with its parent list and a sorted copy of it. A chain of N merges is N frames deep, ~68 KB a frame (2 × 1,024 × 33-byte `GitId`), and `order` keeps every parent list through pass 2.
    - Each save stores its 1,024 parents' 32-byte IDs, which don't compress: ~33 KB a save on disk.
    - No limit counts parent edges, or what an import writes.
  - **Who is hit.** Anyone importing a repository from someone else, including a plain `git clone` from a hostile server: the pack arrives as it was sent, and Git's clone and checkout of it take seconds.
  - **Proof (test).** `rt3_2_importing_a_small_chain_of_octopus_merges_needs_little_memory` (8,000 merges):
    ```
    `bolt import` of a 1009001-byte Git repository took 650 MB of memory and wrote a 264566534-byte .bolt
    ```
  - **Proof (script).** `sh redteam/attacks3/octopus.sh /tmp/t/release/bolt 1000 5000 20000 52000` (`octopus.txt`):
    ```
    N=1000 merges of 1,024 parents: .git 304 KB on disk   → exit 0, 2.1 s, peak 85 MB;   .bolt 32548 KB
    N=5000 …: .git 700 KB on disk                          → exit 0, 10.0 s, peak 403 MB; .bolt 161568 KB
    N=20000 …: .git 2188 KB on disk                        → exit 0, 37.1 s, peak 1599 MB; .bolt 645412 KB
    N=52000 …: .git 5396 KB on disk                        → exit killed by signal 9, 32.4 s, peak 4083 MB
    ```
    The new `.bolt` grows ~300 times as fast as the Git repository, and memory ~700 times.
  - **Fix.**
    - Memory: keep commits in pass 1 and `order` as indexes into one table of IDs (4 bytes an edge instead of 66), and don't copy each parent list to sort it. Pass 2 re-reads every commit anyway, so `order` needs no parents at all.
    - Limits: count parent edges per import, and stop before writing past a limit (as the 1,024-parent limit does per commit).
    - Disk: an import-wide budget on bytes stored, relative to the Git repository's size, or an owner ruling that whole records per save are accepted. The same holds for any history Git delta-compresses and Bolt stores whole (see Suspicions).
  - **Fixed** in 78a6f5f. Pass 1 keeps each commit as an index into one table of IDs, and a commit's parents, as 4-byte indexes, only while that commit waits on the walk's stack; pass 2 reads each commit's parents again, so no parent list is kept. An import may add at most 1,000,000 parents beyond each commit's first (decision 043), counted in pass 1 before anything is written; git/git's history has 21,699. Decision 043 accepts the disk a save's parents take: within the limit, at most about 35 MB. `rt3_2_…` passes in a Linux container from the `bolt-redteam` image (no network): the import stops in 4.8 s (debug build) with a peak of 13 MB and no `.bolt`, saying `This Git history's merges have more than 1,000,000 parents beyond their first, and Bolt takes at most that many in one import, …`. Its assertion already accepted a stop (exit 0 or 1, under 256 MB). After the review of the fix it also checks that the `.bolt` left behind stays under 40 MiB, as decision 043's "under about 35 MB" allows, and it still passes in the Linux container.

- **RT3-3 Medium (new: a dependency bug makes valid repositories "damaged"; it was Bolt's own loop, see Fixed).**
  - **What.** `odb::Inflater` feeds miniz_oxide 0.9.1's streaming `inflate` 16 KiB of input at a time (`MZFlush::None`). For some valid streams of large, mostly-zero data, miniz_oxide reports `StreamEnd` a few hundred bytes early. Given the whole input in one call, the same stream inflates in full, and Python's zlib (Git's library) inflates every one of them. Bolt's size check then refuses the object:
    ```
    error: Bolt can't import this Git repository: …/objects/10/f1a0bf47… holds 209714386 bytes, not the 209715200 it says, in the file `disk.img` of commit `229ccf3d…`.
    hint: Check the repository with `git fsck`, or import a fresh clone of it.
    Nothing was committed. Bolt kept the .bolt folder it began here, so that running bolt import again can finish …
    ```
    `git fsck` finds nothing, and every re-run fails the same way. The size and ID checks mean nothing wrong is ever stored: it is a refusal, not corruption.
  - **Who is hit.** Anyone importing a repository holding a large file that is mostly zeros: disk and VM images, padded game archives, database files, sparse data. That is Bolt's big-file audience. No attacker is needed.
  - **Proof (test).** `rt3_3_a_valid_200_mib_file_of_zeros_imports` (the object compressed by miniz_oxide's own compressor, as `Craft` writes it). Output above.
  - **Proof (scripts).** `redteam/attacks3/inflate-sweep.txt`, from `measure-all.sh … zeros` and `zeros.py` (end to end), and `inflate-replay.rs` with `zsweep.py` (Bolt's loop alone):
    ```
    KiB=150000: ok      KiB=204800 (209715200 bytes): holds 209714891 bytes, not the 209715200 it says
    KiB=262144: ok      KiB=262145: holds 268435913 bytes …      KiB=307200 level=1/6/9: short
    out buffer 16384: … in=4 consumed=4 written=15 status=Ok(StreamEnd) total=209714906   (Python: 209715215)
    whole input in one call: 209715215
    SWEEP 24 short of 28 streams (zeros and sparse data, 110 to 300 MiB); 0 short of 36 below 100 MiB
    ```
  - **Fix.** Report it to miniz_oxide with the 200 MiB stream, and pin a fixed version. Meanwhile, try another inflater for Git's objects (zlib-rs, which flate2 can use, is pure Rust too), or, when a stream ends short, retry it inflating the whole compressed input in one call; streams that compress this well are small. Keep the sweep as a test against a second inflater. When a stream does end short, don't send the user to `git fsck`.
  - **Fixed** in 937b1a8. The stream didn't end early: Bolt dropped bytes. Given no input, miniz_oxide's `inflate` writes the rest of a copy it had stopped at the end of its 32 KiB window, then returns `Err(MZError::Buf)` with `bytes_written` above 0, though its documentation says Buf means no progress. Bolt's `Inflater` took Buf for "read more" and dropped those bytes, up to 258 a time. It takes a copy cut at the window's end just as a 16 KiB input buffer runs out, which data that compresses about 1,000 to 1 meets often. The `Inflater` now counts what was written whatever the status. 0.9.1 is miniz_oxide's newest release and its master has the same code, so no dependency changed. A stream that ends before its declared size now says so and asks for a report, without `git fsck`. `rt3_3_…` passes on Windows (and in the Linux container). Two tests keep it: `a_stream_inflates_whole_where_miniz_oxide_says_buf_after_writing` (52 MiB, every push) and the ignored sweep `big_mostly_zero_streams_inflate_whole` (zeros and sparse data of 110 to 300 MiB at levels 1, 6 and 9, checked byte for byte; 83 s in release). Both fail on the old loop (the sweep: 158 of 240 reads short).

- **RT3-4 Medium (T11: delta-base amplification).**
  - **What.** `BaseCache` keeps no base over 256 MiB, so every read of an object whose delta chain passes through a bigger object rebuilds it, through every delta below it.
    - The import reads each commit twice (pass 1 and pass 2; `HEAD`'s twice more), each tree once, and each blob once (a blob over 64 MiB twice). Looking at a header doesn't rebuild anything.
    - It reads each tag object once for every tag ref through it: 1.6 million reads for RT3-9's 100,000 refs.
    - The chain may be 4,094 deltas deep.
  - **Who is hit.** Anyone importing a repository from someone else, `git clone` included. Git's `index-pack` builds each object of a chain once, from its base. So the clone of a 64-deep chain costs 64 rebuilds, while Bolt pays them on every read. Git's own `log -p` or checkout rebuild per object too (its cache is 96 MiB), but they don't read every object of the history.
  - **Proof (test).** `rt3_4_commits_on_one_huge_delta_base_import_in_reasonable_time` (16 commits on a 300 MiB object rebuilt through 8 deltas):
    ```
    `bolt import` of 16 commits in a 6149-byte Git repository was still running after 20 s: … peak_mb: 611
    ```
  - **Proof (script).** `sh redteam/attacks3/amplify.sh /tmp/t/release/bolt 8:300:1 200:300:1 8:300:8 8:300:64` (`amplify.txt`):
    ```
    N=8 commits on a 300 MiB base under 1 delta(s): .git 44 KB on disk → 3.4 s, peak 306 MB
    N=200 commits on a 300 MiB base under 1 delta(s): .git 76 KB on disk → 68.2 s, peak 305 MB
    N=8 commits on a 300 MiB base under 8 delta(s): .git 44 KB on disk → 28.6 s, peak 606 MB
    N=8 commits on a 300 MiB base under 64 delta(s): .git 48 KB on disk → 253.9 s, peak 605 MB
    ```
    Linear: 0.34 to 0.5 s a commit for each 300 MiB rebuilt. 1,000 commits over 64 deltas take ~9 hours; over 4,094, ~24 days.
  - **Fix.** Count the bytes an import rebuilds through deltas against a budget (say a few GiB plus some multiple of the packs' size), and stop with a clear message. Keeping the last base whatever its size cuts the one-delta case only. Reading objects grouped by their bottom base, as `index-pack` resolves them, removes the repetition.
  - **Fixed** in 0bf24cd. An import may spend at most 4 GiB, or 500 bytes for each byte of the repository's packs if that is more, inflating and applying deltas (and inflating the object a chain starts from), checked before each step. A release import of git/git needed 10.3 GiB of it (11,040,651,903 bytes, against 325,164,403 bytes of packs: about 34 a byte), so its budget of 151 GiB leaves a margin of 14. `rt3_4_…` passes on Windows (and in the Linux container): the import stops in 0.76 s with `rebuilding its objects from Git's deltas would take more than 4 GiB of work, so it looks built to make importing slow.` Its assertion already accepted a stop (it checks only that the import ends within 20 s), so it is unchanged.
  - **Fixed again** in 86486b8, after the review of the fix. The budget rested on the packs' length, and Bolt checks only a pack's header and checksum against its index, so an extra pack of no objects with a hole between the two (a few hundred bytes under `tar --sparse`) raised it to 500 times the hole. The allowance now rests on the compressed bytes of pack entries actually inflated, each entry counted once: at most 4 GiB, or 500 bytes for each such byte. A release import of git/git inflates 323,399,596 bytes and needs 34 bytes of work for each by its end, and at most 46 at any point, a margin of about 11. A new proof, `rt3_4b_an_empty_pack_full_of_hole_does_not_raise_the_work_allowed` (RT3-4's repository beside an empty pack with a 64 MiB hole), passes on Windows: the import stops well within the same 20 s, saying `more than the 4 GiB of work Bolt allows`. On the old budget it would have said about 31 GiB; the test checks those words as well as the time, since how long that much rebuilding takes depends on the machine (about 7 s here). The stop now says which commit or file the import was reading.
  - **Second look** (re-review of 86486b8). The fix's premise, that the allowance rests on data a hole can't supply, is false. A hole inside an entry's deflate stream is read, inflated and counted. Stored blocks of zeros inflate fast (512 MiB in 0.29 s), so 1 GiB costs Bolt about 0.6 s and buys 500 GiB of rebuilding, about 1,000 times the time. A dynamic-Huffman body whose literal zero has the one-bit code `0` turns a 64 MiB hole into 512 MiB in 1.3 s and buys about 31 GiB of rebuilding, roughly 35 times the time. The bound is therefore about 35 to 1,000 times Bolt's inflating time, not a fixed cost, and a sparse archive can still make an import run for hours. For this milestone the allowance stays as built, documented as it is (design.md §5.16, security.md T11): an import made slow can be stopped, commits nothing, and reuses what it stored when run again, though it reads and rebuilds every object again. The redesign is deferred as the owner's question in the follow-ups: rebuild each chain once from its bottom base, keep rebuilt objects in the cache, and rebuild a deltified big blob once for both of its reads.

- **RT3-5 Medium (T2, T24: `bolt save` stores the `.git` spellings the import leaves out).**
  - **What.** `validate_name`, the one place for name rules, refuses `.bolt` spellings everywhere but not `.git` spellings. Only the importer checks `is_git_alias` ("Left out N entries whose names Bolt never writes to disk (such as .git and .bolt)"). The save walk skips only a folder named exactly `.git` (any letter case only where the drive ignores case). So:
    - On Linux, `bolt save` stores `.GIT/…` and `git~1/…`, which are `.git` on Windows (case, and its 8.3 short name), and `.g\u{200c}it/…` and `.git\u{feff}/…`, which are `.git` on HFS+.
    - On every system, it stores a `.git` pointer file in a folder that isn't a project link (a submodule added after the import, or a nested worktree), and the HFS+ spellings.
    - Git refuses to track all of these (`core.protectNTFS` has been on everywhere since 2.24, and fsck checks HFS+ spellings).
    - `bolt show` prints `.g‌it/config` with the joiner unescaped (RT2-3's joiner exception), so it reads as `.git/config`.
  - **Who is hit.** Today, history only. From milestone 3, anyone who writes out such a save on Windows or macOS gets files written into Git's own `.git` beside the project, where an import leaves it. A `config` with `core.fsmonitor`, or a hook, then runs a command at the next `git status`, as in CVE-2014-9390. A project shared as a `.bolt` folder can carry these names anyway, so milestone 3's write-out must refuse them whatever save does.
  - **Proof (tests).** `rt3_5_save_leaves_out_every_name_import_takes_for_git` (Linux):
    ```
    the save holds names Bolt's import never brings in: [".GIT", ".GIT/config", ".GIT/hooks", ".GIT/hooks/post-checkout", ".git\u{feff}", …, ".g\u{200c}it", …, "git~1", "git~1/config", "git~1/hooks", "git~1/hooks/post-checkout", "sub/.git"]
    ```
    `rt3_5b_save_leaves_out_a_git_file_and_an_hfs_spelling_of_git_everywhere` (all systems): `[".g\u{200c}it", ".g\u{200c}it/config", "sub/.git"]`.
  - **Proof (manual run, release).**
    ```
    Saved zrlz  "add things"  (9 files)
      added     .GIT/config  (37 B)
      added     .g‌it/config  (37 B)
      added     git~1/hooks/post-checkout  (27 B)
      added     sub/.git  (22 B)        … and the rest
    ```
  - **Fix.** One rule for "never stored, never written", used by save, import and write-out alike: skip (with the import's note) or refuse every name `is_git_alias` matches, in every folder, on every system. Treat a folder holding a `.git` file as Git does (a nested repository, not files to save). Milestone 3's write-out needs Git's `verify_path` check as well. Note that putting this in `validate_name` would also make the listing decoder refuse saves that already hold such names.
  - **Fixed** in e70ec3b, as decision 043 rules. The save's walk uses the import's check, `names::is_git_alias`, on every entry it would otherwise keep, file or folder, in every folder and on every system, and leaves out each one Git treats as `.git`, with everything in it. A `git_names_left_out` warning names the first five by path, escaped, and counts them. A folder named `.git` as the drive spells it is still skipped without a word, and so is an entry an ignore rule keeps out. The last save's listings are read without such names, so neither an entry kept as it was by name (a project link, a name this computer can't hold) nor an ignored file the last save holds brings one back, and a folder gone from disk doesn't come back for one; at e70ec3b those were dropped without a warning. A folder kept whole is the exception: one this computer can't hold (`aux/` on Windows, or `Lib/` beside `lib/` on a drive that ignores case), inside a folder gone from disk too, keeps its listing and everything in it, so a `.git` spelling the last save holds there stays. Only a save made before this fix, or a planted `.bolt`, can hold one, and writing files out (milestone 3) checks every name again. The rest of a nested Git repository is saved as before, and `validate_name` is unchanged. `rt3_5_…` passes in a Linux container from the `bolt-redteam` image (no network); `rt3_5b_…` passes on Windows and in the same container. The RT3-5b case, run by hand with a debug build, now gives:
    ```
    warning: Left out 2 entries whose names Git treats as .git, with everything in them:
      .g‌it
      sub/.git
    Git keeps such names for itself (some spellings only on Windows or macOS), so Bolt leaves them out of saves, as it does on import. Rename them to save them, or list them in .boltignore to leave them out without this warning.
    ```
    Milestone 3's write-out still needs a check of its own (decision 043).
  - **Fixed further** in 6899abd, after the review of the fix.
    - The `.git` spellings the last save holds are named too, in the same `git_names_left_out` warning, each once. The walk notes what it drops from every listing of the last save it reads: the top, the folders it keeps, and those below folders gone from disk.
    - The warning shows every invisible character in its paths (`text::escape_all`, which also escapes the zero-width joiners that `escape` keeps), so the HFS spelling no longer reads as `.git`.
    - Its hint no longer tells the owner of a submodule's or worktree's `.git` file to rename it.
    - A new test has the last save hold `.GIT/x`, and the next save names it.
    - `rt3_5_…` and `rt3_5b_…` still pass, on Windows and in the Linux container. The RT3-5b case now gives:
    ```
    warning: Left out 2 entries whose names Git treats as .git, with everything in them:
      .g\u{200c}it
      sub/.git
    Git keeps such names for itself (some spellings only on Windows or macOS), so Bolt leaves them out of saves, as it does on import. If Git uses them (a submodule's or worktree's .git file), list them in .boltignore to leave them out without this warning; otherwise rename them to save them.
    ```

- **RT3-9 Medium (T7, T11: a tag list costs four times its budget).**
  - **What.** Each tag keeps a copy of its tag objects' bytes, so many refs to one big tag object fill the 512 MiB budget from a tiny repository. The import then holds the list about four times over: `tag_list.tags`, the encoded record (a buffer grown by doubling), and `put_record`'s read-back check, which decodes it into a third copy. The converter's own comment says "the tags returned hold at most [512 MiB], and reading holds one chain more, at most 16 MiB".
  - **Who is hit.** Anyone importing a repository from someone else, `git clone` included (it fetches tags).
  - **Proof (test).** `rt3_9_storing_a_tag_list_takes_at_most_twice_its_size` (300 refs to one tag object just under 1 MiB):
    ```
    importing 300 tags (a 300 MiB tag list) took 1249 MB
    ```
  - **Proof (script).** `sh redteam/attacks3/measure-all.sh /tmp/t/release/bolt tags` (`tags.txt`):
    ```
    fat, 100 tag refs: .git 68 KB  → exit 0, 0.6 s, peak 417 MB
    fat, 480 tag refs: .git 92 KB  → exit 0, 3.3 s, peak 1985 MB   (.bolt afterwards: 64 KB)
    fat, 500 tag refs: refused by the budget at tag `t0000481`
    chain, 100000 tag refs: .git 6040 KB → exit 0, 36.4 s, peak 723 MB
    ```
  - **Fix.** Encode the record once, into a buffer of the exact size, and check it without keeping a decoded copy (or don't read back a record Bolt built from checked parts). Better, store each distinct Git tag object once and have tags refer to it: the list then holds IDs, and 100,000 refs through one chain stop costing 100,000 copies of it.
  - **Fixed** in 9bf1616. The import writes each tag into the list as it reads it and lets it go, into a buffer of the size its first pass counted, so the tags are never held whole beside the list; the check before storing reads the record as the decoder does, a tag at a time, keeping none (`TagList::check`). `TagList::encode` writes into a buffer of the list's exact size too. `rt3_9_…` passes in the Linux container: the 300 tags (a list of about 319 MiB, with their 64 KiB messages) import with a peak of 332 MB. Storing each Git tag object once is left for a later format change (decision 043).

- **RT3-6 Low (T12: a tracked `.env` is saved silently).**
  - **What.** A hostile repository tracks `.env` with a placeholder, and lists `.env` in `.gitignore`, so the user believes it is ignored. Saved files stay saved (decision 038), Bolt has no add step and no `status` yet, and `bolt save` names no files. The user's real secrets therefore go into history on their next save, with nothing said.
  - **Judgement.** The rule is Git's, and right for real projects (force-added DLLs). The difference is visibility: Git lists `modified: .env` in `git status` and stages it only on `-a`, `-A`, `add .` or `add .env`, while Bolt behaves like `commit -a` every time without showing it. T12 promises that "bolt save warns about files that look like secrets", which isn't built yet. A finding by the letter of T12; the owner may rule it design.
  - **Proof (test).** `rt3_6_a_tracked_but_ignored_env_is_not_saved_silently`:
    ```
    the save took the user's .env ("API_KEY=sk_live_REAL_SECRET\n") and said only: Saved prtp  "Say hello"  (2 files)
    ```
  - **Fix.** When a save records a change to a file an ignore rule matches, warn and name it ("saved because an earlier save holds it; Git would ignore it"). Add the planned secret-pattern warning, and a `git rm --cached` equivalent.
  - **Ruled in decision 043 (a warning, not a refusal) and fixed** in 623f4b2. The walk notes each file or link it keeps only because the last save holds it while an ignore rule matches it (decision 038). A save that takes a change to one, to its contents or its kind, gives an `ignored_changes_saved` warning that names the first five by path, escaped, counts them, and says Git would leave such changes out unless they were added. Unchanged, new and deleted files don't count. `rt3_6_…` passes on Windows and in the Linux container. Its assertion already accepted a warning that names `.env` (the save may take the file if it says `.env`), so it is unchanged. The proof's case, run by hand with a debug build, now gives:
    ```
    warning: Saved a change to 1 file that an ignore rule matches:
      .env
    The last save holds it, so it stays saved, but Git would leave such a change out unless the file was added (git add). Bolt keeps saving it until it is deleted or moved out of the project folder.
    ```
    The secret-pattern warning (security.md T12) and a `git rm --cached` equivalent stay for later (decision 043).

- **RT3-7 Low (decision 039: a sparse checkout set through an include isn't refused).**
  - **What.** Decision 039 refuses sparse checkouts so that the first save won't record the files Git left out as deleted. The reader takes `core.sparseCheckout` only from `.git/config` itself (and `config.worktree`). Git reads that key through `[include]` and `[includeIf]` too, and from the user's global config. "Includes aren't followed" is right for the format check alone.
  - **Proof (test).** `rt3_7_a_sparse_checkout_turned_on_through_an_include_is_refused`:
    ```
    the import went ahead in a sparse checkout: Imported 1 commit from Git: 1 line, 0 tags.
    ```
  - **Proof (script).** `sh redteam/attacks3/include-sparse.sh` (`include-sparse.txt`): the first save then shows `removed   b.txt` and `removed   c.txt`.
  - **Fix.** Check the effect rather than the key: the first save after an import stops, as for line endings, when files of the imported save are missing from disk, or refuse when `.git/info/sparse-checkout` exists. Otherwise follow includes for this key.
  - **Ruled in decision 043: a warning, not a refusal; proof test stays ignored.** Built in 5e2960f: when `.git/config`, or the `config.worktree` Git reads beside it, has an `[include]` or `[includeIf]` section, the import warns (`config_includes_ignored`) that Bolt can't tell whether they turn on sparse checkout, and says how to check and turn it off before the first save. `rt3_7_…` asserts a refusal, so it stays ignored, citing the ruling; `config_includes_are_warned_about` checks the warning.

- **RT3-8 Low (T7: a deltified blob is held three times while it streams).**
  - **What.** `Converter::stream` binds both readers of a big blob to `blob`. A shadowed binding lives to the end of the function, so a deltified blob (which `blob_reader` rebuilds whole in memory) is still held by the first reader while the second rebuilds it. The peak is three times the file, where the limits allow two (a 512 MiB object and its 512 MiB base).
  - **Proof (test).** `rt3_8_streaming_a_deltified_blob_holds_it_at_most_twice`: `importing one 300 MiB deltified file took 912 MB`.
  - **Proof (script).** `sh redteam/attacks3/measure-all.sh /tmp/t/release/bolt big-blob` (`big-blob.txt`): 128, 256 and 512 MiB files peak at 393, 776 and 1,541 MB. With `drop(blob);` added after the first pass (a patch tried in this copy, then reverted), 512 MiB peaks at 1,029 MB.
  - **Fix.** That `drop(blob)`, or the first reader in a block of its own.
  - **Fixed** in d817953. The first reader is in a block of its own, dropped before the second opens. `rt3_8_…` passes in the Linux container: one 300 MiB deltified file imports with a peak of 612 MB.

- **RT3-10 Low (T21: two imported saves can share a change ID, and then neither can be picked by it).**
  - **What.** A commit's `change-id` header (Jujutsu's) becomes its save's change ID, as decision 032 says, and nothing stops two commits from carrying the same one. Jujutsu marks such changes divergent and lets you pick by commit ID. Bolt shows both as the same ID, its `show` refuses the whole ID as ambiguous, and its hint asks for more letters that don't exist. A hostile repository can give a malicious save the change ID, message, author and date of a reviewed one, and `bolt history` shows two identical lines.
  - **Proof (test).** `rt3_10_every_save_history_shows_can_be_picked_by_the_id_it_shows`:
    ```
    two saves show as "klmnopqrstuvwxyzklmnopqrstuvwxyz" in `bolt history`, and `bolt show klmnopqrstuvwxyzklmnopqrstuvwxyz` said: error: "klmnopqrstuvwxyzklmnopqrstuvwxyz" matches more than one save: klmnopqrstuvwxyzklmnopqrstuvwxyz, klmnopqrstuvwxyzklmnopqrstuvwxyz.
    hint: Type more of the ID to pick one.
    ```
  - **Fix.** Mark saves that share a change ID wherever IDs are shown (as Jujutsu's `??`), and when an ID is ambiguous, list the saves by fingerprint so one can be picked. Or let the import take a header's change ID only when no other commit in the import has it.
  - **Fixed** in 1a529e0. A `change-id` header's change ID goes to the first commit in the import's fixed order that has it (decision 043), and to none when Jujutsu's rule gives that ID to some commit of the import from its own commit ID; every other commit takes the ID its own commit ID gives, and a `duplicate_change_id` warning counts them. Pass 1 notes which header IDs some commit's own ID gives, before anything is written. The second condition goes past the ruling's words, which cover a header used earlier: without it, a commit whose header spells a plain commit's change ID, made to come first in the order (a root on another branch, with a lower ID), would still share it. `rt3_10_…` passes on Windows and in the Linux container.

## Suspicions (not proven)
- **Big similar trees amplify disk like RT3-2.** A folder of 1,000,000 entries changed by one entry a commit is a ~100-byte delta in Git and a whole listing in Bolt, every commit. Not measured.
- **RT3-3 below 180 MiB.** The whole-read path (objects up to 512 MiB, and every delta) uses the same `Inflater`. The sweep found no short stream below 180 MiB, but tried only a few shapes of content. *(Since confirmed: on the old loop, zlib streams of zeros and of sparse data came out short at 90 and 100 MiB too. Fixed with RT3-3 in 937b1a8, which is the same `Inflater` for both paths.)*
- **`.gitattributes` conversions** (`working-tree-encoding`, `ident`, filters) make the first save record every such file as changed. Decision 039 accepts this; with no `git` in the sandbox, not run.
- **The `.bolt` and `.git` checks split names differently.** `is_bolt_spelling` looks at the first backslash part only, so `x\.bolt` is a valid name, while `.git` is checked in every part. Harmless as long as T1 keeps names holding `\` from being written on Windows; one rule would be safer.
- **A planted unfinished `.bolt`.** Its `config.toml` and packs stay in the new project, and a refusal says "Bolt kept the .bolt folder it began here" about a folder Bolt didn't begin.
- **`refs/replace/*`** is listed among the refs not imported, but nothing says that `git log` shows the replaced history while Bolt imports the original objects. Grafts get a warning. A clone doesn't fetch replace refs by default.
- **Many packs.** `find` searches every pack, in order, for every lookup (up to 50,000 packs). Not measured.
- **A corrupt packed copy with a good one elsewhere.** Git retries another pack; Bolt reads the first and refuses. Rare, and not run.
- **Headers of deep chains** (noted while fixing RT3-4). `Repo::header` of a deltified object walks its whole chain, up to 4,096 entry headers, without the base cache, once for each blob, and the allowance for rebuilding doesn't count that walk. A pack of many small blobs, each a delta on top of a 4,095-deep chain, could make an import read billions of entry headers while building almost nothing. Not run.

## Held up (don't repeat)
- **Output.** Ref names, paths, people and messages holding ANSI escapes, OSC titles, bidi controls, U+2028 and invisible characters were all escaped in the import summary (renaming list, skipped refs and entries), `history` and `show` (manual run with a hostile tree and refs). `Main` and `main` were renamed and reported (`main → main-2`, "You're on line main-2.").
- **Exactness** (by reading and runs). Each commit is rebuilt and compared before its save is stored, with `git-header` kept when needed. Non-standard modes and skipped names mark a tree inexact, and memoized trees carry it to every commit that holds them. Tag objects are kept byte for byte. Saves carry their commit's ID, so two histories can't share saves. Branches or `HEAD` pointing at tags, and tags pointing at trees or blobs, stop or are listed.
- **Planted unfinished `.bolt`** holding session 2's 5 GiB sparse Bolt pack: refused at once at 10 MB ("its 5368709055 bytes don't fit its entry count of 0"). Reused objects are read and checked first (`has_good_copy`).
- **Tag chains.** 100,000 refs through one 16-object chain: 1.6 million re-reads in 36 s. Its memory is RT3-9.
- **`packed-refs` at its limits.** 7,500,000 refs (480 MB, 19 MB gzipped): import in 7.1 s, peak 1,489 MB (`measure-all.sh … packed-refs`, output in `packed-refs.txt`).
- **Zlib bombs, wrong IDs, delta loops and depth, huge declared sizes:** refused, nothing stored (the builders' tests, and reading).
- **`.git` and `.bolt` spellings in Git trees.** Skipped and listed (the output run above left out `.GIT` and `git~1`). A `.bolt` folder below the top gets a warning; one at the top stops the import, with a hint that never puts the name into a command.
- **Refs.** `check-ref-format` names, loose refs found by walking, and links in `.git` refused (by reading).
- **The line-ending stop** compares in 64 KiB pieces, in bounded memory, and only files whose size fits a conversion.
- **Decision 039's kept entries** (case twins, names this system can't hold, project links). Edits to them aren't saved, by design, and the save's summary counts them.
