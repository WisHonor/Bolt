## Findings

- **RT10-1 Medium (a damaged project passes as sound; T9, decision 118).**
  - **What.** A big file is stored as a chunk list naming its chunks, and reading the file takes each chunk as *content* only (a chunk is never read through another list). `verify` builds the set of objects it "knows" from every ID in every index, whatever its kind. So when a chunk is in no pack as content, but some pack holds a *chunk list* under that chunk's ID:
    - the check of the packs passes the file's list over ("a chunk no pack holds is left to the check of what the project needs", `rebuild` with `skip_missing_chunks`);
    - the check of what the project needs finds the chunk's ID in an index, so it isn't missing (`look_at`: `kept` minus `noted.known`, which holds every ID of any kind);
    - the planted list under the chunk's ID rebuilds correctly (its two pieces are the chunk's two halves), so nothing about it is wrong either.

    The kind check that records get (`Unread::OtherKind`, "stored, but as another kind") never applies to chunks, which are kept by ID without being read.
  - **Who is hit.** A store a hostile or broken tool wrote, or a copied `.bolt` someone made. Bolt itself never writes it. The person who runs `verify` to check a project they were given, or one after a disk problem, is told it is sound, and then can't check out the file.
  - **Proof (test).** `rt10_1_verify_finds_a_chunk_stored_only_as_a_chunk_list`: a 3 MiB file whose first chunk is stored only as a chunk list of its two halves.
    ```
    bolt goto main: Some(1) error: A switch between saves stopped at big.bin: This project's Bolt data looks damaged: pack …/9401b4bf….pack (the chunk list of 5a841f9e… names chunk f79ff173… of 79457 bytes, which isn't in the store).
    bolt verify: Some(0) Verified .tmpCrIxcV: no problems found.
        + 49 stored objects in 4 packs (3.0 MiB) match their fingerprints
        + 2 saves, 1 line and 0 shelves point to objects that exist
        + the undo diary (3 entries) is intact
    ```
  - **Fix.** Count a chunk as present only when an index holds it as content: keep a second set, `content_known`, filled in `survey` from `ObjectKind::Content` lines, and in `look_at` test the chunks the lists name (`noted.via`'s keys, or every chunk `chunks()` keeps) against it, telling one held only as another kind with the "stored, but as another kind of object" message. Simpler still, `rebuild` could stop passing a list over when its missing chunk's ID is in an index under another kind, and report it there.

- **RT10-2 Medium (a damaged project passes as sound; T9, decision 118).**
  - **What.** A folder listing gives each file its size, and storage-format.md §3 says it is the file's length. Writing a file out checks the content against that size, and refuses when they differ. `verify` reads every listing and finds every content it names, but never compares the listing's size with the size of the content or chunk list it names. A save whose listing says 999 bytes for a 6-byte file, or one byte too many for a 3 MiB chunked file, passes.
  - **Who is hit.** As RT10-1: a store from a hostile or buggy writer (an importer, a merge of someone else's packs). The size lives in the listing record, whose fingerprint covers it, so this isn't damage on disk but a save that was written wrong; `verify` is the command meant to find exactly that before the user relies on it.
  - **Proof (test).** `rt10_2_verify_finds_a_listing_whose_size_isnt_its_files`: a planted save with `a.txt` (6 bytes, listed as 999) and `big.bin` (3 MiB chunked, listed one byte longer).
    ```
    bolt goto main: Some(1) error: A switch between saves stopped at a.txt: This project's Bolt data looks damaged: the content 8e4c7c1b… isn't the size the switch expects.
    bolt verify: Some(0) Verified .tmp2kQvlR: no problems found.
        + 47 stored objects in 4 packs (3.0 MiB) match their fingerprints
        + 2 saves, 1 line and 0 shelves point to objects that exist
    ```
  - **Fix.** When marking walks a listing for `verify`, note each file entry's (ID, size), and once the packs are known compare it with the index line's uncompressed size for that ID (a chunk list's index line records its file's size, §6), reporting a mismatch as damage needed by that save and path. A symlink entry's size is its target's length, the same check. `tidy` needn't do it; it is `verify`'s alone.

- **RT10-3 Medium (a save every reader refuses passes as sound; T7, decision 025).**
  - **What.** storage-format.md §3 limits a save to 10,000,000 entries, counting a listing reached through two paths twice, and says every reader walking a save must stop with an error past it. `goto` does. `verify` marks each listing once (the `followed` set), so it never counts entries by path, and a save past the limit, a tree bomb, passes.
  - **Who is hit.** A hostile save, from a copied `.bolt` or (later) a server. The save is never usable: `goto`, `changes` and every walk refuse it. `verify` says otherwise.
  - **Proof (test).** `rt10_3_verify_finds_a_save_past_the_entry_limit`: one listing of 10,001 folders, each the same listing of 1,000 files (10,011,001 entries; 13 KiB stored).
    ```
    bolt goto main: Some(1) error: This project's Bolt data looks damaged: this save is too large to read safely: it has more than 10000000 files and folders in total.
    bolt verify: Some(0) Verified .tmpQFeTQl: no problems found.
        + 9 stored objects in 3 packs (13 KiB) match their fingerprints
    ```
  - **Fix.** For each save `verify` reads, count the entries below its root by path without walking them again: the count of a listing is its own entries plus, for each folder entry, its folder's count, memoised by listing ID (and the depth the same way, the deepest folder plus one). Saturate the sums and report a save over 10,000,000 entries or 4,096 levels as damage, naming the save. Memoising keeps the cost at one pass over each listing, as now.

- **The release workflow** (code reading, `.github/workflows/release.yml`):
  - The only job that may write (`release`, `contents: write`) runs only on `workflow_dispatch` from `refs/heads/main`.
  - A pull request runs `prepare` and `build` with `contents: read` and `actions: read`. From a fork the token is read-only anyway.

## Suspicions without proof

None of these counts as a finding.

- **A deep tree bomb makes `goto` slow before it refuses.** Before RT10-3 was made wide, it was a chain of 24 listings of two entries each (2^24 files, 31 objects, 8.4 KiB). The debug build's `goto` ran for about four and a half minutes, holding 200 MB and writing nothing, and was stopped by hand before it refused. Each listing seems to be read once per path that reaches it. The 10,000,000-entry limit bounds it; no document bounds the time. Not measured in a release build.
- **A pack of zstd bombs makes `verify` slow.** An object may claim up to 1 TiB, and `verify` must decompress and hash all of it to find it false. zstd turns about 24 MB into 1 TiB of zeros, so a planted pack costs on the order of 20 seconds of `verify` per megabyte. Reasoned from the format, not run.
- **`verify`'s memory per chunk list.** Each list that checks out is kept with a copy of its pack's file name until the rebuild (`Found::lists`), about three times what an ID costs. It grows with the objects, which is the known limit; not measured.
- **The release job has no protected environment.** Anyone who can push a branch can push a workflow that makes a release with the repository's token. The repository's settings (default token permissions, environments, rulesets) decide that, and they can't be read from the sandbox.
