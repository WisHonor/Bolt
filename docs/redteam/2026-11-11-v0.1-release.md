# Red-team report: the v0.1 release (RT14, decision 024, 2026-11-11)

Code attacked: a copy of `v0.1-engine` at 0bca8ea, built in release mode (`cargo build --release -p bolt-vcs`) in the no-network sandbox (Debian, git 2.39.5, git-lfs 3.3.0), plus two items only Windows and macOS can show, run on GitHub's runners from the branch `redteam/v01-names`.
Proof tests: `crates/bolt-vcs/tests/redteam14.rs`. 3 tests, each marked `#[ignore = "RT14-n: …; until its fix is in"]` and each asserting the SAFE behaviour. RT14-1 runs on Linux only (it reads peak memory from `/proc`; elsewhere it compiles away). Run them with `cargo test --release -p bolt-vcs --test redteam14 -- --ignored --test-threads=1` (or `redteam/attacks13/run.sh proofs`, which runs it in the sandbox); RT14-3 compares times, so run it in a release build. In the sandbox, on the code attacked: `test result: FAILED. 0 passed; 3 failed; 0 ignored; 0 measured; 0 filtered out; finished in 30.36s`. Without `--ignored` the file passes (3 ignored). It is formatted with `rustfmt --edition 2024` and passes `cargo clippy -p bolt-vcs --tests --all-features -- -D warnings` in the sandbox, also with its Linux-only test compiled away as on Windows and macOS.
Platform probes: `crates/bolt-vcs/tests/redteam14_platforms.rs` (Windows and macOS only, both tests `#[ignore]`d; the branch ran them without the attribute). Both held; see "What held".
Attack code: `redteam/attacks13/`: differential fuzzes of the ignore matcher against `git check-ignore`, of the look-alike test against Git's own `verify_path`, and of the Git LFS pointer reader against `git lfs pointer --check` (`rt14_wild.rs`, `rt14_alias.rs`, `rt14_lfs.rs`); the deep tree against every command (`rt14_deep.rs`); the cost of a large hostile `.gitignore` (`ignore_cost.sh`); `--json` on hostile names (`json_names.sh`); a Git LFS pointer padded past 1,024 bytes (`lfs_tail.sh`). `run.sh explore <name>` copies an exploration test into the suite and runs it in the sandbox; `run.sh script <file>` runs a script there.

Counts: Critical 0, High 0, Medium 0, Low 3.

## Findings

- **RT14-1 Low (a project built to be slow: a small planted save within the limits; T11, T32; `listing.rs`, `diff.rs`, the status output).**
  - **What.** Decision 130 refuses a planted tree of shared listings at once when it passes the 10,000,000-entry limit, and walks it path by path when it doesn't ("a save within the limits the format sets is never refused"). A chain of 21 listings each naming the next twice is about 1 KiB stored and 8,388,606 entries by path, inside the limit. On it, in a release build: `status` 17.1 s and **1,446 MiB** peak; `changes --save main` 26.5 s; `show main` 16.1 s; a partial `save "x" deep` 7.9 s; `verify` 0.06 s, and says nothing, since the save is within the limits. `goto` would write 4,194,304 files (not run: it fills the disk). Memory in `status` is about 180 bytes a path, so the limit allows about 1.7 GiB.
  - **Who is hit.** Anyone who opens a project they were given (`.bolt` planted), then runs `status`, `changes`, `show`, `goto` or `discard`: from 1 KiB, a command takes seconds to a minute and over a gigabyte. Bolt still beats Git here (Git has no limit at all), and it is a resource cost, not a data risk.
  - **Proof (test).** `a_small_planted_save_within_the_limits_costs_status_little`: the chain above on `main`, the folder at the first save, `bolt status`:
    ```
    Ended { code: Some(0), timed_out: false, secs: 14.994066703, peak_mb: 1446, ... }
    status held 1446 MiB for a save of about 1 KiB
    ```
  - **Suspected fix.** Either keep decision 130's rule and write this down as a known cost with these numbers (the owner's ruling); or bound what sharing can amplify: a second limit on entries by path against entries stored (the measure already knows both), refused with the same words; or have `status` stream changes instead of holding them all. The first is honest for v0.1.

- **RT14-2 Low (a verdict changed: a boolean Git refuses; T2, T5; `git/config.rs`, `parse_int`).**
  - **What.** Git refuses an integer config value below -(2^31 - 1) when it reads a boolean or an int (its range check is `-max / factor > value`), so `-2147483648`, `-2g` and `-2097152k` are "bad boolean config value" and stop every Git command. Bolt's `parse_int` lets -2^31 through (`i32::try_from`), so `read_bool` says true. A `.git/config` with format version 1 and `extensions.preciousObjects = -2147483648` is refused by Git (`fatal: bad boolean config value '-2147483648' for 'extensions.preciousobjects'`) and imported by Bolt (`Imported 1 commit from Git: 1 line, 0 tags.`). The same value in `extensions.worktreeConfig` makes Bolt read `config.worktree` for a repository Git can't open; in `core.sparseCheckout` both stop, with other words.
  - **Who is hit.** Nobody loses data: Git can't use such a repository at all. It breaks the module's own rule ("a value Bolt takes that it can't read exactly as Git does" is refused) and the rewrite's claim to give Git's answers.
  - **Proof (test).** `import_refuses_a_boolean_extension_git_refuses`: the repository above; Git refuses it, `bolt import` succeeds:
    ```
    Bolt imported a repository Git refuses: Imported 1 commit from Git: 1 line, 0 tags.
    ```
  - **Suspected fix.** In `parse_int`, refuse a negative value below `-(i32::MAX / factor)`, before scaling, as Git checks it; a unit test for -2147483648, -2147483647, -2g and -2097152k.

- **RT14-3 Low (a project built to be slow: glob ignore lines cost many times Git's time; T11; `ignore.rs`, `run`).**
  - **What.** The bracket parser is linear, as claimed, and matching never backtracks; but each line that isn't a plain name or one star runs `run`, which allocates four `Vec`s for every line and path it tries, however soon the first byte fails. A `.gitignore` under 1 MiB of lines that match nothing, against 2,000 files in one folder (`ignore_cost.sh`, `bolt status` against `git status --porcelain -uall`, release build):
    ```
    plain      lines=100000  git=  0.87s bolt=  0.22s
    star       lines=81818   git=  1.67s bolt=  1.11s
    glob       lines=47368   git=  1.14s bolt= 14.27s     [!a-z]N*[xy]?
    dirs       lines=52941   git=  3.62s bolt= 26.25s     **/zN/**/q*
    classes    lines=23076   git=  1.44s bolt=  5.14s     [[:alpha:][:digit:]]N[[:space:]]*
    anchored   lines=69230   git=  1.36s bolt=  0.93s     d/zN*/q
    ```
    The time grows with lines times paths, as Git's does, so a project of 100,000 files with the `glob` file would take about twelve minutes for every `status` (Git about one).
  - **Who is hit.** A cloned or imported project whose `.gitignore` (or a `.boltignore`) was written to be slow; every `status` and `save` pays it, until the file is fixed. Memory stays small (under 31 MiB).
  - **Proof (test).** `hostile_glob_ignore_lines_cost_bolt_no_more_than_twice_git`: the `glob` lines through `Matcher` against 2,000 paths, and the same through `git check-ignore --stdin`:
    ```
    git 1.13 s, bolt 13.80 s
    Bolt took 13.80 s where Git took 1.13 s
    ```
  - **Suspected fix.** Keep the four state vectors in the `Matcher` (or a thread-local scratch) and reuse them, or hold the states as bits in a `u64` for patterns of up to 63 pieces; and stop at once when the first piece is a byte or a set the first byte of the path fails, as Git does. Measure with the table above.

## What held

- **The ignore matcher against `git check-ignore`** (`rt14_wild.rs`): 4,000 random rule files of one to three lines drawn from 45 pieces (brackets with `]` first, `!` and `^`, backwards and cross-case ranges, `[Z-a]`, unknown and half classes, escapes everywhere, `**` glued and repeated, escaped trailing spaces, `\/`), each against 40 random paths of up to three names, with letter case counted and folded (`core.ignorecase`): 320,000 verdicts, no difference, once a path below a folder Git's rules keep out is judged by that folder and pathspec magic is off. Lines Git 2.52 reads differently from 2.39 (`foo**/bar`) were left out, as `ignore_vs_git.rs` leaves them out; Bolt follows 2.52 there, on purpose.
- **One long hostile line** (`long_lines.sh`): a single `.gitignore` line of 100 KB and of 900 KB, of each shape (a bracket of ranges, of classes, of `[:` that never closes a class, of escaped `]`, a run of `*a`, a run of `**/`), against 50 files: `bolt status` takes 0.05 to 0.38 s, growing with the line. The bracket parser is linear, as claimed; see RT14-3 for many lines.
- **The look-alike test against Git's own** (`rt14_alias.rs`): 155,865 names (every name of up to three of 33 pieces, among them `.`, `g`/`G`, `~1`, `:`, `\`, trailing dots and spaces, U+200C to U+200F, U+202A, U+206F, U+FEFF, U+FFFE, U+FFFF, U+2060, U+00AD, U+0130, U+0131, U+212A, plus 120,000 random ones) as folder names fed to `git update-index` with `core.protectNTFS` and `core.protectHFS`: no name Git refuses that Bolt takes. 102 names Bolt refuses and Git on Linux takes, all an HFS+ spelling of `.git` followed by `\`, which Bolt treats as a separator on every system: stricter, on purpose.
- **Windows and macOS drives** (branch `redteam/v01-names`, run 43125626496): on NTFS (`windows-latest`) and APFS (`macos-latest`), every name made from `.git` or `.bolt` by putting one character from U+0080 to U+FFFF in place of one of its characters or between two of them (about 1.3 million names): none the drive opens as the real folder escapes `is_git_alias` and `is_bolt_alias` (so NTFS doesn't take `ı` U+0131 for `i`, nor APFS any case folding for these letters). On NTFS with short names on, a project where `g it` came before `.git` and four `b olt`-like folders before `.bolt` gives `.git` the short name `GIT~2` and `.bolt` the hashed `BO5DC6~1`, which no fixed list catches; a planted save holding `GIT~2/config` and `BO5DC6~1/planted` (the names `dir /x` showed): `goto main` writes into neither, `.git/config` keeps its bytes. All four jobs of run 43125626496 passed; the branch is deleted.
- **The Git LFS pointer reader against `git lfs pointer --check`** (`rt14_lfs.rs`): 3,000 mutated pointers (line order swapped, tabs and doubled spaces, empty and whitespace lines, CRLF, Unicode whitespace at either end and inside, NUL, `+12`, `-0`, `007`, `1e3`, `0x10`, Arabic digits, 2^63 - 1 and 2^63, versions near the three accepted, ext lines anywhere with good and bad keys and values, invalid UTF-8 at either end): no difference but the two known ones. A repeated `ext-` key whose first value is bad (Git LFS keeps the last: the known limit), and a blob over 1,024 bytes whose first 1,024 hold a pointer: `pointer --check` accepts it, but Git LFS's smudge filter passes it through as it is (`lfs_tail.sh`, a real checkout), as Bolt does, so Bolt matches what Git LFS writes.
- **The deep tree, outside the limits** (`rt14_deep.rs`, 2^25 by path): `show`, `changes`, `status` (with the tree's folder on disk but kept out by an ignore rule, and with the tree under a 300-byte name Linux can't hold, which the walk keeps as it was), `goto main` to that second save, `goto` between two planted trees, `changes --save` and `undo` of that step: each refused in 0.08 to 0.12 s and at most 6 MiB. `history`, `history --json`, `line`, `undo --list` and `tidy` don't walk it and finish. `save`, a partial `save` over it and `save --amend` go ahead in 0.1 s, as decision 130 and the gone-folder search intend (a save beside a save too large to compare goes ahead), and `verify` names the save.
- **A config file read as Git reads it** (by reading only, against Git's `config.c`; the one difference found was then checked in the sandbox, RT14-2): quoting, escapes, continuations at the end of the file, comments after values, `isspace` without `\v` and `\f`, headers with and without subsections, a key on the header's line, a partial byte order mark, `GIT_CONFIG_COUNT` at 0, -0, -1, 2^31 - 1, 2^31, a 64-bit overflow and Windows' 32-bit `unsigned long`: the same as Git, but RT14-2. `tidy_path` follows Git's `normalize_path_copy_len` on `.`, `..` at the start and end, separators runs, drives of one to four non-ASCII bytes and network shares.
- **`--json` on hostile names** (`json_names.sh`): 15 names (quotes and braces, a backslash, ANSI escapes, tab and LF, DEL, a name that looks like a JSON document, U+2028 and U+2029, a byte order mark, NFD, a 254-byte name, U+202E, emoji, a name that isn't UTF-8) across 10 commands (`status`, `save`, `show`, `changes`, `changes --save`, `history`, `line`, `verify`, `tidy`, `undo --list`): every document parses, and the names Windows would refuse stop the save with the portability error, in valid JSON.

## Not done

The caches are sealed with the user's key and `verify` reads none of them, so a planted one is only ever ignored; stale ones were not tried.
- The pack reader's block budget (decision 112) was not attacked again; RT13 did.
- `git/person.rs` was read against Git's `split_ident_line` but not fuzzed against `git log`.
- `goto` of a planted tree within the limits (it would write four million files) and `discard` of one: not run.
- macOS's Unicode-composing drive against the ignore rules (NFD names, a `.gitignore` in an NFD folder): not run; APFS was tried only for look-alikes.
