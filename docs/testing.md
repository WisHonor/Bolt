# Bolt Test Plan — Draft

> **Status:** drafted in the design phase (2026-10-31); §3 and §4 describe the tests and CI as they run after milestone 1 (2026-11-02), with milestone 2's differential tests, ignore-rule tests, hostile Git repositories and fuzz targets (2026-11-03), and milestone 3's model test, switch crash tests, hostile saves written out, memory checks and new fuzz targets (2026-11-06), and milestone 4's undo, redo, shelves and amend in the model test, its new crash tests and hostile diaries (2026-11-07), and milestone 5's big files in the model test, its crash tests of big files, hostile chunk lists, Git LFS imports, new fuzz targets, the speed gates and the benchmarks (2026-11-09), and milestone 6's presets, `bolt setup`, `bolt verify`, Git's words, the terminal design, the `--json` documents read against json.md, hostile rule files, the user guide and the release workflow (2026-11-10).

**In plain words.** Bolt's first promise is "never lose or corrupt your data". Tests are how that promise survives every change to the code. Each kind of test below proves something specific, and together they run on Windows, macOS and Linux every time code is pushed.

## 1. Rules

- A task is done only when its tests pass on all three systems.
- Every on-disk format has test vectors ([storage-format.md](storage-format.md) §13) before it holds real data.
- Every bug fix comes with a test that fails without the fix.
- Speed and size claims come only from the benchmarks in §5.

## 2. Kinds of tests

| Kind | What it proves | Tools |
|---|---|---|
| Unit tests | Each small piece does what it says | Rust's built-in tests |
| Format tests | Every record encodes to exactly the bytes in the test vectors and decodes back; every invalid variant is rejected | golden files in `crates/bolt-vcs-core/tests/vectors/` |
| Round-trip tests | Saving and then restoring gives byte-identical files, names, executable flags, symlinks and empty folders | `assert_fs` |
| Property tests | Random sequences of edits and commands never lose data and always match a simple model of what should happen | `proptest` |
| Crash tests | Stopping Bolt at any point while it writes leaves the repository usable, and the next command recovers | fault injection, killed processes |
| Differential tests | Importing a real Git repository gives exactly the same files, for every commit, as Git itself; Bolt's ignore rules keep the same files as Git's | `git` as the reference |
| Fuzz tests | Decoders and parsers never crash, hang or over-allocate on garbage input | `cargo-fuzz` |
| Malicious-repository corpus | Each attack in [security.md](security.md) is refused or handled safely | crafted repositories |
| Red-team sessions | A determined attacker can't break what the other tests didn't think of; once per milestone ([decision 024](decisions/024-red-team-gate.md)) | a fresh agent in a no-network Docker sandbox |
| CLI tests | Commands print what they should, both for people and as `--json` | `assert_cmd`, `insta` snapshots |
| Benchmarks | Speed and size claims are true, and stay true | ignored tests that print what they measure, `hyperfine` |

## 3. Details

**Property tests.** An in-memory model tracks what the folder and history should contain. Each random action (create, change, move or delete files; save; amend; goto; discard; undo; redo; shelf; unshelf) is applied to both Bolt and the model. After every action: `status` matches the model, every save restores byte-identically, `undo` returns to the previous state, and nothing the model says exists is missing.

The model test, `crates/bolt-vcs/tests/model.rs` (`edits_saves_switches_shelves_and_undos_match_the_model`), drives the engine in the test's own process (a process per action would be too slow on Windows) through up to 30 random actions. Milestone 3 built it with these:
- write one of six files, at one of three lengths, so that files often keep their size when they change;
- write other bytes of the same length over a file;
- on Unix, turn a file's executable bit on or off;
- delete or rename a file, and make or delete one of three folders;
- save;
- `goto` a random save or line, first saving or discarding unsaved work, or keeping it;
- discard everything or one path;
- a status that reads every file.

Milestone 4 added these ([decisions 070](decisions/070-undo-and-redo-step-through-the-diary.md) to [074](decisions/074-save-amend.md)):
- `undo` and `redo` of 1 to 3 steps, with or without `--shelve`;
- `undo --to` a random diary entry: the current one, one redo or undo reaches, or any other, which is a jump;
- `shelf`, and `unshelf` of the newest shelf or of a numbered one, a number no shelf has included;
- `save --amend`, with a new message or the old one.

Milestone 5 added these ([decision 082](decisions/082-how-big-files-are-cut-into-chunks.md)):
- write a big file, 1 to 3 MiB of noise, which a save cuts into chunks;
- put 3 bytes into one of the big files at a random place, moving the rest along, or write them over its own there, so a few chunks change and the rest stay.

Milestone 6 added this ([decision 115](decisions/115-bolt-setup.md)):
- `setup --preset` with Code, Game or Custom, writing or removing `bolt.toml` and the `.boltignore` block as one step that moves no line, always followed by an `undo` and a `redo`; switching to the preset the files already hold records nothing.

The checks below cover big files like any other, so every switch, discard, shelf, undo and redo must write them back byte for byte, and every save must read them back through their chunk lists.

The model holds the folder's files (bytes and executable bit) and folders, every save's (its first parent, change ID and message, and whether it is a shelf's), the lines, the position and the shelves; the steps done and undone, each with its state and the whole folder before and after it; and every diary entry with its state. Its undo puts back the state from before the step and switches the folder from the "after" to the "before" by `goto`'s rule (redo the other way); a collision stops the command at that step, and `--shelve` sets the work in the way aside on a new shelf first. Shelves stay, except one the step added or removed. A jump switches from the current save to the entry's save; an amend is refused at a save, or when another line's history holds the save. After each action:
- the folder on disk holds exactly what the model holds;
- `status`, trusting the file cache, lists exactly the files added, changed, removed or changed in kind since the model's save;
- the lines, position and shelves match, and so do the command's outcome, and a stop's paths and flags;
- the diary gained exactly the entries the model made, each with the right action and the model's whole state, `head` names the newest, and an entry records a folder change exactly when its command changed the folder, whose two saves differ exactly where the folder before and after the step differs;
- undo's lists, at 20 steps (the command's) and at 3 (so `more` is often true), are the model's steps: their entries, commands, whether they changed files, and their effects.

Each save holds exactly the model's files and folders in the store, checked when it is made and again at the end, with every save's message and first parent. Once per case, `bolt undo --list --json` runs as a command, and its document must be the one the model builds by [json.md](json.md)'s rules.

Each write leaves the file one of three modified times, which together cover the file cache's rules ([decision 053](decisions/053-file-state-cache.md)):
- the clock's, often within 2 s of the cache's last look, so the racy rule must make status read the file again;
- a time long past that no earlier write had, so the cache trusts the file and must notice the new time;
- the time the file had before. With the same size, that is [decision 011](decisions/011-status-and-write-out.md)'s accepted case, once the old time is more than 2 s old (1.5 s by the test's clock, for slack between clocks): status that trusts the cache may then miss the change, and a status that reads every file must see it, which also puts the cache right for the actions after. A file given an earlier time keeps that leeway when it is renamed. When the old time is newer than that, the racy rule applies and plain status must see the change.

A `goto` that keeps unsaved work is held exactly to decisions [050](decisions/050-unsaved-work-in-goto-and-discard.md) and [065](decisions/065-matching-work-doesnt-collide.md). It must stop, with nothing changed, when an unsaved change that differs from the target sits at, above or below a path where the target differs from the current save (a file, or a folder on one side only) and the folder isn't already as the target is. Otherwise it must go ahead. Work the target already agrees with, such as a file deleted that the target doesn't hold, and new files in a folder the target adds, come along. The rule came from this test: before decision 065, a deletion the target agreed with came along at a file but stopped the goto below a folder the target removes. The test also found a goto that left out a file the target adds when the user had deleted the folder it goes in; `goto.rs` keeps that case.

When it goes ahead, the folder must end as the target's own differences applied around the unsaved work, and folders made since the save stay, with the folders above them.

Names differ in more than letter case, so every drive holds them all, and a save made at a save starts a new line, as it must.

With milestone 4's actions the test found an engine bug, now fixed: a step's two saves could differ at a folder the user had made, which the step only wrote inside, so undoing a `goto`, `unshelf` or jump into it removed the folder, or stopped at it, or with `--shelve` shelved unrelated work in it, and redoing a `discard` inside it removed it. Both saves now hold such a folder ([storage-format.md](storage-format.md) §9), and its shrunk cases are tests of their own in `crates/bolt-vcs-core/src/undo/tests.rs`.

The test hands the engine a cache key, so the file cache is read and written as for a user; until milestone 4 it had none, and the cache was never on in it. With the cache on, each of the cache's checks was broken in turn and the test run for 64 cases: the modified time alone not compared, or the racy rule alone taken out, passed, since the change time catches every edit either lets through; both times not compared passed too (only a same-size edit of a saved file whose entry isn't racy catches it, which the random actions rarely line up), though a 3-action sequence fails at once; both times and the racy rule broken failed within 3 cases. The racy rule needs an edit within one tick of the drive's clock after the status before it, which random actions almost never make, so the model test doesn't exercise it: the cache's own unit test `a_file_changed_within_two_seconds_of_now_is_read_again` (`filecache.rs`) pins it, entries just inside and outside the 2 seconds included.

It runs 64 cases on every push (about 21 s in a debug build on a Windows laptop with milestone 5's big files, and 89 s for 256 cases, measured 2026-11-09), and 1,024 nightly, through `PROPTEST_CASES`. A failure prints the action it failed after and the shrunk sequence. Rare paths stay rare in 64 cases (an amend refused because another line's history holds the save, a jump that stops), so the nightly run is where they are met.

**Crash tests.** Every disk write goes through one small layer that tests can make fail (return an error, or abort the process) at the N-th operation, or fail at one named point (`BOLT_FAULT_FAIL=start:read-back`) and let the command carry on. For each N, a test runs a command, fails it at step N, then checks that the repository opens, `bolt verify` passes, no saved data is missing, and the next command finishes or rolls back the interrupted one. Separately, a loop kills real Bolt processes at random moments.

A command can now write several packs, so milestone 2 added crash tests for the gap between two of them. A named point, `packs:rolled-over`, sits right after a full pack goes into the store.
- `a_crash_between_packs_leaves_the_repository_as_it_was` (in `crates/bolt-vcs-core/src/repo.rs`) fails a command that needs three packs at every step. It checks that `state/head` still names the old entry, that the store checks out, and that running the command again works.
- `crates/bolt-vcs-core/tests/import_interrupted.rs` does the same to `bolt import`, with a test-only limit of three objects a pack. After every stop there is no project yet (`.bolt/format` is missing), and running the import again gives the saves and state of a clean import. At least one stop must fall between two packs.

Merging small packs (milestone 3) adds two named points: `merge:written`, right after the new packs go into the store, and `merge:removing`, before each old pack is removed; an error there leaves that pack as a second copy. `a_merge_stopped_at_every_step_leaves_every_object_readable` (in `crates/bolt-vcs-core/src/merge.rs`) fails a merge of 34 packs at every step, and checks that every object reads and the store checks out, and that merging again leaves at most two packs, and one when nothing went wrong.

Switching the folder between saves (milestone 3) adds three named points: `switch:written`, inside each file write, after the new contents are flushed in `.bolt/tmp` and before they are renamed into place; `switch:changed`, after each change to the folder; and `journal:removed`, after the journal is deleted and before its folder is flushed; the head write's own `write:before-rename` sits between the two. `a_switch_stopped_at_every_write_is_finished_by_the_next_command` (in `crates/bolt-vcs-core/src/writeout/tests.rs`) stops a switch at every one of them, checks that every file is wholly old or wholly new, then runs `save`, which must finish the switch (saying so only when `head` hadn't moved yet), leave the folder exactly as the target save (checked all the way down) and remove the journal. `a_finish_stopped_in_turn_is_finished_by_the_command_after` stops a switch at a few points, then stops the `save` that finishes it at every step, and checks that the save after that finishes it.

A command has happened once `head` moves, and from then on nothing fails it ([decision 075](decisions/075-crash-recovery.md)), so milestone 4 adds two named points where an error is only a warning and the command goes on: `head:renamed`, after `state/head` is renamed into place and before `state/` is flushed (`head_not_flushed`), and `journal:removing`, before a switch's journal is deleted (`switch_unfinished`: the journal is left for the next command to remove); an error at `journal:removed` is now `head_not_flushed` too. The sweeps that make each point fail in turn count such a run as a stop after the head moved and carry on to the next point; the crash sweeps check that a crash there leaves the command done. `crates/bolt-vcs/tests/recovery.rs` fails each of the three by name, and crashes `bolt undo --to` picking up a lost `head` at every point.

Milestone 4's new commands are crashed at every write in turn (`BOLT_FAULT_AT`, a real process each time). After each stop every file must be wholly old or wholly new, and the next command that changes the project must finish the step (with `switch_finished`, unless only the journal was left) or find it not begun, and leave no journal; an amend writes no file, so its sweep checks instead that the line holds the old save or the new one:
- `an_undo_stopped_at_every_write_is_finished_by_the_next_command` and `an_undo_shelve_stopped_anywhere_is_finished_by_the_next_command` (`crates/bolt-vcs/tests/undo.rs`): the undo of a `goto`, and with `--shelve` the shelf it makes, which holds the edit whenever the undo was made;
- `a_shelf_or_unshelf_stopped_at_every_write_is_finished_by_the_next_command` (`shelf.rs`);
- `an_amend_stopped_at_every_write_leaves_the_old_save_on_the_line` (`amend.rs`): an amend writes no file, so the folder never changes, the store checks out, and the line holds either the old save or the new one;
- `running_undo_again_after_a_stop_finishes_it_and_takes_no_further_step`, `undo_to_after_a_stop_finishes_it_and_takes_no_step` and `running_unshelf_again_after_a_stop_finishes_it_and_brings_back_no_other_shelf`: the command run again finishes the stopped one and goes no further ([decision 075](decisions/075-crash-recovery.md)).

`tidy` adds three named points: `tidy:marked`, once it knows what to keep; `tidy:written`, once its new packs are in the store; and `tidy:removing`, before each old pack is removed, where an error leaves that pack with a `pack_not_tidied` warning. `tidy_stopped_at_every_step_loses_nothing` (in `crates/bolt-vcs-core/src/tidy/tests.rs`) fails a `tidy` at every step, and must have stopped at each of the three; after every stop each object it keeps still reads, and tidying again finishes the job. `packs_holding_nothing_to_keep_go_first_even_when_writing_fails` checks that packs holding nothing to keep are already gone when writing a new pack fails, so a full disk still gets space back.

Milestone 5 stops commands in the middle of a big file. `crates/bolt-vcs/tests/chunks_stopped.rs` lowers the test-only pack limit to 16 objects, so one 3 MiB file's chunks fill several packs (the limit reaches every command in the process, so these tests keep a file of their own):
- `a_save_stopped_between_chunks_leaves_the_project_as_it_was` fails a save of the file at every step: `head` must not move, the next save must store the file, every file of every save the diary names must read back whole, the store must check out, and at least one stop must fall between two of the file's chunks;
- `a_discard_or_shelf_of_a_big_file_stopped_anywhere_loses_nothing` does the same to `discard` and to `shelf` of the file, once replaced by other bytes: after the next command it is wholly one version or the other, and both are still in a save the diary names;
- `a_crash_sweep_of_a_threaded_save_stops_at_the_same_places` stops a save of the big file and 40 small ones at each step, with one worker thread and with eight, and checks that both stop at the same place and leave the same packs, as the single writer thread promises ([decision 084](decisions/084-files-are-read-once-on-several-threads.md)).

`tidy_stopped_at_every_step_loses_no_chunk` (in `crates/bolt-vcs-core/src/tidy/tests.rs`) stops `tidy` at every step with big files in the store, and checks that every file of every kept save still reads whole, with its chunks, and so does a list stored again in a young pack.

Beside them, `crates/bolt-vcs-core/tests/pack_limit.rs` is not a crash test: it checks the test-only limit itself, that it splits a command's packs until it is cleared. The limit applies to every command in the process, so that file and `import_interrupted.rs` each hold a single test.

**Differential tests against Git.** `crates/bolt-vcs/tests/import_vs_git.rs` makes repositories with Git itself, runs `bolt import`, and then `assert_matches_git` (in `tests/support/`) compares the project with what Git holds, reading Git's objects through `git cat-file --batch`:

- each commit `git rev-list --all` lists has exactly one save, which rebuilds the commit's exact bytes, and commits Git writes itself rebuild from their saves' own fields, without their Git header;
- each author and committer line in Git's own form names the save's person, time and zone, so a kept Git header can't hide a wrong one;
- each Git tree, read once, is a listing with the same names after Bolt's skip rules, the kinds its modes make, and files whose Git blob IDs, computed in the test, are the entries' IDs;
- the lines, server lines and tags are the branches, server branches and tags `git for-each-ref` lists, under the names Bolt's renaming rule gives them (the everyday test also checks a few names as written, so a wrong rule can't pass on both sides), and annotated tags keep their tag objects' exact bytes.

Git runs with nothing from the computer's set-up: no system or user config, no templates, no replace objects.

On every push, on all three systems, it compares six repositories: everyday history (renames, deletions, an executable, links, case twins, a submodule, Unicode names, a merge and an octopus merge, every kind of branch, server branch and tag, then the same with a detached `HEAD`); unusual commits written byte by byte (signatures, a merge tag, Latin-1, a change ID, `-0000`, an odd author line, an unknown header, a parent named twice); packed and loose objects with deltas; a SHA-256 repository; Git's optional files (commit-graph, multi-pack index, bitmap, reverse index, worktree config, only packed refs); and names Windows can't hold, saved again after the import. One more test checks that a link Git wrote keeps its target when saved, on all three systems: Git for Windows writes the `/` in a link's target as `\`, and Bolt stores `/` there, as Git does ([decision 045](decisions/045-link-targets-stored-with-slashes.md)). In CI the test fails rather than skip if Git can't make the link. Before milestone 3 built this, a nightly job ran the test on GitHub's Windows runner as the evidence the decision rests on: in [run 41644016857](https://github.com/WisHonor/Bolt/actions/runs/41644016857) it failed as it should, saving `dir\target.txt` where Git stores `dir/target.txt`.

Git LFS is held to Git LFS itself (milestone 5). `an_lfs_repository_matches_what_git_lfs_checks_out` (`crates/bolt-vcs/tests/import_lfs.rs`) has Git LFS track the `.bin` and `.psd` files of a three-commit history, among them a 3 MiB file edited in the middle, imports it, and checks that each commit's save holds exactly the files as they were committed, which a checkout with Git LFS gives back. `after_git_lfs_checkout_the_save_goes_through` checks out a pointer with Git LFS told to skip, and checks that the first save stops at it and goes through once `git lfs checkout` has written the file. Both run `git lfs install --local` in their own repository, never in the user's or the global config, and skip, saying so, where `git lfs` isn't found; GitHub's runners have it, so CI runs them on all three systems.

Nightly and when started by hand (§4), `a_real_repository_matches_git` imports a full clone of Git's own repository (git/git; it checks the clone isn't shallow) and compares all of it. It imports in its own process and prints how long the import took and the process's peak memory, which Linux reports as `VmHWM`, read right after the import.

Measured on 2026-11-03 in release builds, on git/git as of 2026-11-01: 85,977 commits and 1,012 tags (Bolt leaves out the one that tags a file). Every commit, tree, file and ref matched Git; 98 commits have trees in forms Git no longer writes, and 219 keep their Git header.

- GitHub's Linux runner (`ubuntu-latest`, nightly run 41638396168): imported in 102.0 s, with a peak of 583 MiB (`VmHWM`).
- A Windows 11 laptop (AMD Ryzen 7 7730U with 8 cores, 16 GB of RAM, an NVMe SSD) with Git 2.50.1: imported in 165 s, with a peak working set of 503 MiB; the comparison took 124 s more. Windows tells a process its peak memory only through a system call, so there the test prints none: this figure is the test process's `PeakWorkingSet64`, read by PowerShell twice a second and taken as the import ended (the comparison never raised it).

Measured again on 2026-11-09, by the `Bench` workflow's `import-git` job rather than this test ([benchmarks.md](benchmarks.md) §3): git/git as of 2026-11-06 (86,059 commits and 1,022 refs), imported by `bolt` built from `main` and from milestone 5, three times each on one machine, with each import's time and peak memory from GNU `time`. On GitHub's Linux runners `main`'s took 165.0 s and milestone 5's 165.1 s on an AMD EPYC 7763, and 168.9 s and 171.2 s on an EPYC 9V74, within 1.3% of each other; an earlier run took 101.3 s with `main`'s on an EPYC 9V45, so the runner's processor matters more than the version, and nightly runs of this test on `main` have imported it in 95 to 168 s. The peak was about 573 MB (547 MiB) with `main`'s and 669–680 MB (638–649 MiB) with milestone 5's, about 100 MB more: most likely the Git reader's cache of rebuilt objects, which then stayed near its 256 MiB budget, since cut to 96 MiB ([decision 104](decisions/104-an-import-keeps-96-mib-of-rebuilt-objects.md)). The laptop wasn't measured again.

**Ignore rules against Git.** Bolt's ignore matcher is a port of Git's own, and three kinds of test hold it to Git:
- Every row of Git's wildmatch table (`t/t3070-wildmatch.sh`, 190 rows) passes, with and without letter case folded. A port of Git's recursive matcher, kept in the tests, must agree with Bolt's loop on 20,000 random patterns and texts. A count of the steps the matcher takes (not a clock) shows that its work stays within the pattern's length times the text's.
- `crates/bolt-vcs/tests/ignore_vs_git.rs` writes random rule files in random projects (as `.gitignore` for Git and `.boltignore` for Bolt, in several folders, with names in both letter cases and in composed and decomposed Unicode). For 256 projects each, it checks that a save keeps exactly the files `git ls-files --others --exclude-standard` lists, and that the verdict on every path is the one `git check-ignore --no-index -v` gives. A third check lays a `.boltignore` of mostly `!` lines beside the `.gitignore` files and shows Git only the `.gitignore` files: Bolt's verdict from the `.gitignore` lines alone, which the warning about files a `.boltignore` takes back rests on, must still be Git's. Git is told what the drive is like (letter case, Unicode form) and kept from the user's own ignore list.
- The same file holds the cases of Git's own `t/t0008-ignores.sh` that need only a project's own ignore files, and a test of Git's two personal lists ([decision 047](decisions/047-git-personal-ignore-lists-read.md)): a user's own list, named to Git as `core.excludesFile`, and `.git/info/exclude`, with project rules that take back some of their lines, must leave a save exactly the files Git lists. The CLI tests point `HOME` and `XDG_CONFIG_HOME` at a folder of their own and remove `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_NOSYSTEM`, `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_COUNT` from each `bolt` they run, so the real user's Git settings never reach them; the engine's own tests hand it the variables it reads, never setting the process's.

Git before 2.52 reads a `**` right after the literal start of a pattern with a `/` differently, and Bolt follows 2.52 and later; with an older Git such lines are left out of the random rules. The CI runners' Git is new enough that nothing is left out.

**Fuzz targets.** Twenty-three cover the decoders and parsers of data from outside Bolt:
- Bolt's records: `decode_listing` (folder listings), `decode_save`, `decode_diary` (diary entries), `decode_tag_list`, `decode_server_lines` and `decode_project_link` (project links, [storage-format.md](storage-format.md) §7; what decodes must encode back to the same bytes).
- Big files (milestone 5): `decode_chunk_list` (chunk lists, [storage-format.md](storage-format.md) §6; what decodes must encode back to the same bytes) and `cut_chunks` (the cutter: every chunk at most 256 KiB, every one but the last longer than 16 KiB, the sizes adding up to the file's, and the same cuts when the file is handed over a few bytes at a time).
- Bolt's files: `open_pack` (a pack of either version, with its index, trailer and every entry, each also looked up by its ID and read as a record, as a chunk list and as content), `format_file` (`.bolt/format`), `change_ids` (`cache/change-ids` and its seal), `other_lines` (`cache/other-lines` and its seal), `file_cache` (`cache/files`), `decode_journal` (`state/journal`) and `name_rules` (a list of names given to `validate_name`, `is_git_alias` and `folder_problems`: the always-on name rules, the `.git` spellings and the clashes among one folder's names).
- `ignore_rules`: ignore files, the matcher and wildmatch, on drives that do and don't ignore letter case or compose Unicode.
- `parse_rules` (milestone 6): `bolt.toml` ([storage-format.md](storage-format.md) §12): nothing panics, what is kept keeps to its limits, a size Bolt writes reads back the same, and no warning about the file holds an escape character. It first runs in the nightly job once milestone 6 is merged into `main`.
- The Git reader: `git_loose` (loose objects, as they are and compressed, to get past zlib), `git_pack` (a pack and its index, given the checksums no fuzzer finds by chance), `git_delta`, `git_objects` (commits, trees, tags, people, and the tests for Git LFS pointers: a pointer Git LFS's parser reads, written in the exact form Git LFS writes, must read back the same and count as exact), `git_refs` (`packed-refs` and `HEAD`, then the renaming of branch and tag names) and `git_config`.

The decoder for conflict records gets its own in the milestone that builds it.

**Malicious-repository corpus.** At least one case per threat in [security.md](security.md) §4: path tricks, `.bolt` spellings, symlink escapes, case and Unicode collisions, device names, bombs, non-canonical encodings, wrong fingerprints, truncated packs and corrupted indexes. The cases from the review of Git's published vulnerabilities (2026-11-02, security.md §6) are in `crates/bolt-vcs/tests/corpus_git.rs`: each is a Git repository written byte by byte with `Craft`, which only Bolt reads, run through `bolt import` (in the test's own process where a sweep imports a thousand times), and each test checks the exact refusal, or what was left out and how it was listed, and that nothing was committed when the import stopped. The write-out cases (milestone 3) are in `crates/bolt-vcs/tests/corpus_writeout.rs`: each plants a save, or a journal, as a hostile `.bolt` could hold it, runs `bolt goto` onto it, and checks what was written and that nothing reached outside the project (security.md T1 to T5). The hostile diaries (milestone 4) are in `crates/bolt-vcs/tests/corpus_diary.rs`: undo, redo, `undo --to` and unshelf of planted records, each case seen failing with its defence taken out (security.md T26 and §6; the links-leading-out defence was seen failing on CI, 2026-11-07, since the Windows laptop the tests are written on can't make links). The hostile chunk lists (milestone 5) are in `crates/bolt-vcs/tests/corpus_chunks.rs`: each plants a save naming a big file through a chunk list no honest writer makes, runs `goto`, `discard`, `status`, `changes` and `show` over it, each stopped after 60 s if it hangs, and checks that the list is refused as damage, naming its pack, or that a good copy is read, and that nothing reached outside the project; each case was seen failing with its defence taken out (security.md T9 and §6). Milestone 5 also added Git LFS's write-out lessons to `corpus_writeout.rs` (a hard link at each path a switch writes, and a folder swapped for a link, each with a file stored as chunks; CVE-2025-26625), and `corpus_git.rs`'s Git LFS case now checks that a pointer comes in as its file and a look-alike as it is. The hostile rule files and planted presets (milestone 6) are in `crates/bolt-vcs/tests/corpus_rules.rs` (security.md T33 and T34, storage-format.md §12): a `bolt.toml` that is a link out of the project, a folder, a pipe (Unix) or 2 MiB long; TOML of brackets, tables and dotted keys nested hundreds of thousands deep; every number at its limit and one past it; keys, values, a preset label and a pattern holding escape codes, run through `start`, `save` and `setup` in a log and on a terminal with colour (checked to be on), and `setup` and `save` with `--json`; as many rules as fit in 1 MiB (349,522 passed over, or 37,448 kept); a `.boltignore` with ten thousand start marks, with and without end marks, where `setup --preset` replaces only the first block and `undo` gives back every byte; a `.boltignore` that is a link, which stops `setup --preset` and `start --preset` before either rule file is written; every engine's and language's files planted at once, which change only the suggestion; 25,000 names (a quarter more than a look meets before it stops), links named like an engine's folders that point at a folder of 21,000 names, and engine files 200 folders deep, each looked at in bounded time; and a Git repository whose history holds rule files, where only the folder's `bolt.toml` counts: it keeps a 3 MiB file whole that Git's copy, and Bolt's own 1 MiB, would cut, through the import and a later save. A command over a hostile file is stopped after 120 s if it hangs; the slowest, `start --preset code` in the folder of many names, takes at most a few tens of seconds on the slowest system (its first save walks every name), and most take under a second. The cases that need a link to a file run where the account can make one (CI), and the pipe on Unix only. The terminal's side (security.md T36) is in `crates/bolt-vcs/tests/terminal.rs`: `project_text_is_escaped_with_colour_on` runs `status`, `changes`, `history`, `show`, `undo --list`, `shelf --list`, `setup` and `verify` over a file name, a message, an author, a shelf message and a `bolt.toml` that would drive the terminal, with colour and with `NO_COLOR`, and checks both are escaped and the same once Bolt's own colour codes are taken out (and `goto` once, with colour); `a_line_name_that_spells_an_escape_code_cannot_recolour_the_row` and `cutting_a_path_never_cuts_through_an_escaped_character` pin the rows and the cuts of §7 of terminal.md; and `nothing_printed_ever_holds_a_wrapping_mark` checks each step's exit code. Run them with `cargo test -p bolt-vcs --all-features --test corpus_rules` and `--test terminal`: the cases with colour need `--all-features`, which builds the faked terminal (`BOLT_FAKE_TERMINAL`). The write-out, diary and chunk-list corpora share the helpers in `crates/bolt-vcs/tests/support/corpus.rs`. `crates/bolt-vcs/tests/corpus.rs` runs the malicious names through `bolt save`, and checks that every `.bolt` spelling is left out with a warning (decision 059).

**Big zlib streams.** Bolt inflates Git's objects with miniz_oxide, 16 KiB of input a call. Given no input, miniz_oxide can still write the rest of a copy and then say it made no progress, which once cost big, mostly-zero files their last bytes. A unit test in `git/odb.rs` inflates the smallest stream found to do that, 52 MiB of zeros, on every push. `big_mostly_zero_streams_inflate_whole` sweeps zeros and sparse data of 110 to 300 MiB at three compression levels, checking each byte against the data compressed; it takes a few minutes in a release build, so it is ignored in normal runs and runs nightly (§4).

Each runs on the systems its attack needs; six of milestone 2's run on Linux only: five measure peak memory through `/proc`, and one of RT3-5's needs a drive where letter case counts. Of milestone 3's, `rt5_4` runs on Unix only (hard links and mode bits) and `rt5_6` on Windows and macOS only (a drive that ignores case). Of milestone 4's, `rt6_1` and `rt6_2` run on every system, while `rt6_4` (it measures peak memory) and `rt7_1` run on Linux only. RT6-3's proof (the pick-up after a stopped switch, deferred by decision 079) and RT7-2's (lengthening the undo window after a `tidy`, deferred by decision 080) were ignored until milestone 6 fixed both, and run again ([decision 123](decisions/123-follow-ups-done-or-moved-past-v0.1.md)).

**The speed work's red-team proofs** (milestone 6, [decisions 111](decisions/111-rulings-after-the-first-red-team-session-on-the-speed-work.md) and [112](decisions/112-rulings-after-the-second-red-team-session-on-the-speed-work.md)). `crates/bolt-vcs/tests/redteam12.rs` holds the first session's three, each fixed and running on every push: `rt12_1` (an amend among 10,000 lines stays within a memory cap) on Linux, where an address-space cap is enforced; `rt12_2` (a scattered small read of a pack costs a small read) on Linux, where the bytes a process read can be counted; `rt12_3` (`goto` with a whole ID that no save has says so, whatever a list claims) on every system. `crates/bolt-vcs/tests/redteam13.rs` holds the second session's two, both fixed and both on Linux, for the same count of bytes read: `rt13_1` (tiny chunks stored in pairs, each pair in another block of the pack, still cost small reads) and `rt13_2` (a second amend doesn't read the other lines' saves again).

**Windows-specific tests.** A helper process holds a file open, to test retries and the "file in use by" message; reserved names; long paths; read-only files; the hidden `.bolt/` folder; junctions inside and around `.bolt/`; a project nested as deep as a path allows, 2,048 folders whose last path is 4,095 bytes (§4); an undo stopped by a file another program holds, finished by the next undo (`an_undo_with_a_file_held_open_is_finished_by_the_next_command`); renames, removals and new folders still working when written through to the disk, and read-only files replaced and removed on the plain path FAT and exFAT get (in the platform crate, run on NTFS; [decision 076](decisions/076-renames-reach-the-disk-on-windows.md)).

**Memory and races.** Some tests measure what a hostile or huge input costs, or race the walk:
- `crates/bolt-vcs-core/tests/writeout_memory.rs` writes a 300 MiB file out and checks that the process's peak memory grew by less than 100 MiB, and `pack_memory.rs` opens a planted pack whose index claims 2^24 objects and checks that it costs reads, not memory. Only Linux reports the peak (`VmHWM`), so each file holds a single test. `shelving_a_big_file_uses_little_memory` (`crates/bolt-vcs/tests/shelf.rs`, Linux) shelves a 300 MiB file of noise and brings it back, and checks that each process peaked under 100 MB.
- `bolt changes` on a file of 60 MiB of newlines, past the line limit ([decision 064](decisions/064-changes-line-limit.md)), must finish within 30 s, and on Unix under a 512 MB address-space cap.
- `crates/bolt-vcs-core/tests/swapped_folder.rs` swaps a folder for another between its listing and the look at its files, and checks that the save is refused.
- `saving_a_10_gib_file_stays_under_500_mb` (`crates/bolt-vcs/tests/speed.rs`, ignored, Linux only) is the memory gate (§5).
- `an_import_reads_each_big_blob_once` (`crates/bolt-vcs/tests/chunks.rs`) imports a 3 MiB file and a 66 MiB one, the second too big for Git's reader to hand over whole, and on Linux checks through `/proc/thread-self/io` that the import read less than 1.5 times the bigger one's size, which reading it twice would exceed ([decision 084](decisions/084-files-are-read-once-on-several-threads.md)).
- `a_big_file_changed_during_the_save_stops_it` (`chunks_stopped.rs`) makes a big file grow once the save has stored part of it, and checks that the save is refused and `head` stays where it was.

**What speed puts at risk (milestone 6, [security.md](security.md) T32).** Every shortcut milestone 6 added has tests that it is never taken where it would be wrong.
- Through the `bolt` command, in `crates/bolt-vcs/tests/speed_shortcuts.rs`: a file cache or a change-ID cache sealed with another key is never trusted (`a_planted_cache_is_never_trusted`); a cache put back from an older state is trusted only file by file, each of size, times and file ID varied alone where the system lets a test set it (`a_stale_cache_is_only_trusted_file_by_file`), and a stale list of a line's saves gives what the store gives (`a_stale_change_id_cache_gives_what_the_store_gives`); a file changed within two seconds of the scan is read again; a change made right after a `goto`, with the same size, shows in the next `status`. Three more run the scan in-process, with the fault-injection feature, and act at the point between a folder's listing and the looks at its files, then run the next command through `bolt`: a file changed there is seen; a folder swapped for a link there is refused when a file in it must be read (when the cache vouches for every file there, nothing is read and the scan answers for the folder as it was listed); and a `.git` made there is seen by the next command.
- `crates/bolt-vcs/tests/early_flush.rs` saves and switches to files past the 16 MiB flush step with every flush the helper makes made to fail: the save and the `goto` stop, and nothing is named, renamed into place or moved on the strength of a flush that failed. It also checks that a save writes the same packs with the helper as without it (the save's and the diary entry's own records aside, which hold the time).
- In the engine: the ignore index and the two-ends match agree with the plain matcher on random rules and names (`ignore.rs`); the late verdict names the same files in the two warnings as matching every name during the walk (`snapshot.rs`); a folder takes the last save's listing ID only when every entry is equal; the one-read path refuses what the streamed path refuses, frame by frame (`pack.rs`); a store that takes a listing read ahead remembers exactly what a store that read it itself remembers, in six cases, and the walk's scan, warnings and store are the same with the helper on and off (`store.rs`, `walk.rs`); a list of a line's saves that lies under a good seal changes no save shown or gone to (`history.rs`); a deep chain's folders are each opened at most twice (`walk.rs`); a pack reader's blocks stay within four times the bytes asked of it when reads come in pairs across blocks, and a run of side-by-side reads is answered from one block once 16 KiB has been asked (`pack.rs`); `cache/other-lines` reads back as written, refuses each broken rule, keeps a run true at its cap and loads as empty under another key (`otherlines.rs`, with its vector in `tests/vectors.rs`); and a second amend reads no save of a line that hasn't moved, while the check before an amend names the same lines with the kept runs as without them (`history.rs`).
- The three memory tests of `cli.rs` run `bolt` with its address space capped at 64,000 KB, under one arena of the C library's allocator, so the cap measures what `bolt` holds ([decision 110](decisions/110-the-last-saves-listings-are-read-ahead-of-the-walk.md)).

**CLI tests.** Each command has its own file in `crates/bolt-vcs/tests/` (`status.rs`, `changes.rs`, `goto.rs`, `discard.rs`, `lines.rs`, `undo.rs`, `shelf.rs`, `amend.rs` and `tidy.rs` beside `cli.rs` and `import.rs`; `recovery.rs` holds the lost `head` and the warnings after `head` moves). Milestone 5's features have files of their own: `chunks.rs` (big files end to end: chunking changes no ID, big files go to and come back byte for byte, an import reads each big blob once and rebuilds a long history of a big file within its allowance, and the way past the allowance that its stop names works) and `import_lfs.rs` (Git LFS repositories end to end, and the first save's stop at pointer files). Milestone 6's are:
- `setup.rs`: `bolt start`'s question and `--preset`, what each preset writes, `bolt setup` showing the rules and switching presets, and `undo` and `redo` of the `setup` step;
- `verify.rs`: `bolt verify` (and `fsck`) on a sound project and a damaged one, its document against json.md, and that it changes no file Bolt stored, its own leftovers included;
- `git_words.rs`: each shortcut runs its Bolt command, each explained word changes nothing, the hint shows once per word and only on a terminal, and a `git-words` file Bolt can't use is never an error;
- `terminal.rs`: what each command prints on a terminal and without one (colour, symbols, wrapping, cutting, progress, at 60, 80 and 120 columns), and project text escaped with colour on;
- `json_formats.rs`: every command's `--json` document holds only the fields [json.md](json.md)'s tables list for it, and parses with `bolt_json` and `warnings` ([decision 117](decisions/117-what-json-covers-at-v0.1.md));
- `guide.rs`: every line of the [user guide](guide.md)'s `sh` blocks runs, in order, in a scratch project set up with the guide's own `[user]` settings, and each `bolt` command must exit with 0; an `sh` block may hold only `bolt` commands and `echo` into a file, a block marked anything but `sh`, `text` or `toml` fails the test, so none is passed over unrun, and every command `bolt` lists but `import` must be among those run; and every link in the guide, the README and `SECURITY.md` leads to a file or heading that exists. The output the guide shows is checked by reading, not by this test.

The terminal is faked for these tests: `BOLT_FAKE_TERMINAL=<columns>` makes both streams count as terminals of that width, and `BOLT_PROGRESS_QUIET_MS` shortens the 400 ms before progress shows. Both are read only in builds with the `fault-injection` feature (the tests' `--all-features`), never in a release build. The command-line tests share one test environment (`tests/support/`): the test user, no fault point, and settings and Git's own files in a folder of the test's own, with the helpers that read a project's files, saves and head. Every command must end quietly, with exit code 0, when whoever reads its output stops reading (`every_command_ends_quietly_when_its_reader_has_gone`); a stdout that fails mid-document ends the command with exit 1 and the error on stderr (`a_stdout_that_fails_mid_document_ends_it_with_the_error_on_stderr`).

## 4. CI on GitHub

- **Every push and pull request** (but a push to a `gate/` branch, which only measures a commit its own branch has already tested): formatting check, clippy with warnings denied, every test on Windows, macOS and Linux (the differential tests against Git on small repositories among them), run to the end even when one fails (`--no-fail-fast`), so one failing test file can't hide the others, a build without features, and `cargo-deny`, on the workspace and on the fuzz crate (it also checks the RustSec advisory database and that every crate comes from crates.io). On Windows, one more step runs the slow tests that save a project nested 2,048 folders deep (a last path of 4,095 bytes) and refuse one a level deeper (4,097 bytes); they are marked ignored, so only that step runs them.
- **Nightly, on every push to `main`, and when started by hand:** fuzzing of every target (§3), 5 minutes each nightly and 1 minute each otherwise.
- **Nightly, and when started by hand (not on pushes):** the differential test on a fresh full clone of git/git, on Linux in a release build, within an hour; its log must show the one test passed, and shows the import's time and peak memory (§3). The sweep of big zlib streams runs beside it, also in a release build (§3), and so do the model test with 1,024 cases (§3), the write-out of a chunk list of the most chunks a list may hold (`most-chunks`, §3), the timing of `status` on 100,000 files (§5), and the memory gate (`memory-gate`, §5), which fails its job above 500,000,000 bytes. Each of these jobs' logs must show its one test passed, and the memory gate's the peak it read too. The job that checked the links Git for Windows writes is gone since 2026-11-05: `a_link_git_wrote_keeps_its_target_when_saved` now runs on Windows on every push.
- **The `Bench` workflow** (`.github/workflows/bench.yml`), started by hand or by a push to a `bench/` branch, on GitHub's machines: the memory gate; Bolt, Git and Git with Git LFS through the same steps on the same data, on Linux and on Windows, with the speeds of the parts and what compressing again would save (§5); and git/git imported by `main`'s `bolt` and the branch's in turn (§3). A push to a `redteam/<name>-sizes` branch runs only the import of the red team's RT4-1 repository, which is attack code and runs nowhere else. Its results are copied into [benchmarks.md](benchmarks.md) by hand, with the runs they came from. The memory gate's job is in `.github/workflows/memory-gate.yml`, which both workflows call: it frees about 22 GiB of the runner's disk first.
- **The gate against Git** ([decision 099](decisions/099-a-third-speed-gate-within-twice-gits-time.md)): a `speed-gate` job, in `.github/workflows/speed-gate.yml`, which the `Bench` and nightly workflows both call, runs `bench/run.sh gate` on GitHub's Linux and Windows runners. It builds `bolt`, fetches Git's source at `v2.56.0`, times Bolt and Git through the code set's steps, ten runs each, and fails when the median of `status` with nothing changed, of a small save or of going back to the first version is more than twice Git's median ([decision 108](decisions/108-the-third-gate-compares-medians.md)); each step's mean, best and worst run are printed beside it (§5). A push to a `gate/` branch runs this job alone, to measure one change.
- **The `Release` workflow** (`.github/workflows/release.yml`, [decision 119](decisions/119-packaging-v0.1.md)) starts only by hand, or on a pull request that changes the workflow file, `about.toml`, `about.hbs` or anything under `docs/releases/`. It builds `bolt` with `--locked` for Windows (x86-64, C runtime linked in), Linux (x86-64, on the oldest Ubuntu runner) and macOS (Apple silicon, and Intel on an Intel runner), runs each program it built (`--version`, then `start --preset custom`, a save, `history` and `verify` in a scratch folder with its own `BOLT_CONFIG_DIR`), and packs each into an archive (the `.tar.gz` ones with every entry owned by 0/0, by number) that must hold exactly the program, `README.md`, `docs/guide.md` and `THIRD-PARTY-LICENSES.html` (written by `cargo-about`, downloaded at a pinned version and checked against its SHA-256). On a pull request, or started by hand from any branch but `main`, it stops there: the archives are the run's artifacts, and a change is proved by that run's log, which shows each smoke test's commands and each archive's listing. Started by hand from `main`, a last job, the only one that may write, checks that `Cargo.toml`'s version is the release's and that no release (drafts included) or tag `v0.1.0` exists, writes `SHA256SUMS` and makes a draft release on the commit the archives were built from. If that job fails halfway, a draft it already made stays, and the next start refuses because a release named `v0.1.0` exists: delete that draft by hand on the repository's releases page, then start again. The pull-request run is the workflow's only test until that first start from `main`.
- The whole suite runs locally before a push, and pushes come at task boundaries: CI minutes counted while the repository was private (for a time from 2026-11-05; it is public again, checked 2026-11-06), and a local run finds a failure sooner.
- A `.gitattributes` file turns off Git's line-ending conversion, so test files stay byte-exact on Windows.
- Workflows run with read-only permissions, actions are pinned to exact commits, and Dependabot opens weekly update pull requests for Rust crates and actions.

## 5. Benchmarks and measurements

- **Micro:** the parts of a save, each timed alone on one thread: the cutter, run over 256 MiB of noise as one stream; BLAKE3, fed the same noise 64 KiB at a time; and zstd at levels 3, 9 and 19, on each 64 KiB piece of that noise and of 64 MiB of sound, one piece at a time. And, for compressing again, what levels 9 and 19 store against level 3, on the pieces a save stores (a small file whole, a big one's chunks) of code, of uncompressed assets and of compressed ones, and how long they take. These are the ignored tests `speeds_of_the_parts` and `what_compressing_again_would_save` in `crates/bolt-vcs-core/tests/throughput.rs`, run in a release build by the `Bench` workflow and by hand; they print MB/s and bytes, with no `criterion` ([decision 088](decisions/088-benchmarks-and-the-speed-gates.md); results in [benchmarks.md](benchmarks.md) §4 and §5).
- **End to end:** `bolt` against Git and against Git with Git LFS, with the same steps on the same data (`bench/run.sh`, timed with `hyperfine`, 5 runs after a warm-up): a code project and Godot's demo projects at fixed tags, and generated sets (20 files of noise, a 1 GiB file in 10 versions, 1 GiB of one repeated block). The steps: first save, saving a small change, `status` on an unchanged project, `status` after touching one big file, going back to the first version, and the space each takes. Imports of a Git LFS repository and of a 200 MiB file in 50 versions are timed too, with their sizes against Git's. Results are published with the machines and versions they ran on ([benchmarks.md](benchmarks.md) §2 and §3).
- **Release gates for v0.1** ([decision 023](decisions/023-v0.1-speed-bar.md)): saving a 10 GB file uses at most about 500 MB of memory, and `status` on an unchanged 100,000-file project takes under 2 seconds on an SSD. Both run as automated benchmarks; the memory gate fails its job above the limit, while the status time is printed and read, not enforced, until v0.1. A third gate ([decision 099](decisions/099-a-third-speed-gate-within-twice-gits-time.md)) holds Bolt to Git on a code project: on Git's source at `v2.56.0`, `status` with nothing changed, a small change saved, and going back to the first version each take Bolt at most twice Git's time, on GitHub's Linux runner and on its Windows runner. `bench/run.sh gate` measures it as the end-to-end steps above are measured, with 10 timed runs of each step, both tools in one job on one machine, and fails when a step is over; the `speed-gate` job runs it nightly (§4). Everything else is measured and published, not gated.
- **Results:** [benchmarks.md](benchmarks.md) gives the gates' numbers, Bolt against Git and Git LFS, the imports, the parts of a save and the ruling on compressing again, with the machines, the versions and the exact commands, the steps Git or Git LFS wins included.
- **The status gate, measured:** `crates/bolt-vcs/tests/speed.rs` (`status_on_an_unchanged_100_000_file_project`, ignored; run by hand and nightly) builds 100,000 small files, 100 to a folder, an hour old, saves them, runs `status` twice and prints both times. First run, 2026-11-05, on a Windows 11 laptop (Ryzen 7 7730U, NVMe), release build: **1.26 s, then 1.20 s**, under the 2 s gate; the first save took 26.3 s. Again on 2026-11-06, after the file cache began reading each file's change time (decision 069): **1.30 s, then 1.36 s**; the first save took 36.8 s. The test saves with `--yes`, since 100,000 new files ask the large-save question. Before `save` and `status` looked at files on several threads, the same kind of project took about 4.4 s. On Windows each file is still opened once to read its size and time, since the folder listing can hold old ones for a file open for writing; most of what is left is those opens. Runs on this laptop vary by up to about 0.7 s (Windows Defender working through new files, the power state), so the nightly Linux run is the reference figure. Measured again on 2026-11-09, after milestone 5's changes ([benchmarks.md](benchmarks.md) §1): **0.70 s, then 0.70 s** on GitHub's Linux runner (nightly run 42592855953, whose first save took 1.93 s), and **1.16 s, then 1.15 s** on the Windows laptop, whose first save took 5.10 s.
- **The memory gate, measured:** `saving_a_10_gib_file_stays_under_500_mb` (`crates/bolt-vcs/tests/speed.rs`, ignored) writes 10 GiB of BLAKE3's extendable output into a temporary folder, a mebibyte at a time, runs `bolt save --yes` on it, and reads the `bolt` process's `VmHWM` from `/proc` every 20 ms. So it measures on Linux only, and says it skipped elsewhere. It fails above 500,000,000 bytes, and when it read no peak or the file wasn't stored. The nightly and `Bench` workflows run it; on Windows the same save is measured by hand, its peak working set read by PowerShell. Measured on 2026-11-09: **43.5 MB** on GitHub's Linux runner and **48.7 MB** on the Windows laptop ([benchmarks.md](benchmarks.md) §1).
- **Dedup:** how much space chunking really saves on real assets (textures, models, audio, video, engine files), so claims stay honest (design.md risk 4). Milestone 5 measured it on Godot's demo projects and generated sets ([benchmarks.md](benchmarks.md) §2): ten versions of a 1 GiB file take 1,041 MiB in Bolt against 10 GiB in Git, and Godot's demos take 3% more in Bolt than in Git. Other real assets are still to be measured (design.md §7).
